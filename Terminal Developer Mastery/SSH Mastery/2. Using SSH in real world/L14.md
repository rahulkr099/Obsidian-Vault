# Step 1 — Connect to the Server

If you've configured SSH aliases:

```bash
ssh production
```

Otherwise:

```bash
ssh ubuntu@203.0.113.10
```

Verify you're on the correct server:

```bash
hostname
```

```bash
whoami
```

---

# Step 2 — Check Server Health

Before changing anything:

Memory:

```bash
free -h
```

Disk:

```bash
df -h
```

CPU Load:

```bash
uptime
```

If disk usage is at 100% or memory is critically low, investigate before deploying.

---

# Step 3 — Navigate to the Project

Example:

```bash
cd /var/www/backend
```

Verify:

```bash
pwd
```

Expected:

```
/var/www/backend
```

---

# Step 4 — Check Git Status

Current branch:

```bash
git branch
```

Status:

```bash
git status
```

Recent commits:

```bash
git log --oneline -5
```

This helps ensure you're deploying from the expected branch.

---

# Step 5 — Pull the Latest Code

```bash
git pull origin main
```

Possible output:

```
Updating...
Fast-forward
```

Or:

```
Already up to date.
```

---

# Step 6 — Install Dependencies

If dependencies changed:

```bash
npm ci
```

If no lockfile exists:

```bash
npm install
```

For production deployments, `npm ci` is generally preferred because it installs exactly what's recorded in `package-lock.json`.

---

# Step 7 — Run Database Migrations (If Required)

Many applications include database migrations.

Example:

```bash
npm run migrate
```

Not every project has this step, but if yours does, it should happen before restarting the application.

---

# Step 8 — Restart the Application

Using PM2:

```bash
pm2 restart backend
```

Check status:

```bash
pm2 status
```

Expected:

```
backend    online
```

---

# Step 9 — Verify the API

Health endpoint:

```bash
curl <http://localhost:5000/health>
```

Example response:

```json
{
  "status": "healthy"
}
```

If your project doesn't have a health endpoint yet, adding one is a good practice.

---

# Step 10 — Review Logs

Recent logs:

```bash
pm2 logs backend --lines 50
```

Look for:

```
Server started
Connected to MongoDB
Listening on port 5000
```

Avoid deploying and immediately disconnecting without checking logs.

---

# Step 11 — Verify Nginx

Status:

```bash
sudo systemctl status nginx
```

Reload after configuration changes:

```bash
sudo systemctl reload nginx
```

Only restart Nginx if necessary.

---

# Step 12 — Test from Outside

From your local machine:

```bash
curl <https://api.example.com/health>
```

Or simply visit:

```
<https://api.example.com/health>
```

A deployment isn't complete until you've confirmed users can reach the application.

---

# Deployment Checklist

```
✓ Connected to correct server

✓ Checked memory

✓ Checked disk

✓ Checked CPU load

✓ Pulled latest code

✓ Installed dependencies

✓ Ran migrations

✓ Restarted application

✓ Verified PM2

✓ Tested health endpoint

✓ Checked logs
```

This is a solid checklist for most Node.js backend deployments.

# Scenario 1 — Deployment Fails

After restarting:

```
backend    errored
```

First step:

```bash
pm2 logs backend --lines 100
```

Example:

```
Error:
Cannot find module dotenv
```

Cause:

Dependencies weren't installed.

Fix:

```bash
npm ci
```

Restart:

```bash
pm2 restart backend
```

---

# Scenario 2 — Database Connection Error

Logs:

```
MongoNetworkError
```

Things to check:

- Connection string
- Environment variables
- Atlas IP allowlist
- Database availability

Restarting repeatedly won't fix a configuration issue.

---

# Scenario 3 — Port Already in Use

Example:

```
EADDRINUSE
```

Find what's listening:

```bash
ss -tlnp
```

Or:

```bash
lsof -i :5000
```

Investigate before killing any process.

---

# Scenario 4 — Disk Full

Check:

```bash
df -h
```

Example:

```
/dev/sda1
100%
```

Possible cleanup:

```bash
pm2 flush
```

or rotate/remove old logs according to your team's policies.

---

# Scenario 5 — Nginx Configuration Error

Before reloading:

```bash
sudo nginx -t
```

Expected:

```
syntax is ok
test is successful
```

Only then:

```bash
sudo systemctl reload nginx
```

# Automating the Deployment

Instead of typing every command manually:

```bash
#!/bin/bash

cd /var/www/backend || exit 1

git pull origin main

npm ci

pm2 restart backend

curl <http://localhost:5000/health>
```

Run:

```bash
./deploy.sh
```

Automation reduces mistakes and ensures a consistent deployment process.

# Common Mistakes

## ❌ Skipping Health Checks

The process restarted successfully.

But does the API actually work?

Always verify.

---

## ❌ Not Reading Logs

A successful restart doesn't guarantee a healthy application.

Logs often reveal startup issues immediately.

---

## ❌ Deploying to the Wrong Branch

Always confirm:

```bash
git branch
```

before pulling.

---

## ❌ Ignoring Resource Usage

A nearly full disk or exhausted memory can cause deployment failures that have nothing to do with your code.

# Key Takeaways

- Treat deployments as a repeatable process, not a series of random commands.
- Verify each stage before moving to the next.
- Logs and health checks are essential after every deployment.
- Small deployment scripts reduce human error and improve consistency.

# Practical Assignment ⭐

Create a simple deployment script for one of your Node.js projects:

```bash
#!/bin/bash

set -e

echo "Checking Git status..."
git pull origin main

echo "Installing dependencies..."
npm ci

echo "Restarting application..."
pm2 restart backend

echo "Testing health endpoint..."
curl <http://localhost:5000/health>

echo "Deployment complete!"
```

Save it as:

```
deploy.sh
```

Make it executable:

```bash
chmod +x deploy.sh
```

Run it:

```bash
./deploy.sh
```

Even if you're practicing locally, this exercise builds the habits you'll use when deploying applications to real servers.

## Pro Tip ⭐

For a backend engineer, **deployment is not finished when `pm2 restart` succeeds**.

A professional deployment ends only after you can confidently answer **yes** to all of these:

- ✅ Is the application running?
- ✅ Does the health endpoint respond?
- ✅ Are the logs clean?
- ✅ Can users reach the service?

That verification mindset is what separates reliable deployments from risky ones.
