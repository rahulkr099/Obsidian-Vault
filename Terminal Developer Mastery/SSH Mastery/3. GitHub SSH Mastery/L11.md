# Why Commit Signing Exists

Imagine someone pushes a commit like this:

```
Author: Rahul Kumar
Message: Fix login bug
```

Can GitHub know for certain that **you** created it?

Without signing:

**Not necessarily.**

Git author information is just text and can be configured to almost anything.

For example:

```bash
git config user.name "Rahul Kumar"
git config user.email "rahul@example.com"
```

or even:

```bash
git config user.name "Linus Torvalds"
```

Git itself doesn't verify that the name is genuine.

Commit signing provides cryptographic proof that the commit was created by someone who possesses a specific private key.

---

# Authentication vs Commit Signing

This is one of the most misunderstood topics in Git.

## SSH Authentication

Used when communicating with GitHub.

Example:

```bash
git push
```

SSH proves:

> "I am allowed to access this repository."

---

## Commit Signing

Used when creating a commit.

Example:

```bash
git commit -m "Fix authentication"
```

Signing proves:

> "This commit was created using my private key."

---

```

   ▼

```

vs

```

```

These happen at different stages.

# What Is the "Verified" Badge?

On GitHub, you may see:

```
✔ Verified

Fix authentication bug
```

This means GitHub successfully verified the commit's cryptographic signature against a public key associated with the author's account.

It does **not** necessarily mean the code is correct or secure.

---

# Before SSH Commit Signing

GitHub might show:

```
Add JWT authentication
```

No badge.

---

# After SSH Commit Signing

GitHub shows:

```
✔ Verified

Add JWT authentication
```

This indicates GitHub verified the commit signature.

# Requirements

You need:

- ✅ Git 2.34 or newer (SSH commit signing support)
- ✅ An SSH key
- ✅ The corresponding public key added to GitHub
- ✅ GitHub account

Check your Git version:

```bash
git --version
```

Example:

```
git version 2.46.0
```

---

# Step 1 — Find Your Public Key

Display it:

```bash
cat ~/.ssh/id_ed25519.pub
```

You'll need the **public key**.

---

# Step 2 — Tell Git Which Key to Use

Configure Git:

```bash
git config --global gpg.format ssh
```

This tells Git:

> "Use SSH instead of traditional GPG for commit signing."

---

Next:

```bash
git config --global user.signingkey ~/.ssh/id_ed25519.pub
```

Notice:

You specify the **public key file**.

---

# Step 3 — Enable Automatic Signing

```bash
git config --global commit.gpgsign true
```

Now every new commit will be signed automatically.

---

# Verify Your Configuration

Check:

```bash
git config --global --list
```

You should see something like:

```
gpg.format=ssh
user.signingkey=/home/rahul/.ssh/id_ed25519.pub
commit.gpgsign=true
```


```bash

```

If your key is passphrase-protected and not already unlocked, SSH or `ssh-agent` may prompt you.

# View the Signature Locally

Show the latest commit:

```bash

```

Example:

```

```

That means Git recognized the signature locally.

# Common Mistakes

## ❌ Confusing GPG with SSH

Git has long supported GPG signing.

Modern Git also supports SSH signing.

Both are valid.

SSH is often simpler if you're already using SSH keys for GitHub.

---

## ❌ Using the Wrong Public Key

If GitHub doesn't know the public key corresponding to the signing key, commits won't be shown as verified.

---

## ❌ Expecting Old Commits to Change

Enabling signing today doesn't retroactively sign older commits.

Only **new** commits are signed.

---

## ❌ Forgetting `ssh-agent`

If your SSH key has a passphrase:

```bash
ssh-add ~/.ssh/id_ed25519
```

helps avoid repeated prompts.

# Key Takeaways

- SSH authentication and SSH commit signing are different concepts.
- Authentication happens during Git operations like `push` and `pull`.
- Commit signing happens when you create a commit.
- The **Verified** badge indicates GitHub successfully verified the commit signature.
- SSH signing is a convenient alternative to GPG signing if you already use SSH keys.
