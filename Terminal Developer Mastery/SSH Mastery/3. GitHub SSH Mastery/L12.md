# SSH Mastery — Module 3, Lesson 12

# GitHub SSH Security Best Practices ⭐⭐⭐⭐⭐

Knowing SSH is good.

Using SSH **securely** is what professional developers do.

A stolen SSH private key can give an attacker access to your Git repositories, CI/CD systems, and sometimes production servers.

This lesson focuses on preventing that.

---

# Learning Objectives

By the end of this lesson, you'll know how to:

- Protect your private keys
- Choose strong passphrases
- Rotate SSH keys
- Remove compromised keys
- Audit your GitHub SSH keys
- Secure your development machine
- Follow industry best practices

---

# Security Principle #1

## Your Private Key Is Secret

Never share:

```
~/.ssh/id_ed25519
```

Never upload it to:

- GitHub
- Google Drive
- Slack
- Discord
- Email
- Stack Overflow

Only the **public** key should ever be shared.

---

# Private vs Public

Safe to share:

```
id_ed25519.pub
```

Never share:

```
id_ed25519
```

Think of it like:

```
Public Key
↓

Padlock
```

Anyone can have a padlock.

But:

```
Private Key
↓

The only key
```

Only you should possess it.

---

# Security Principle #2

## Always Use a Passphrase

When creating a key:

```bash
ssh-keygen -t ed25519
```

You'll be asked:

```
Enter passphrase:
```

Don't leave it blank unless you have a specific reason.

A passphrase protects your private key if someone copies the file.

---

# Weak vs Strong Passphrases

Weak:

```
123456
password
rahul
```

Strong:

```
Coffee!Train#Ocean2026
```

Or use a password manager to generate and store one.

---

# Security Principle #3

## Check File Permissions

SSH refuses to use private keys that are too permissive.

Check:

```bash
ls -l ~/.ssh
```

Good:

```
-rw------- id_ed25519
-rw-r--r-- id_ed25519.pub
```

Fix if needed:

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519
chmod 644 ~/.ssh/id_ed25519.pub
```

---

# Security Principle #4

## Use One Key Per Device

Instead of copying the same private key everywhere:

❌ Laptop

↓

Copy

↓

Desktop

↓

Copy

↓

Work PC

Instead:

Laptop:

```
id_ed25519_laptop
```

Desktop:

```
id_ed25519_desktop
```

Work:

```
id_ed25519_work
```

If one device is lost, you only revoke that device's key.

---

# Security Principle #5

## Audit Your GitHub Keys

Over time you may accumulate:

- Old laptop
- Old desktop
- Temporary VM
- Internship machine

Review them periodically.

Example:

```
✓ Lenovo Laptop

✓ Desktop

✓ Work Mac

✗ Old College Laptop
```

Delete keys for devices you no longer use.

---

# Security Principle #6

## Rotate Keys Periodically

Organizations often rotate credentials.

Create a new key:

```bash
ssh-keygen -t ed25519
```

Upload the new public key.

Verify it works.

Then remove the old public key from GitHub.

No downtime.

---

# Security Principle #7

## Revoke Lost Devices Immediately

Imagine:

Your laptop is stolen.

Don't wait.

Immediately:

1. Remove that device's public key from GitHub.
2. Generate a replacement key for your new machine.
3. Update any SSH configurations that referenced the old key.

Because each device has its own key, you don't need to replace keys on your other computers.

---

# Security Principle #8

## Don't Commit Private Keys

Never put this inside a Git repository:

```
id_ed25519
```

Even accidentally.

If you run:

```bash
git status
```

and see:

```
id_ed25519
```

Stop immediately.

Remove it before committing.

---

# Prevent It with .gitignore

Example:

```
*.pem
*.key
id_ed25519
```

Remember:

`.gitignore` only prevents future tracking. If a private key was already committed, removing it from `.gitignore` is **not enough**—you must remove it from the repository and consider the key compromised.

---

# Security Principle #9

## Lock Your Computer

SSH security also depends on physical security.

If someone gains access to your unlocked computer:

- They may be able to use your unlocked SSH keys.
- They may access repositories without knowing your passphrase if your `ssh-agent` has already unlocked the key.

Use:

- Screen lock
- Full-disk encryption
- Strong login password

---

# Security Principle #10

## Use ssh-agent Wisely

Good:

```bash
ssh-add ~/.ssh/id_ed25519
```

Bad:

Leaving an unlocked session unattended.

Before leaving for the day:

- Lock your computer, or
- Log out.

If needed, remove loaded identities:

```bash
ssh-add -D
```

---

# Real Backend Scenario

Imagine you're working on a production payment service.

Your company laptop is stolen.

Because you:

- Used a separate SSH key
- Protected it with a passphrase
- Removed the public key from GitHub immediately

The incident is much easier to contain than if the same private key had been copied to every device.

# Useful Commands

Generate a key:

```bash
ssh-keygen -t ed25519
```

List SSH files:

```bash
ls -la ~/.ssh
```

Fix permissions:

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519
chmod 644 ~/.ssh/id_ed25519.pub
```

List loaded identities:

```bash
ssh-add -l
```

Clear loaded identities:

```bash
ssh-add -D
```

Show the public key:

```bash
cat ~/.ssh/id_ed25519.pub
```

# Common Mistakes

### ❌ Emailing Your Private Key

Never send:

```
id_ed25519
```

Even to yourself.

---

### ❌ Reusing One Private Key Everywhere

Generate a unique key for each device.

---

### ❌ No Passphrase

An unencrypted private key is much easier to misuse if it's copied.

---

### ❌ Ignoring Old Keys

Old keys on unused machines increase your attack surface.

Remove them.

---

### ❌ Assuming SSH Alone Is Enough

SSH protects authentication, but your overall security also depends on:

- OS updates
- Strong passwords
- Multi-factor authentication on GitHub
- Secure device practices

# Key Takeaways

- Keep your **private key private**.
- Protect it with a strong passphrase.
- Use one SSH key per device.
- Remove old or compromised keys from GitHub promptly.
- Never commit or upload private keys.
- Good SSH security is a combination of key management and good device security.

Perform a security audit of your SSH setup:

1. Check your SSH directory:

```bash
ls -la ~/.ssh
```

1. Verify permissions:

```bash
ls -l ~/.ssh
```

1. List loaded identities:

```bash

```

1. Review the SSH keys associated with your GitHub account and remove any that belong to devices you no longer use.
2. If your current key has **no passphrase**, consider generating a new passphrase-protected key and migrating to it.

## Pro Tip ⭐

Enable **multi-factor authentication (MFA)** on your GitHub account. Even if someone compromises your password, MFA provides an additional layer of protection for your account. SSH keys authenticate Git operations, but MFA helps protect account login and account management actions.
