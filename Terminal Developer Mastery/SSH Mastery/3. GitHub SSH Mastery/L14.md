# SSH Mastery — Module 3, Lesson 14

# Open Source Collaboration with SSH (Forks, Upstream & Pull Requests) ⭐⭐⭐⭐⭐

This lesson teaches the workflow you'll use when contributing to open-source projects (like GSSoC), where you **don't have direct write access** to the original repository.

Instead, you'll:

- Fork the repository
- Clone your fork with SSH
- Keep it synchronized with the original project
- Submit Pull Requests

This is the standard workflow used by millions of developers.

# Why Fork?

Suppose you want to contribute to:

```
github.com/opensource/backend-api
```

You don't have write permission.

Instead of pushing directly:

You create:

```
github.com/rahul/backend-api
```

This is called **your fork**.

Think of it as your own copy of the project.

---

# Visual Example

```

          │
          ▼
      Your Fork
rahul/backend-api
          │
          ▼
     Your Computer
```

You push to **your fork**, never directly to the original project.

# Clone Your Fork

Clone using SSH:

```bash
git clone git@github.com:rahul/backend-api.git
```

Move inside:

```bash
cd backend-api
```

---

# Check the Default Remote

```bash
git remote -v
```

Output:

```
origin git@github.com:rahul/backend-api.git
```

Notice:

`origin`

is **your fork**.

---

# Add the Original Repository

Now add another remote.

Example:

```bash
git remote add upstream git@github.com:opensource/backend-api.git
```

Now check:

```bash
git remote -v
```

Output:

```
origin
git@github.com:rahul/backend-api.git

upstream
git@github.com:opensource/backend-api.git
```

Perfect.

# Understanding `origin` vs `upstream`

## origin

Your repository.

You can push here.

```
origin
↓

Your GitHub Fork
```

---

## upstream

Original project.

Normally:

Read-only.

```
upstream
↓

Original Project
```

# Check for Updates

Fetch updates from the original project:

```bash
git fetch upstream
```

This downloads changes but doesn't modify your working branch.

---

# Update Your Main Branch

Switch:

```bash
git checkout main
```

Merge updates:

```bash
git merge upstream/main
```

Or, if you prefer a linear history:

```bash
git rebase upstream/main
```

---

# Push Updated Main to Your Fork

Your local `main` is now current.

Update your fork:

```bash
git push origin main
```

Now:

- Local repository ✅
- Your fork ✅
- Original repository ✅

are synchronized.

# Merge Conflicts

Suppose:

You changed:

```
login.js
```

Meanwhile:

Someone else also changed:

```
login.js
```

Git cannot decide automatically.

You'll see something like:

```
<<<<<<< HEAD

Your code

=======

Their code

>>>>>>> upstream/main
```

You must:

- Decide which code to keep
- Remove the conflict markers
- Test the result
- Commit the resolution

---

# Fetch vs Merge vs Rebase

## Fetch

```bash
git fetch upstream
```

Downloads changes.

No files change.

---

## Merge

```bash
git merge upstream/main
```

Creates a merge commit (if needed).

Safe and beginner-friendly.

---

## Rebase

```bash
git rebase upstream/main
```

Replays your commits on top of the latest upstream changes.

Creates a cleaner, linear history but requires a good understanding of Git.

# Common Mistakes

## ❌ Pushing to `upstream`

Wrong:

```bash
git push upstream main
```

Most contributors don't have permission anyway.

Push to:

```bash
git push origin
```

---

## ❌ Developing on `main`

Always:

```bash
git checkout -b feature/new-feature
```

---

## ❌ Forgetting to Update Your Fork

Before starting new work:

```bash
git fetch upstream
```

Update your local `main`, then push it to your fork.

---

## ❌ One Giant Pull Request

Instead of:

```
50 files changed
```

Prefer:

```
Fix login validation
```

One logical improvement per PR makes reviews much easier.

# Key Takeaways

- `origin` usually refers to **your fork**.
- `upstream` refers to the **original repository**.
- Always create feature branches.
- Keep your fork synchronized with `upstream`.
- Push changes to your fork, then open a Pull Request.
- Update the same Pull Request by pushing additional commits if reviewers request changes.

# Practical Assignment ⭐

Create a practice workflow (or use an open-source repository if you're already contributing):

1. Fork a repository on GitHub.
2. Clone your fork using SSH:

```bash
git clone git@github.com:YOUR_USERNAME/REPOSITORY.git
```

1. Add the original repository:

```bash
git remote add upstream git@github.com:ORIGINAL_OWNER/REPOSITORY.git
```

1. Verify your remotes:

```bash
git remote -v
```

1. Fetch updates:

```bash
git fetch upstream
```

1. Create a branch:

```bash
git checkout -b feature/practice-pr
```

1. Make a small documentation change, commit it, and push:

```bash
git push origin feature/practice-pr
```

1. Open a Pull Request from your fork to the original repository.

## Pro Tip ⭐

Before starting **every new contribution**, make it a habit to update your local `main` branch from `upstream`. This greatly reduces the chance of merge conflicts later.

A common sequence is:

```bash
git checkout main
git fetch upstream
git merge upstream/main
git push origin main
```

This keeps your local repository, your fork, and the original project aligned.
