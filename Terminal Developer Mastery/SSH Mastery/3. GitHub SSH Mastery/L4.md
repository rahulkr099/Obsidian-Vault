# SSH Mastery — Module 3, Lesson 4

# Testing Your GitHub SSH Connection

Congratulations! 🎉

If you've completed Lesson 3, your computer and GitHub should now "know" each other through SSH.

Now it's time to **test the connection**.

This lesson teaches you how to verify that your SSH authentication works **before** you try cloning or pushing code.

---

# Learning Objectives

By the end of this lesson, you'll know how to:

- Test GitHub SSH authentication
- Understand the output
- Handle the first connection prompt
- Fix common authentication problems
- Verify which SSH key GitHub is using

---

# The Test Command

Run:

```bash
ssh -T git@github.com
```

Let's understand every part.

|Part|Meaning|
|---|---|
|`ssh`|Start an SSH connection|
|`-T`|Don't allocate an interactive terminal|
|`git`|GitHub's SSH user (always `git`)|
|`github.com`|GitHub's SSH server|

Notice:

You **never** replace `git` with your GitHub username.

❌ Wrong:

```bash
ssh rahul@github.com
```

✅ Correct:

```bash
ssh -T git@github.com
```

---

# Why `git`?

GitHub isn't giving you a Linux shell.

Instead, GitHub runs a service that accepts Git operations like:

- Clone
- Push
- Pull
- Fetch

There is no shell for you to log into.

That's why `-T` is used.

---

# First Connection

The first time you connect, SSH doesn't know GitHub yet.

You'll probably see:

```
The authenticity of host 'github.com' can't be established.
ED25519 key fingerprint is SHA256:xxxxxxxx...
Are you sure you want to continue connecting (yes/no/[fingerprint])?
```

This is completely normal.

---

# Why This Happens

Remember the file:

```
~/.ssh/known_hosts
```

SSH stores trusted server fingerprints here.

Since GitHub isn't in the file yet:

SSH asks:

> "Do you trust this server?"

---

# Accepting the Host Key

Type:

```
yes
```

SSH will reply:

```
Warning: Permanently added 'github.com' (ED25519) to the list of known hosts.
```

Now GitHub is remembered.

You won't be asked again unless GitHub's host key changes or you remove the entry.

---

# Successful Authentication

If everything is configured correctly, you'll see something like:

```
Hi YOUR_USERNAME! You've successfully authenticated, but GitHub does not provide shell access.
```

This message is **exactly what you want**.

It tells you:

- SSH works
- GitHub recognized your key
- Authentication succeeded

---

# Why "No Shell Access"?

GitHub isn't a Linux server you can log into.

If you try:

```bash
ssh -T git@github.com
```

GitHub authenticates you, then immediately disconnects after displaying the success message.

This is expected behavior.

---

# Authentication vs Authorization

These are different concepts.

### Authentication

"Who are you?"

SSH proves your identity using your key.

---

### Authorization

"What are you allowed to do?"

Example:

You authenticate successfully.

Then you try:

```bash
git clone git@github.com:someone/private-repo.git
```

GitHub may respond:

```
ERROR: Repository not found.
```

Authentication succeeded.

Authorization failed because you don't have permission to access that repository.

---

# How SSH Chooses a Key

SSH usually tries:

```
~/.ssh/id_ed25519
```

If it exists, it'll offer that key first.

If you have multiple keys, SSH may try several.

Later we'll configure:

```
~/.ssh/config
```

to control exactly which key GitHub should use.

---

# Debugging Authentication

If something doesn't work, use verbose mode:

```bash
ssh -vT git@github.com
```

For even more detail:

```bash
ssh -vvT git@github.com
```

Or maximum debugging:

```bash
ssh -vvvT git@github.com
```

---

# Reading the Debug Output

Example:

```
Offering public key:
/home/rahul/.ssh/id_ed25519
```

This tells you:

SSH found your private key.

Later:

```
Server accepts key
```

Perfect!

Authentication is working.

---

# Common Error 1

```
Permission denied (publickey).
```

Meaning:

GitHub didn't accept any offered key.

Possible causes:

- Public key not added to GitHub
- Wrong GitHub account
- Wrong SSH key
- Incorrect permissions
- SSH agent doesn't have the key loaded (if you're relying on it)

---

# Common Error 2

```
Host key verification failed.
```

Meaning:

The stored fingerprint doesn't match GitHub's current host key.

Possible fix:

```bash
ssh-keygen -R github.com
```

Then reconnect.

---

# Common Error 3

```
Could not resolve hostname github.com
```

Meaning:

DNS isn't working.

Check:

```bash
ping github.com
```

Or:

```bash
nslookup github.com
```

---

# Which Key Is Being Used?

You can ask SSH:

```bash
ssh -G github.com
```

Useful output:

```
identityfile ~/.ssh/id_ed25519
```

This shows which identity file SSH plans to use.

---

# Real Backend Example

You're deploying code.

You SSH into your VPS:

```bash
ssh production
```

Inside the server:

```bash
git pull
```

If GitHub authentication fails:

The deployment stops immediately.

That's why testing:

```bash
ssh -T git@github.com
```

before your first deployment can save time and frustration.

# Key Takeaways

- Test GitHub SSH with:

```bash
ssh -T git@github.com
```

- The first connection asks you to trust GitHub's host key.
- "You've successfully authenticated" means your SSH setup is correct.
- GitHub intentionally does **not** provide shell access.
- Authentication (who you are) is different from authorization (what you can access).
