# Module 4 — Lesson 10: Incremental Backups

One of the most important jobs of a Linux administrator or backend developer is **making reliable backups**.

Imagine these situations:

- You accidentally delete your project.
- Your SSD fails.
- A deployment breaks production.
- Your database becomes corrupted.
- A ransomware attack encrypts files.

Without backups, recovery may be impossible.

With a good backup strategy, recovery can take just minutes.

---

By the end of this lesson, you'll be able to:

- Understand incremental backups

- Create snapshot-style backups
- Use hard links to save disk space

- Verify backup integrity
- Follow the 3-2-1 backup strategy

# What is a Backup?

A backup is simply:

> A copy of important data stored separately from the original.

Example:

```
Laptop
│
├── project/
├── photos/
└── database.sql
```

Backup:

```
External Drive
│
├── project/
├── photos/
└── database.sql
```

If the laptop fails, the backup remains.

---

# Types of Backups

There are three common types.

## 1. Full Backup

Copies everything.

```
Project

1000 files
```

Every backup copies all 1000 files.

Advantages:

- Easy to restore
- Simple

Disadvantages:

- Slow
- Uses more storage

---

## 2. Incremental Backup ⭐

Copies **only new or changed files** since the last backup.

Day 1:

```
1000 files
```

Day 2:

```
Changed:

app.js
```

Backup:

```
1 file
```

Advantages:

- Very fast
- Saves disk space

This is why `rsync` is so powerful.

---

## 3. Differential Backup

Copies every file changed since the last **full** backup.

It's a compromise between full and incremental backups.

---

# Why `rsync` is Perfect

Suppose your project:

```
my-app/

500 MB
```

Yesterday:

```
500 MB
```

Today:

Only:

```
server.js
```

changed.

Using:

```bash
rsync -av project/ backup/
```

Only:

```
server.js
```

is copied.

Very efficient.

---

# Creating Your First Backup

Suppose:

```
Documents/
```

Backup:

```bash
rsync -av ~/Documents/ ~/Backups/Documents/
```

Result:

```
Backups/

Documents/
```

---

# Backing Up a Project

```bash
rsync -av ~/Projects/my-app/ ~/Backups/my-app/
```

Only changed files are copied on future runs.

---

# Backup with Progress

```bash
rsync -avh --progress \
~/Projects/ \
~/Backups/
```

Shows:

- Progress
- Human-readable sizes

---

# Delete Removed Files

If you want the backup to exactly match the source:

```bash
rsync -av --delete source/ backup/
```

Example:

Source:

```
A
B
```

Backup:

```
A
B
C
```

After syncing:

```
A
B
```

`C` is removed.

⚠️ Be careful: `--delete` permanently removes files from the backup destination.

---

# Dry Run Before Backup

Always test:

```bash
rsync -av --delete --dry-run \
source/ backup/
```

Nothing changes.

You'll only see what **would** happen.

---

# Excluding Unnecessary Files

Never back up:

- `node_modules`
- `.git`
- build caches
- temporary files

Example:

```bash
rsync -av \
--exclude=node_modules \
--exclude=.git \
project/ backup/
```

---

# Timestamped Backups

Instead of overwriting the previous backup:

```
Backups/

2026-07-29/

2026-07-30/

2026-07-31/
```

Create folders using the current date:

```bash
mkdir -p ~/Backups/$(date +%F)
```

Example:

```
Backups/

2026-07-29
```

Backup:

```bash
rsync -av project/ ~/Backups/$(date +%F)/
```

Now each day's backup is stored separately.

---

# Snapshot Backups with Hard Links

Professional Linux systems often create **snapshots**.

Imagine:

```
Day 1

1000 files
```

Day 2:

Only:

```
app.js
```

changed.

Without snapshots:

```
1000 files
```

are copied again.

Huge waste.

---

With hard links:

```
999 files
```

are shared.

Only:

```
app.js
```

takes new disk space.

This saves enormous amounts of storage.

---

# Using `-link-dest`

Example:

```bash
rsync -av \
--link-dest=/backup/latest \
project/ \
/backup/2026-07-29/
```

Meaning:

- Reuse unchanged files from `/backup/latest`
- Copy only changed files
- Create a new snapshot

This is how many backup systems work internally.

---

# Updating the Latest Backup

After a successful backup:

```bash
ln -sfn /backup/2026-07-29 /backup/latest
```

Now:

```
latest
```

always points to the newest snapshot.

---

# Backup Over SSH

Backup to another server:

```bash
rsync -avz \
project/ \
user@backup-server:/backup/project/
```

This combines:

- SSH encryption
- Incremental transfer
- Compression

---

# Backup an Entire Home Directory

```bash
rsync -av \
~/ \
/mnt/backup/home/
```

Usually you'll exclude caches and temporary files:

```bash
rsync -av \
--exclude=.cache \
--exclude=Downloads \
~/ \
/mnt/backup/home/
```

---

# Backup a Database Dump

First create the dump:

```bash
mysqldump mydb > backup.sql
```

Then copy it:

```bash
rsync -av backup.sql ~/DatabaseBackups/
```

> The exact dump command depends on your database (MySQL, PostgreSQL, MongoDB, etc.).

---

# Verify the Backup

Compare directories:

```bash
diff -r source backup
```

No output:

✅ Backup matches the source.

---

Or compare checksums:

```bash
sha256sum source/file.txt
```

```bash
sha256sum backup/file.txt
```

If the hashes match:

✅ Files are identical.

---

# Restore a Backup

Restoring is simply another `rsync`.

```bash
rsync -av \
backup/ \
project/
```

Everything is copied back.

---

# Backup Script

Create:

```bash
nano backup.sh
```

Contents:

```bash
#!/bin/bash

SOURCE="$HOME/Projects/"
DEST="$HOME/Backups/Projects"

rsync -avh \
  --delete \
  --exclude=node_modules \
  "$SOURCE" \
  "$DEST"
```

Make executable:

```bash
chmod +x backup.sh
```

Run:

```bash
./backup.sh
```

# Production Server Backup

```bash
rsync -avz \
/var/www/ \
backup@example.com:/srv/backups/www/
```

This copies website files to a remote backup server.

# The 3-2-1 Backup Rule

This is an industry-standard strategy:

- **3 copies** of your data
- **2 different types of storage**
- **1 copy stored off-site**

Example:

```
Original Laptop
      │
      ├── External SSD
      │
      └── Remote Backup Server
```

If one device fails, your data is still safe.

---

# Common Mistakes

## Forgetting to Test Restores

A backup isn't useful unless you can restore it.

Regularly restore a few files to verify your backups.

---

## Backing Up `node_modules`

Avoid:

```bash
rsync -av project/ backup/
```

Instead:

```bash
rsync -av \
--exclude=node_modules \
project/ backup/
```

You can reinstall dependencies later with:

```bash
npm install
```

or

```bash
npm ci
```

---

## Using `-delete` Carelessly

Always preview:

```bash
rsync -av --delete --dry-run source/ backup/
```

before running the actual command.

---

## Keeping Only One Backup

If today's backup becomes corrupted, yesterday's backup is gone.

Keep multiple dated snapshots whenever practical.

---

# Best Practices

- Use incremental backups for daily work.
- Keep multiple backup versions.
- Store at least one backup on another device or server.
- Exclude generated files such as `node_modules` and caches.
- Test restores regularly.
- Use `-dry-run` before destructive synchronizations.
