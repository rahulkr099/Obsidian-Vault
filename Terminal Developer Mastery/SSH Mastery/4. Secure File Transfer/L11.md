# What is Deployment?

Deployment means:

> Moving your application from your local computer to a server where users can access it.

Example:

```
Laptop
   │
   │
   ▼
Linux Server
   │
   ▼
Internet Users
```

# Typical Deployment Workflow

```
Write Code
    │
    ▼
Commit Changes
    │
    ▼
Test Application
    │
    ▼
Build (if required)
    │
    ▼
Transfer Files
    │
    ▼
Restart Application

    ▼

```

Every production deployment follows roughly this pattern.

---

# Method 1 — Deploy with `rsync`

This is one of the simplest and fastest approaches.

Project:

```
my-api/

server.js
package.json
src/
```

Deploy:

```bash
rsync -avz \
  --delete \
  --exclude=node_modules \
  ./ \
  user@server:/home/user/my-api/
```

This command:

- Transfers only changed files
- Deletes removed files on the server
- Skips `node_modules`
- Uses SSH securely

---

# Install Dependencies on the Server

After uploading:

```bash
ssh user@server
```

Go to the project:

```bash
cd ~/my-api
```

Install packages:

```bash
npm install
```

Or, for production:

```bash
npm ci
```

`npm ci` is preferred when a `package-lock.json` file is present because it installs the exact dependency versions recorded in the lockfile.

---

# Restart the Application

If using PM2:

```bash
pm2 restart my-api
```

Check status:

```bash
pm2 status
```

View logs:

```bash
pm2 logs my-api
```

# Method 2 — Deploy with Git

Many teams deploy by pulling from Git.

Server:

```bash
git clone <https://github.com/user/my-api.git>
```

Later deployments:

```bash
cd my-api

git pull
```

Install dependencies if needed:

```bash
npm ci
```

Restart:

```bash
pm2 restart my-api
```

Advantages:

- Smaller transfers
- Version history
- Easier rollbacks

---

# Method 3 — Docker Deployment

If the application uses Docker:

Build locally:

```bash
docker build -t my-api .
```

Transfer files or push the image to a registry.

On the server:

```bash
docker compose up -d --build
```

Docker rebuilds and restarts the containers.

Deploy:

# Environment Variables

Don't upload:

```
.env
```

Instead:

Keep the server's production `.env` file.

Deploy with:

```bash
rsync -av \
--exclude=.env \
./ \
user@server:/app/
```

This prevents accidentally overwriting production secrets.

# Deployment Script

Create:

```bash
nano deploy.sh
```

Example:

```bash
#!/bin/bash

set -e

echo "Deploying..."

rsync -avz \
  --delete \
  --exclude=node_modules \
  --exclude=.git \
  ./ \
  user@server:/home/user/my-api/

ssh user@server <<'EOF'
cd ~/my-api
npm ci
pm2 restart my-api
EOF

echo "Deployment complete."
```

Make executable:

```bash
chmod +x deploy.sh
```

Run:

```bash
./deploy.sh
```

Now one command performs the deployment.

# Rollback Strategy

Suppose a deployment fails.

Current release:

```
release-2
```

Previous release:

```
release-1
```

Switch back:

```
current -> release-1
```

Restart:

```bash
pm2 restart my-api
```

Users are now served the previous version.

---

# Simple Release Layout

Many production servers use a structure like:

```
/var/www/my-app/

releases/
├── 20260729-1200/
├── 20260730-1015/
└── 20260731-0910/

current -> 20260731-0910
```

Deployment steps:

1. Upload a new release directory.
2. Verify it.
3. Point `current` to the new release.
4. Restart or reload the application.

This keeps older releases available for rollback.

---

# Zero-Downtime Concept

Without careful deployment:

```
Restart Server
     │
     ▼
Users see errors
```

With a better deployment process:

```
Upload New Version
       │
       ▼
Verify
       │
       ▼
Switch Traffic
```

Users experience little or no interruption.

Tools commonly used for this include:

- PM2 reload (for Node.js cluster mode)
- Reverse proxies such as Nginx
- Load balancers
- Container orchestration platforms

# Common Deployment Mistakes

## Uploading `node_modules`

Avoid:

```bash
rsync -av project/ server:/project/
```

Instead:

```bash
rsync -av \
--exclude=node_modules \
project/ server:/project/
```

Install dependencies on the server.

---

## Overwriting `.env`

Don't:

```bash
rsync -av ./
```

Do:

```bash
rsync -av \
--exclude=.env \
./
```

Keep production secrets on the server.

---

## Restarting Before Upload Finishes

Always:

```
Upload

↓

Verify

↓

Restart
```

Restarting too early may leave the application in an incomplete state.

---

## Skipping Verification

Always test after deployment:

```bash
curl <http://server-ip:3000/health>
```

Check logs:

```bash
pm2 logs
```

---

# Best Practices

- Use `rsync` for efficient file transfers.
- Exclude `node_modules`, `.git`, and `.env` during deployments.
- Use `npm ci` in production when a lockfile is available.
- Automate repetitive deployment steps with a shell script.
- Keep previous releases for quick rollbacks.
- Verify the deployment before considering it complete.
