# Module 4 — Lesson 13: Security Best Practices for File Transfers

So far, you've learned **how** to transfer files.

Now it's time to learn **how to do it securely**.

Many real-world server compromises happen because of weak SSH configurations, exposed private keys, or careless deployment practices—not because of flaws in `scp` or `rsync`.

This lesson focuses on practical security measures used by Linux administrators and DevOps engineers.

---

# Learning Objectives

By the end of this lesson, you'll be able to:

- Secure SSH authentication
- Protect SSH keys
- Disable insecure login methods
- Use the principle of least privilege
- Secure file transfers with `scp`, `sftp`, and `rsync`
- Verify server identity
- Protect secrets during deployments
- Build a secure deployment workflow

---

# Security Starts with SSH

Remember:

```
scp
sftp
rsync
```

all use **SSH** for secure communication.

If SSH is secure, your file transfers inherit that security.

---

# Password vs SSH Keys

## Password Authentication

```
Laptop
   │
Password
   │
   ▼
Server
```

Problems:

- Weak passwords
- Password reuse
- Brute-force attacks
- Phishing

---

## SSH Key Authentication

```
Laptop
   │
Private Key
   │
   ▼
Server
```

Advantages:

- Much stronger authentication
- No password sent over the network
- Resistant to brute-force guessing
- Easier to automate securely

For production servers, SSH keys are the preferred approach.

---

# Protect Your Private Key

Example:

```
~/.ssh/

id_ed25519
```

This is your **private key**.

Never:

- Upload it
- Email it
- Commit it to Git
- Share it with anyone

Treat it like the key to your house.

---

# File Permissions for SSH Keys

Correct:

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519
chmod 600 ~/.ssh/authorized_keys
```

Check:

```bash
ls -la ~/.ssh
```

Example:

```
drwx------ .ssh
-rw------- id_ed25519
-rw------- authorized_keys
```

---

# Use a Passphrase

When creating a key:

```bash
ssh-keygen -t ed25519
```

You'll be asked:

```
Enter passphrase:
```

A passphrase encrypts your private key on disk.

Even if someone steals the file, they still need the passphrase to use it.

---

# Use `ssh-agent`

Instead of typing the passphrase repeatedly:

Start the agent:

```bash
eval "$(ssh-agent -s)"
```

Add the key:

```bash
ssh-add ~/.ssh/id_ed25519
```

Now SSH, `scp`, `sftp`, and `rsync` can use the key without prompting for the passphrase during the session.

---

# Disable Password Authentication (Production)

On production servers, many administrators disable password logins after confirming SSH keys work.

SSH configuration:

```
/etc/ssh/sshd_config
```

Example:

```
PasswordAuthentication no
PubkeyAuthentication yes
```

After changing SSH settings:

```bash
sudo systemctl restart ssh
```

> **Important:** Test key-based login in a **new terminal** before closing your current SSH session. Otherwise, you could lock yourself out.

---

# Disable Root Login

Avoid logging in directly as:

```
root
```

Instead:

```
rahul
```

Then:

```bash
sudo command
```

SSH configuration:

```
PermitRootLogin no
```

Benefits:

- Better accountability
- Smaller attack surface
- Reduced risk from brute-force attacks

---

# Verify the Server Fingerprint

The first time you connect:

```bash
ssh user@server
```

You'll see:

```
The authenticity of host can't be established.

ED25519 key fingerprint is:

SHA256:xxxxxxxxxxxx
```

Verify this fingerprint using a trusted source (for example, your cloud provider's console or your own server documentation) before accepting it.

If it matches:

```
yes
```

SSH stores it in:

```
~/.ssh/known_hosts
```

---

# If the Fingerprint Changes

You'll see:

```
WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!
```

Possible reasons:

- Server reinstalled
- SSH keys regenerated
- IP address now points to another machine
- Potential man-in-the-middle attack

Never ignore this warning. Investigate before proceeding.

---

# Use Strong SSH Algorithms

Modern systems generally default to strong algorithms.

Generate a modern key:

```bash
ssh-keygen -t ed25519
```

Avoid creating new DSA keys, which are obsolete.

---

# Secure `rsync`

Instead of:

```bash
rsync source/ destination/
```

Use SSH:

```bash
rsync -avz \
-e ssh \
project/ \
user@server:/project/
```

For a custom port:

```bash
rsync -avz \
-e "ssh -p 2222" \
project/ \
user@server:/project/
```

---

# Never Upload Secrets

Do **not** upload:

```
.env
```

Contains:

```
Database password

API keys

JWT secrets
```

Deploy:

```bash
rsync -av \
--exclude=.env \
./ \
user@server:/app/
```

Keep production secrets on the server.

---

# Protect Backup Files

Suppose:

```
backup.sql
```

Contains:

- Users
- Password hashes
- Customer data

Never leave backups in publicly accessible directories.

Store them in restricted locations with appropriate permissions.

Example:

```bash
chmod 600 backup.sql
```

Only the owner can read and write the file.

---

# Secure File Permissions

Avoid:

```bash
chmod 777 app.js
```

This grants everyone full access.

Prefer the minimum permissions required.

Examples:

```bash
chmod 644 app.js
```

```bash
chmod 755 deploy.sh
```

Follow the **principle of least privilege**.

---

# Use a Dedicated Deployment User

Instead of:

```
root
```

Create a deployment account, for example:

```
deploy
```

Workflow:

```
Laptop
   │
SSH
   │
deploy
   │
Application Directory
```

Benefits:

- Better isolation
- Easier auditing
- Lower risk

---

# Verify File Integrity

After transferring an important file:

Source:

```bash
sha256sum app.tar.gz
```

Destination:

```bash
sha256sum app.tar.gz
```

If the hashes match:

```
Same SHA-256 hash
```

The file contents match exactly.

---

# Use Dry Runs Before Deleting

Never run:

```bash
rsync --delete
```

blindly.

Preview:

```bash
rsync -av \
--delete \
--dry-run \
source/ \
destination/
```

Review the planned changes first.

---

# Protect Your Git Repository

Never commit:

```
.env

id_ed25519

backup.sql
```

Use:

```
.gitignore
```

Example:

```
.env
node_modules/
*.sql
*.pem
*.key
```

This helps prevent accidental commits of sensitive files.

---

# Example Secure Deployment

Synchronize:

```bash
rsync -avz \
--delete \
--exclude=.env \
--exclude=node_modules \
./ \
deploy@server:/var/www/my-app/
```

Connect:

```bash
ssh deploy@server
```

Restart:

```bash
cd /var/www/my-app

npm ci

pm2 restart my-app
```

No secrets are transferred.

---

# Principle of Least Privilege

Only grant the permissions required.

Instead of:

```
Everyone
```

Grant access only to:

```
Application User
```

This reduces the impact of mistakes or compromised accounts.

---

# Security Checklist

Before deploying:

- ✅ Use SSH keys
- ✅ Protect private keys
- ✅ Use a passphrase
- ✅ Keep `.env` on the server
- ✅ Exclude secrets from `rsync`
- ✅ Verify the host fingerprint
- ✅ Avoid direct root login
- ✅ Review `-delete` with `-dry-run`
- ✅ Restrict file permissions
- ✅ Keep backups protected

# Common Security Mistakes

## Uploading `.env`

❌

```bash
rsync -av ./
```

✔

```bash
rsync -av \
--exclude=.env \
./
```

---

## Committing SSH Keys

Never:

```
git add ~/.ssh/id_ed25519
```

A leaked private key should be considered compromised and replaced immediately.

---

## Using `chmod 777`

Avoid:

```bash
chmod 777 app.js
```

Instead, assign only the permissions that are actually needed.

---

## Using Root for Everything

Prefer:

```
deploy
```

instead of:

```
root
```

Use `sudo` only when required.

---

## Ignoring SSH Warnings

If SSH warns:

```
REMOTE HOST IDENTIFICATION HAS CHANGED
```

Don't bypass the warning. Verify the cause before reconnecting.

---

# Best Practices

- Use SSH keys with passphrases.
- Protect private keys with correct file permissions.
- Disable password authentication only after verifying key-based login works.
- Disable direct root login on production systems.
- Exclude secrets and unnecessary files from deployments.
- Keep backups encrypted or access-restricted.
- Verify server fingerprints before trusting a new host.
- Apply the principle of least privilege.
