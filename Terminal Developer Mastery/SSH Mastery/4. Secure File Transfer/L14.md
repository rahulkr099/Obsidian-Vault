# What Does a DevOps Workflow Look Like?

A typical production deployment isn't just:

```
scp project server
```

Instead, it looks like:

```
Write Code
      │
      ▼
Commit Code
      │
      ▼
Push to GitHub
      │
      ▼
Run Tests
      │
      ▼
Build Application
      │
      ▼
Backup Current Version
      │
      ▼
Deploy New Version
      │
      ▼
Restart Application
      │
      ▼
Health Check
      │
      ▼
Users
```

Every step reduces risk.

# Example 1 — Small Startup Deployment

Imagine you're the only backend developer.

Workflow:

```
Laptop
   │
   ▼
rsync
   │
   ▼
Linux VPS
   │
   ▼
npm ci
   │
   ▼
pm2 restart
```

Commands:

```bash
rsync -avz \
  --delete \
  --exclude=node_modules \
  --exclude=.env \
  ./ deploy@server:/home/deploy/my-api/
```

SSH into the server:

```bash
ssh deploy@server
```

Update dependencies:

```bash
cd ~/my-api

npm ci
```

Restart:

```bash
pm2 restart my-api
```

Verify:

```bash
curl <http://localhost:3000/health>
```

# CI/CD Basics

CI = **Continuous Integration**

Every code change:

```
Push Code

↓

Run Tests

↓

Run Linter

↓

Build Project
```

Problems are caught early.

---

CD = **Continuous Delivery / Deployment**

After CI succeeds:

```
Deploy

↓

Restart

↓

Health Check

↓

Production
```

The application reaches users faster and more consistently.

# Example Deployment Script

`deploy.sh`

```bash
#!/bin/bash

set -e

echo "Starting deployment..."

rsync -avz \
  --delete \
  --exclude=node_modules \
  --exclude=.env \
  ./ deploy@server:/home/deploy/my-api/

ssh deploy@server <<'EOF'
cd ~/my-api

npm ci

pm2 restart my-api

curl <http://localhost:3000/health>
EOF

echo "Deployment successful."
```

Run:

```bash
./deploy.sh
```

# Backup Before Deployment

Professional teams back up before making changes.

```
Current Release

↓

Backup

↓

Deploy

↓

Verify
```

Example:

```bash
rsync -av \
/var/www/my-api/ \
~/backups/my-api-$(date +%F-%H%M)/
```

If deployment fails:

Restore:

```bash
rsync -av \
~/backups/latest/ \
/var/www/my-api/
```

# Release-Based Deployment

Instead of replacing files directly:

```
/var/www/my-api/

releases/

20260729/

20260730/

20260731/

current ->
```

Upload:

```
releases/

20260801/
```

When verified:

```
current -> 20260801
```

Restart PM2.

Users immediately use the new release.

---

# Rollback

Suppose:

Release:

```
20260801
```

has a bug.

Switch:

```
current -> 20260731
```

Restart:

```bash
pm2 restart my-api
```

Rollback complete in seconds.

# Blue-Green Deployment

A common production strategy.

Before deployment:

```
Blue

Running
```

Deploy to:

```
Green

Idle
```

Diagram:

```
Users
   │
   ▼
Blue (Live)

Green (New Version)
```

Deploy to Green.

Test Green.

If everything works:

```
Users
   │
   ▼
Green
```

Blue remains available for rollback.

Advantages:

- Minimal downtime
- Safer deployments
- Easy rollback

# Rolling Deployment

Suppose you have:

```
Server 1

Server 2

Server 3
```

Don't restart all at once.

Instead:

```
Restart

Server 1

↓

Verify

↓

Restart

Server 2

↓

Verify

↓

Restart

Server 3
```

Users continue to receive service from the remaining servers.

```bash
rsync project/ app3:/app/
```

Restart each server after updating it.

# Common Deployment Mistakes

## Skipping Tests

Deploying untested code increases the chance of production failures.

---

## No Backup

Without a backup, rollback may be much harder.

---

## Restarting Too Early

Always:

```
Upload

↓

Verify Files

↓

Restart
```

---

## Not Monitoring After Deployment

A deployment can succeed technically but still introduce runtime problems.

Always monitor after releasing.

---

## Editing Production Directly

Avoid changing files manually on the production server.

Treat your local repository as the source of truth and deploy from version-controlled code.

---

# Best Practices

- Automate repetitive deployment steps.
- Back up before every production deployment.
- Use release directories for quick rollbacks.
- Verify health after restarting services.
- Monitor application logs and system resources.
- Avoid manual edits on production servers.
- Test deployments in a staging environment when possible.
