# Module 5 — Advanced SSH

# Lesson 14: SSH Security Hardening — Production-Grade SSH Security

Knowing how to use SSH is only half the job.

The other half is **securing SSH**.

A poorly configured SSH server is one of the most common entry points for attackers. Production systems therefore follow a set of hardening practices to reduce risk.

In this lesson, you'll learn how Linux system administrators and DevOps engineers secure SSH servers in production.

---

# Learning Objectives

By the end of this lesson, you'll be able to:

- Harden `sshd_config`
- Disable insecure authentication
- Restrict SSH access
- Protect against brute-force attacks
- Configure modern cryptography
- Monitor SSH activity
- Rotate SSH keys
- Audit SSH access
- Build a production-ready SSH configuration

# SSH Configuration File

The SSH server configuration is typically located at:

```
/etc/ssh/sshd_config
```

Always make a backup before editing:

```bash
sudo cp /etc/ssh/sshd_config /etc/ssh/sshd_config.backup
```

---

# Test Before Restarting

After making changes:

```bash
sudo sshd -t
```

If no output appears, the configuration syntax is valid.

Only then restart:

```bash
sudo systemctl restart ssh
```

On some distributions, the service name is `sshd`:

```bash
sudo systemctl restart sshd
```

---

# Disable Root Login

Avoid:

```bash
ssh root@server
```

Configure:

```
PermitRootLogin no
```

Instead:

```bash
ssh rahul@server
sudo ...
```

Benefits:

- Better accountability
- Audit trails
- Reduced attack surface

---

# Disable Password Authentication

Instead of:

```
Username

+

Password
```

Use:

```
SSH Key
```

Configuration:

```
PasswordAuthentication no
PubkeyAuthentication yes
```

Always verify key-based login works before disabling passwords.

---

# Limit Which Users Can Log In

Instead of allowing every local account:

```
100 Users
```

Allow only specific users:

```
AllowUsers rahul deploy
```

Or allow a group:

```
AllowGroups sshusers
```

This reduces the number of accounts that can attempt SSH login.

---

# Change the Default Port?

Example:

```
Port 2222
```

instead of:

```
Port 22
```

Changing the port may reduce automated scanning noise, but **it is not a security control by itself**. Strong authentication, firewalls, and updates are far more important.

If you do change the port, remember to update:

- Firewall rules
- Security groups
- SSH client configuration

---

# Disable Empty Passwords

Ensure:

```
PermitEmptyPasswords no
```

This should remain disabled on production systems.

---

# Limit Authentication Attempts

Prevent repeated guessing:

```
MaxAuthTries 3
```

Users get three attempts before the connection closes.

---

# Disconnect Idle Sessions

Example:

```
ClientAliveInterval 300
ClientAliveCountMax 2
```

Meaning:

- Check every 300 seconds (5 minutes)
- Disconnect after two unanswered checks

This helps clean up abandoned sessions.

---

# Restrict Port Forwarding (When Appropriate)

If a server should not be used as a tunnel endpoint:

```
AllowTcpForwarding no
```

Similarly, you can disable X11 forwarding if unused:

```
X11Forwarding no
```

Only disable features you know are unnecessary.

---

# Restrict Agent Forwarding

If users don't need it:

```
AllowAgentForwarding no
```

This reduces the attack surface on systems where agent forwarding isn't required.

---

# Restrict TTY Access

For automation-only accounts:

```
PermitTTY no
```

Useful for service accounts that should never receive an interactive shell.

---

# Use Modern SSH Keys

Prefer:

```
Ed25519
```

Good alternative:

```
RSA (3072+ bits)
```

Avoid generating new:

```
DSA
```

keys, as they are obsolete and unsupported by modern OpenSSH.

Generate a modern key:

```bash
ssh-keygen -t ed25519
```

---

# Key Rotation

Don't keep the same SSH key forever.

Example process:

```
Old Key

↓

Generate New Key

↓

Install New Public Key

↓

Test

↓

Remove Old Key
```

Rotate keys periodically and immediately if a key may have been compromised.

---

# SSH Banner

Display a legal notice before login:

```
Banner /etc/issue.net
```

Example:

```
Authorized users only.
All activity may be monitored.
```

This is common in enterprise environments.

---

# Logging

View recent SSH logs:

Ubuntu/Debian:

```bash
sudo journalctl -u ssh
```

or:

```bash
sudo tail -f /var/log/auth.log
```

RHEL/CentOS:

```bash
sudo tail -f /var/log/secure
```

Watch for:

- Failed logins
- Successful logins
- Unusual login times
- Unexpected IP addresses

---

# Fail2Ban

Repeated failures:

```
Bot

↓

Wrong Password

↓

Wrong Password

↓

Wrong Password

↓

Blocked
```

Install (Ubuntu/Debian):

```bash
sudo apt install fail2ban
```

Enable:

```bash
sudo systemctl enable --now fail2ban
```

Check status:

```bash
sudo fail2ban-client status sshd
```

---

# Firewall

Allow SSH only where needed.

With UFW:

```bash
sudo ufw allow 22/tcp
```

Better:

```bash
sudo ufw allow from 203.0.113.25 to any port 22
```

Cloud firewalls (AWS Security Groups, Azure NSGs, GCP Firewall Rules) should also restrict access.

---

# Keep Software Updated

Regularly update OpenSSH and the operating system:

```bash
sudo apt update
sudo apt upgrade
```

Security patches are essential.

---

# File Permissions

Protect SSH files:

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
chmod 600 ~/.ssh/config
```

Private keys should never be world-readable.

---

# Monitor Active Sessions

Current users:

```bash
who
```

Detailed sessions:

```bash
w
```

SSH connections:

```bash
ss -tnp | grep ssh
```

---

# Real Production `sshd_config`

Example:

```
PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
PermitEmptyPasswords no
AllowUsers deploy admin
MaxAuthTries 3
ClientAliveInterval 300
ClientAliveCountMax 2
X11Forwarding no
AllowAgentForwarding no
```

Adjust these settings according to your organization's needs.

---

# Common Mistakes

## Locking Yourself Out

Changing:

```
PasswordAuthentication no
```

before confirming SSH keys work can prevent all logins.

Always keep one active SSH session open while testing.

---

## Editing Without Validation

Always run:

```bash
sudo sshd -t
```

before restarting the service.

---

## Weak Keys

Avoid creating new weak or obsolete keys.

Use:

```bash
ssh-keygen -t ed25519
```

---

## Shared Accounts

Avoid:

```
deploy
```

used by everyone.

Prefer:

```
rahul
alice
bob
```

with `sudo` privileges as appropriate.

# Interview Questions

### 1. Why disable root login?

It forces administrators to authenticate with individual accounts, improving accountability and reducing the attack surface.

---

### 2. Why are SSH keys preferred over passwords?

SSH keys are significantly more resistant to brute-force attacks and credential guessing than passwords.

---

### 3. What does `AllowUsers` do?

It restricts SSH access to only the specified user accounts.

---

### 4. Why should you run `sshd -t`?

It validates the SSH server configuration before restarting the service, helping prevent accidental lockouts caused by syntax errors.

---

### 5. Is changing the SSH port sufficient to secure a server?

No. It may reduce automated scans, but it is **not** a replacement for strong authentication, proper firewall rules, software updates, and monitoring.
