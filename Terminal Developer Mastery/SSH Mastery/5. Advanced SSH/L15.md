# Project Scenario

Imagine you work at a startup.

The infrastructure looks like this:

```
                    Internet
                        │
                        ▼
                Bastion Host
             (Public IP: 203.0.113.10)
                        │
        ───────── Private Network ─────────
        │                 │               │
        ▼                 ▼               ▼
   API Server       Database Server    Redis Server
   10.0.1.10        10.0.1.20          10.0.1.30
```

Only the **Bastion Host** has a public IP.

Everything else is private.

# Step 1 — Professional SSH Config

Create:

```
Host *
    ServerAliveInterval 60
    ServerAliveCountMax 3
    ControlMaster auto
    ControlPath ~/.ssh/cm/%C
    ControlPersist 15m

Host bastion
    HostName 203.0.113.10
    User deploy
    IdentityFile ~/.ssh/id_work

Host api
    HostName 10.0.1.10
    User deploy
    ProxyJump bastion

Host database
    HostName 10.0.1.20
    User deploy
    ProxyJump bastion

Host redis
    HostName 10.0.1.30
    User deploy
    ProxyJump bastion
```

Now you can type:

```bash
ssh api
```

instead of:

```bash
ssh -J deploy@203.0.113.10 deploy@10.0.1.10
```

# Step 2 — Start the SSH Agent

```bash
eval "$(ssh-agent -s)"
```

Load your key:

```bash
ssh-add ~/.ssh/id_work
```

Verify:

```bash

```

# Step 4 — Enable SSH Multiplexing

Open:

```bash
ssh api
```

Then in another terminal:

```bash
ssh api
```

Notice the second connection opens almost instantly.

Verify:

```bash
ssh -O check api
```

# Step 5 — Create a Database Tunnel

Forward PostgreSQL:

```bash
ssh \
-L 5432:localhost:5432 \
database
```

Now your laptop has:

```
localhost:5432
```

Connect:

```bash
psql \
-h localhost \
-p 5432
```

Or connect using:

- pgAdmin
- DBeaver
- TablePlus

---

# Step 6 — Multiple Tunnels

One connection:

```bash
ssh \
-L 5432:localhost:5432 \
-L 6379:localhost:6379 \
api
```

Now access:

```
PostgreSQL

↓

localhost:5432
```

```
Redis

↓

localhost:6379
```

# Step 7 — Deploy Using `rsync`

Suppose your project:

```
backend/

controllers/
routes/
models/
package.json
```

Deploy:

```bash
rsync \
-avz \
--delete \
--exclude node_modules \
./backend/ \
api:/var/www/backend/
```

SSH handles authentication automatically.

---

# Step 8 — Restart the Application

Connect:

```bash
ssh api
```

Restart:

```bash
pm2 restart backend
```

Verify:

```bash
pm2 status
```

---

# Step 9 — Browse Logs

Mount logs:

```bash
mkdir -p ~/logs

sshfs api:/var/log ~/logs
```

Now:

```bash
cd ~/logs
```

View:

```bash
tail -f nginx/access.log
```

Or:

```bash
less syslog
```

Unmount:

```bash
fusermount3 -u ~/logs
```

---

# Step 10 — Emergency Production Fix

Mount the application:

```bash
mkdir -p ~/production

sshfs api:/var/www/backend ~/production
```

Open:

```bash
cd ~/production
nvim server.js
```

Fix the issue.

Save.

Restart:

```bash
ssh api
pm2 restart backend
```

Unmount:

```bash
fusermount3 -u ~/production
```

> **Note:** Direct production edits should be reserved for emergencies. Normal changes should go through Git, code review, CI/CD, and automated deployments.

Check:

```bash

```

View active users:

```bash

```

Current sessions:

```bash

```

SSH sockets:

```bash
ss -tnp | grep ssh
```

# Step 12 — Close Everything

Stop multiplexed connection:

```bash
ssh -O exit api
```

Kill SSH agent:

```bash
ssh-agent -k
```

Unmount:

```bash
fusermount3 -u ~/logs
```

# Troubleshooting Checklist

## SSH fails

```bash
ssh -v api
```

---

## Tunnel not working

```bash
ss -ltn
```

---

## Key missing

```bash
ssh-add -l
```

---

## Config problem

```bash
ssh -G api
```

---

## Service not responding

```bash
systemctl status ssh
```

or

```bash
systemctl status sshd
```

(depending on your Linux distribution)

---

## rsync problem

```bash
rsync \
-av \
--dry-run \
backend/ \
api:/var/www/backend/
```

# Interview Scenario

**Question:**

> "How would you securely deploy a Node.js application to a private production server?"

A strong answer would include:

1. Use SSH keys for authentication.
2. Access the private server through a bastion host (`ProxyJump`).
3. Use `~/.ssh/config` for reusable aliases.
4. Enable SSH multiplexing for faster repeated connections.
5. Deploy with `rsync` using `-dry-run` first.
6. Restart the application (e.g., with PM2 or systemd).
7. Verify the deployment with logs and health checks.
8. Avoid direct production edits except for emergencies.
