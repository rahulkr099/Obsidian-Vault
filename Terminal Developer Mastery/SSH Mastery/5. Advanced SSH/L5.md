# Module 5 — Advanced SSH

# Lesson 5: Remote Port Forwarding (`ssh -R`) — Reverse SSH Tunnels

In the previous lesson, you learned **Local Port Forwarding (`ssh -L`)**:

> **Local → Remote**

Now you'll learn the opposite:

> **Remote → Local**

This is called **Remote Port Forwarding** or a **Reverse SSH Tunnel**.

It allows a service running on **your local machine** to be accessed **through a remote server**.

This technique is widely used for:

- Remote debugging
- Sharing local development servers
- Accessing machines behind NAT/firewalls
- Temporary demos
- IoT devices
- Secure remote support

---

# Local vs Remote Port Forwarding

## Local Port Forwarding (`L`)

```
Laptop
   │
localhost:5432
   │
SSH Tunnel
   │
Remote PostgreSQL
```

Your laptop connects to a remote service.

---

## Remote Port Forwarding (`R`)

```
Local Web Server
      │
SSH Tunnel
      │
Remote Server
      │
Port 8080
```

The remote server connects back to your local service.

---

# The Problem

Suppose you're developing a website:

```
Laptop

localhost:3000
```

A teammate wants to see it.

Problem:

- Your laptop is behind NAT.
- No public IP.
- Router blocks incoming connections.

Without opening firewall ports, how do you share it?

Use a reverse SSH tunnel.

---

# Basic Syntax

```bash
ssh -R REMOTE_PORT:LOCAL_HOST:LOCAL_PORT user@server
```

General format:

```
ssh -R remote_port:local_host:local_port user@remote_server
```

---

# Example 1 — Share a Local Website

Your laptop:

```
localhost:3000
```

Run:

```bash
ssh -R 8080:localhost:3000 user@server
```

Meaning:

```
Remote Server

localhost:8080

↓

SSH Tunnel

↓

Laptop

localhost:3000
```

Anyone with access to the remote server can now access your local web application through port **8080** (subject to the server's SSH and networking configuration).

---

# Understanding the Flow

Without a tunnel:

```
Internet

↓

Laptop

❌ Not reachable
```

With a reverse tunnel:

```
Browser

↓

Remote Server:8080

↓

SSH Tunnel

↓

Laptop:3000
```

The remote server forwards requests back to your laptop.

---

# Demo with Python

On your laptop:

```bash
python3 -m http.server 8000
```

Open another terminal:

```bash
ssh -R 8080:localhost:8000 user@server
```

On the server:

```bash
curl <http://localhost:8080>
```

You'll receive the content served by your local Python web server.

# Example 3 — Share an Express API

Express:

```
localhost:3000
```

Tunnel:

```bash
ssh -R 9000:localhost:3000 deploy@server
```

On the server:

```bash
curl <http://localhost:9000/api>
```

The request is forwarded to your laptop.

---

# Using `N`

If you only want the tunnel:

```bash
ssh -N -R 8080:localhost:3000 user@server
```

No interactive shell is started.

---

# Background Mode

Keep the tunnel alive without occupying the terminal:

```bash
ssh -f -N -R 8080:localhost:3000 user@server
```

Options:

- `f` → background
- `N` → no remote shell

---

# Remote Port Already in Use

If:

```
8080
```

is already occupied:

```
bind: Address already in use
```

Choose another port:

```bash
ssh -R 9000:localhost:3000 user@server
```

---

# Forward to Another Local Address

Instead of:

```
localhost
```

you can specify another reachable address on your local network:

```bash
ssh -R 8080:192.168.1.20:3000 user@server
```

The SSH client will forward traffic to that address from your local machine.

---

# Reverse Tunnel Through a Bastion

```
Laptop
     │
SSH Tunnel
     │
Bastion Server
     │
Port 9000
```

Developers can SSH into the bastion host and access your local service through the forwarded port.

---

# SSH Config Example

Instead of typing the full command every time:

```
Host reverse-demo
    HostName server.example.com
    User deploy
    RemoteForward 8080 localhost:3000
```

Now simply run:

```bash
ssh reverse-demo
```

The reverse tunnel is created automatically.

---

# How Reverse Tunnels Work

```
Laptop
─────────────

localhost:3000

↓

Encrypted SSH Tunnel

↓

Remote Server

localhost:8080
```

A request to:

```
server:8080
```

is securely transported to:

```
laptop:3000
```

# Security Considerations

Reverse tunnels expose a local service through a remote machine.

Be careful:

- Only create tunnels to trusted servers.
- Close tunnels when finished.
- Avoid forwarding sensitive services unnecessarily.
- Use strong SSH authentication.

By default, forwarded remote ports are often bound only to the remote machine's loopback interface (`localhost`). Making them accessible from other hosts typically requires SSH server configuration (such as `GatewayPorts`) and should be done only when appropriate.

---

# Common Errors

## Error

```
remote port forwarding failed
```

Possible reasons:

- Remote port already in use.
- The SSH server disallows remote forwarding.

Choose another port or review the server's SSH configuration.

---

## Error

```
Connection refused
```

Verify the local application is actually running:

```bash
ss -ltn
```

Example:

```
LISTEN

127.0.0.1:3000
```

---

## Error

Tunnel created, but nothing loads.

Check:

- Correct local port
- Correct remote port
- Firewall rules
- Application is listening on the expected interface

---

# Best Practices

- Use `N` for tunnel-only sessions.
- Use `f` for long-running background tunnels.
- Use high-numbered ports (for example, above 1024) unless you specifically need a privileged port.
- Close tunnels after use.
- Only expose services to trusted environments.

# Interview Questions

### 1. What does `ssh -R` do?

It creates a **remote port forwarding (reverse SSH) tunnel**, allowing a port on the remote server to forward traffic to a service on your local machine.

---

### 2. What is the difference between `ssh -L` and `ssh -R`?

- `ssh -L`: Local → Remote
- `ssh -R`: Remote → Local

---

### 3. Why would you use a reverse SSH tunnel?

To securely expose a local service to a trusted remote server without opening inbound firewall ports or requiring a public IP.

---

### 4. What does `N` do?

It tells SSH to establish the tunnel without starting a remote shell.

---

### 5. What does `f` do?

It sends SSH to the background after authentication, allowing the tunnel to continue running without occupying the terminal.
