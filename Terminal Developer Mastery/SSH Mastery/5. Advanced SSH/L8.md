# What Is a Bastion Host?

A Bastion Host is a **dedicated SSH gateway** that sits between the public internet and a private network.

It should have **one primary job**:

> Securely broker administrative access to internal systems.

It is **not** intended to run application workloads or databases.

---

# Traditional Architecture

Many beginners deploy servers like this:

```
Internet
     │
 ┌───┴──────────────┐
 │                  │
 ▼                  ▼
Production      Database
(Public IP)     (Public IP)
```

Problems:

- Every server is exposed.
- Larger attack surface.
- More firewall rules.
- Harder auditing.

---

# Production Architecture

Instead:

```
Internet
     │
     ▼
 Bastion Host
(Public IP)
     │
──────────── Private Network ────────────
     │
 ┌───┴─────────────┬─────────────┐
 ▼                 ▼             ▼
API Server     Database      Cache
(No Public IP) (No Public IP) (No Public IP)
```

Only the bastion has a public IP address.

---

# Benefits

## Smaller Attack Surface

Instead of protecting:

```
10 Public Servers
```

You protect:

```
1 Bastion Host
```

---

## Centralized Authentication

Everyone logs in through:

```
Laptop

↓

Bastion

↓

Production
```

This makes access management much simpler.

---

## Easier Auditing

Every SSH session starts from one place.

Example log:

```
09:00 Rahul → Bastion
09:01 Rahul → API Server
09:15 Rahul → Database
```

Security teams have a single location to review.

# Bastion Host Responsibilities

A bastion should typically:

- Accept SSH connections
- Verify authentication
- Log access
- Forward users to internal systems

It should **not** normally:

- Host databases
- Run production applications
- Store sensitive business data
- Serve public websites

Keep it as minimal as possible.

---

# Authentication

Production environments generally use:

```
SSH Keys
```

instead of:

```
Passwords
```

Recommended:

```
Laptop

↓

SSH Key

↓

Bastion

↓

Production
```

Avoid password authentication when possible.

---

# Disable Password Authentication

Example in:

```
/etc/ssh/sshd_config
```

```
PasswordAuthentication no
PubkeyAuthentication yes
PermitRootLogin no
```

After making changes:

```bash
sudo systemctl restart ssh
```

**Important:** Always verify key-based login works before disabling password authentication, or you could lock yourself out.

---

# User Accounts

Instead of sharing one account:

```
deploy
```

Create individual users:

```
rahul
alice
bob
charlie
```

Benefits:

- Accountability
- Easier access revocation
- Better audit logs

---

# Principle of Least Privilege

Users should only access what they need.

Example:

```
Rahul

↓

API Server

✓
```

But:

```
Rahul

↓

Finance Database

✗
```

Restrict access wherever possible.

# Logging

Linux authentication logs are commonly found in:

Ubuntu/Debian:

```
/var/log/auth.log
```

RHEL/CentOS:

```
/var/log/secure
```

Useful command:

```bash
sudo journalctl -u ssh
```

or, on systems using `sshd` as the service name:

```bash
sudo journalctl -u sshd
```

You can review:

- Successful logins
- Failed logins
- Disconnects
- Authentication methods

# Fail2Ban

Repeated failed login attempts:

```
Bot

↓

SSH

↓

Fail
```

After several failures:

```
IP Address

↓

Blocked
```

This is a common use case for **Fail2Ban**.

---

# Firewall

Allow only SSH from trusted sources when possible.

Example with `ufw`:

```bash
sudo ufw allow from 203.0.113.25 to any port 22
```

Or, if you can't restrict by source yet:

```bash
sudo ufw allow 22/tcp
```

Then:

```bash
sudo ufw enable
```

Cloud firewalls (AWS Security Groups, Azure NSGs, GCP Firewall Rules) should also be configured appropriately.

---

# Multi-Factor Authentication (MFA)

Many organizations require:

```
SSH Key

+

One-Time Code
```

This significantly improves security.

Examples include TOTP apps, hardware security keys, or enterprise identity providers.

# SSH Agent Forwarding

Recommended workflow:

```
Laptop

↓

SSH Agent

↓

Bastion

↓

Production
```

Do **not** copy private keys onto the bastion.

Use agent forwarding only for trusted bastion hosts.

---

# ProxyJump

Example:

```
Host bastion
    HostName bastion.company.com
    User deploy

Host api
    HostName 10.0.1.10
    ProxyJump bastion
```

Connect:

```bash
ssh api
```

Simple and secure.

---

# High Availability

A single bastion can become a single point of failure.

Large organizations often deploy:

```
Internet
     │
 Load Balancer
     │
 ┌──────┴──────┐
 ▼             ▼
Bastion 1   Bastion 2
     │
Private Network
```

If one bastion fails, another can continue serving SSH connections.

# Common Mistakes

## ❌ Running Applications on the Bastion

```
Bastion

↓

Node API

↓

Database

↓

Redis
```

Bad idea.

The bastion should remain dedicated to administrative access.

---

## ❌ Copying Private Keys

Never:

```bash
scp ~/.ssh/id_ed25519 server:
```

Use:

- SSH Agent
- Agent Forwarding
- ProxyJump

instead.

---

## ❌ Logging in as Root

Avoid:

```bash
ssh root@server
```

Instead:

```bash
ssh rahul@server
sudo ...
```

This improves accountability.

---

## ❌ Leaving Unused Accounts

Regularly remove or disable accounts for former employees or unused automation.

# Security Checklist

- ✅ Public-key authentication only
- ✅ Disable root login
- ✅ Strong firewall rules
- ✅ Individual user accounts
- ✅ Regular security updates
- ✅ SSH logging enabled
- ✅ Fail2Ban or similar protection
- ✅ MFA where possible
- ✅ No private keys stored on the bastion
- ✅ Restrict access to trusted IPs when feasible

# Interview Questions

### 1. What is the purpose of a bastion host?

A bastion host provides a secure, centralized entry point for accessing systems inside a private network.

---

### 2. Why should production servers not have public IP addresses?

Keeping them private reduces the attack surface and limits direct exposure to the internet.

---

### 3. Why should you avoid logging in as `root`?

Using individual user accounts provides accountability, better auditing, and allows fine-grained privilege management with `sudo`.

---

### 4. Why should private SSH keys never be stored on a bastion?

If the bastion is compromised, attackers could steal those keys. Agent forwarding keeps private keys on the administrator's local machine.

---

### 5. Name three bastion security best practices.

- Disable password authentication.
- Disable direct root login.
- Use individual accounts with SSH keys and maintain comprehensive logging.
