So far you've authenticated using **SSH key pairs**:


# Traditional SSH Authentication

Normal SSH authentication looks like:

```
User

↓

Public Key

↓

authorized_keys

↓

Login Allowed
```

Every server stores every user's public key.

Problems:

- Difficult to manage
- Difficult to revoke
- Difficult to audit
- Doesn't scale well

---

# SSH Certificates

Instead of trusting every user's key individually:

```
Server

↓

Trusts

↓

Certificate Authority (CA)

↓

CA Trusts User

↓

Login Allowed
```

The server only needs to trust **one CA public key**.

---

# What is a Certificate Authority (CA)?

A CA is a trusted entity that signs SSH public keys.

Think of it like a passport office.

Instead of every country recognizing every individual directly:

```
Country

↓

Trusts Passport Authority

↓

Passport

↓

Traveler
```

Similarly:

```
Server

↓

Trusts CA

↓

CA Signs User Certificate

↓

User Logs In
```

---

# SSH Key vs SSH Certificate

|SSH Key|SSH Certificate|
|---|---|
|Generated by user|Generated by user + signed by CA|
|Trusted individually|Trusted through CA|
|Stored in `authorized_keys`|Verified against trusted CA|
|Manual distribution|Centralized management|
|Good for small environments|Excellent for large organizations|

---

# Certificate Components

A certificate includes:

- User's public key
- Identity (principal)
- Validity period
- Serial number
- CA signature
- Optional restrictions

Unlike a normal public key, it has an expiration time and is cryptographically signed.

# User Certificates

Example:

```
Laptop

↓

id_ed25519

↓

CA Signs It

↓

id_ed25519-cert.pub
```

The user authenticates with:

- Private key
- Certificate

# Host Certificates

Host certificates identify servers.

Instead of trusting:

```
Server A

↓

Host Key
```

Clients trust:

```
Company CA

↓

Signs Server Host Key

↓

Server Identity Verified
```

This simplifies management when many servers are added or rebuilt.

---

# Creating a CA

Generate a CA key pair:

```bash
ssh-keygen -t ed25519 -f ssh_ca
```

Files:

```
ssh_ca
ssh_ca.pub
```

These are **not** user login keys.

They belong only to the certificate authority.

> **Protect the CA private key carefully.** Anyone who possesses it can issue trusted certificates.

---

# Generate a User Key

Example:

```bash
ssh-keygen -t ed25519 -f rahul_key
```

Produces:

```
rahul_key
rahul_key.pub
```

---

# Sign the User Key

Use the CA:

```bash
ssh-keygen \
-s ssh_ca \
-I rahul \
-n rahul \
-V +52w \
rahul_key.pub
```

Explanation:

|Option|Meaning|
|---|---|
|`-s ssh_ca`|CA private key|
|`-I rahul`|Certificate identity|
|`-n rahul`|Allowed principal (user)|
|`-V +52w`|Valid for 52 weeks|

Output:

```
rahul_key-cert.pub
```

This is the SSH certificate.

---

# Configure the Server to Trust the CA

Copy the CA public key to the server.

Edit:

```
/etc/ssh/sshd_config
```

Add:

```
TrustedUserCAKeys /etc/ssh/ssh_ca.pub
```

Restart SSH:

Ubuntu/Debian:

```bash
sudo systemctl restart ssh
```

RHEL/CentOS:

```bash
sudo systemctl restart sshd
```

Now the server trusts certificates signed by that CA.


The server doesn't need the user's public key in `authorized_keys`.

# Certificate Validity

Unlike ordinary public keys:

```
id_ed25519.pub
```

Certificates expire.

Example:

```
Valid:

2026-01-01

↓

2026-06-30
```

After expiration:

```
Login Denied
```

This reduces the risk of forgotten credentials remaining valid indefinitely.

---

# Revoking Access

Traditional method:

```
Find

↓

Delete Key

↓

Repeat on Every Server
```

Certificates:

```
Certificate Expires

↓

Issue New Certificate

↓

Done
```

Many organizations also maintain revocation lists for certificates that must be invalidated before they expire.

# Viewing Certificate Information

Inspect a certificate:

```bash
ssh-keygen -Lf rahul_key-cert.pub
```

Example output includes:

```
Type: ssh-ed25519-cert-v01@openssh.com
Principals:
    rahul
Valid:
    from 2026-01-01
    to   2026-12-31
```

This is useful when verifying certificate details.

# Common Mistakes

## Losing the CA Private Key

If the CA private key is lost:

- Existing certificates remain valid until they expire.
- You cannot issue new certificates with that CA.

Back up the CA key securely.

---

## Exposing the CA Private Key

Never copy:

```
ssh_ca
```

to ordinary servers or developer laptops.

Ideally:

- Store it offline or in a hardware security module (HSM) or dedicated signing service.
- Restrict who can access it.

---

## Long Certificate Lifetimes

Avoid issuing certificates valid for many years.

Short-lived certificates (hours, days, or weeks, depending on your environment) reduce risk if credentials are compromised.

---

# When Should You Use SSH Certificates?

Ideal for:

- Large companies
- Cloud infrastructure
- Kubernetes node fleets
- DevOps teams
- CI/CD systems
- Frequently rebuilt servers

For a few personal servers, traditional SSH keys are usually simpler.

---

# Security Best Practices

- Use Ed25519 CA keys when appropriate.
- Protect the CA private key with strong access controls.
- Keep certificate lifetimes reasonably short.
- Review issued certificates regularly.
- Use different CAs for development and production environments.
- Rotate CA keys according to organizational policy.

# Interview Questions

### 1. What is an SSH certificate?

An SSH certificate is a public key that has been signed by a trusted Certificate Authority (CA), allowing servers to verify it without storing each user's public key individually.

---

### 2. What is a Certificate Authority (CA)?

A CA is a trusted entity that signs SSH keys and whose public key is trusted by servers.

---

### 3. Why are SSH certificates useful?

They simplify user management, support centralized trust, allow expiration dates, and scale well across large numbers of servers.

---

### 4. What is the difference between a host certificate and a user certificate?

- A **user certificate** authenticates a person or service account to a server.
- A **host certificate** authenticates the server to clients.

---

### 5. Which `sshd_config` option tells a server to trust a CA?

```
TrustedUserCAKeys /etc/ssh/ssh_ca.pub
```
