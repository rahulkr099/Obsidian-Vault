# Module 6 — SSH Security

# Lesson 12: SSH Key Rotation & Lifecycle Management — Managing SSH Keys Securely

Generating an SSH key is **not** the end of the story.

Like passwords, SSH keys have a lifecycle:

```
Generate

↓

Deploy

↓

Use

↓

Rotate

↓

Revoke

↓

Retire
```

A production environment must have a process for managing keys over time.

# What is Key Rotation?

Key rotation means:

```
Old SSH Key

↓

Replace

↓

New SSH Key
```

without disrupting legitimate access.

The goal is to reduce risk if a key is lost, stolen, or becomes outdated.

---

# Why Rotate SSH Keys?

Imagine:

```
Laptop

↓

Private Key

↓

Laptop Stolen
```

If the private key was copied:

```
Attacker

↓

SSH Login

↓

Server Compromised
```

Regular rotation limits the usefulness of an old or exposed key.

---

# When Should You Rotate Keys?

Common situations include:

- Employee leaves the company
- Laptop is lost or stolen
- Key is accidentally exposed
- Periodic security policy (for example, annually)
- Migration to a stronger algorithm (such as Ed25519)

---

# Traditional Rotation Process

```
Old Key

↓

Generate New Key

↓

Install New Public Key

↓

Test Login

↓

Remove Old Key
```

The key point is **never remove the old key until the new one has been tested**.

---

# Step 1 — Generate a New Key

Example:

```bash
ssh-keygen -t ed25519 -C "rahul-2026"
```

Produces:

```
id_ed25519
id_ed25519.pub
```

If you already have a key with that name, use a different filename:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519_2026
```

---

# Step 2 — Install the New Public Key

Using:

```bash
ssh-copy-id user@server
```

or manually append:

```bash
cat id_ed25519_2026.pub >> ~/.ssh/authorized_keys
```

Now both keys work.

---

# Step 3 — Verify the New Key

Test:

```bash
ssh -i ~/.ssh/id_ed25519_2026 user@server
```

Successful login:

```
✓ New Key Works
```

Only after confirming this should you continue.

---

# Step 4 — Remove the Old Key

Edit:

```
~/.ssh/authorized_keys
```

Delete:

```
Old Public Key
```

Save.

Now:

```
Only New Key

↓

Login Allowed
```

---

# Zero-Downtime Rotation

Never do this:

```
Delete Old Key

↓

Generate New Key

↓

Oops...
```

If something goes wrong:

```
No Working Keys

↓

Locked Out
```

Correct workflow:

```
Old Key

↓

Add New Key

↓

Test

↓

Delete Old Key
```

---

# Rotating Keys Across Many Servers

Suppose you manage:

```
100 Servers
```

Workflow:

```
Generate New Key

↓

Install New Key Everywhere

↓

Verify

↓

Remove Old Key Everywhere
```

This minimizes the chance of losing access.

---

# Compromised Key Scenario

Suppose:

```
Private Key Uploaded to GitHub
```

Treat it as compromised.

Immediately:

1. Generate a new key.
2. Install the new public key.
3. Remove the compromised public key from every server.
4. Review logs for unexpected activity.
5. Notify your security team if required.

---

# Auditing `authorized_keys`

View:

```bash
cat ~/.ssh/authorized_keys
```

Look for:

- Unknown keys
- Duplicate keys
- Former employees' keys
- Expired temporary access
- Keys with unnecessary options

---

# Identifying Keys

A key comment helps identify ownership.

Example:

```
ssh-ed25519 AAAAC3... rahul-laptop
```

Better than:

```
ssh-ed25519 AAAAC3...
```

Use meaningful comments such as:

```
rahul-work-laptop
deploy-ci
backup-server
```

---

# Listing Your Local Keys

```bash
ls ~/.ssh
```

Example:

```
id_ed25519
id_ed25519.pub
id_ed25519_2026
id_ed25519_2026.pub
config

```

Remove obsolete keys only after confirming they are no longer used.

# Checking Which Key SSH Uses

Verbose mode:

```bash
ssh -v user@server
```

Look for:

```
Offering public key:
```

This confirms which identity the client is presenting.

---

# Using Multiple Keys

Example:

```
Laptop

↓

Work Key

↓

Personal Key

↓

GitHub Key
```

Configure:

```
~/.ssh/config
```

Example:

```
Host production
    HostName server.example.com
    User rahul
    IdentityFile ~/.ssh/id_ed25519_work

Host github.com
    IdentityFile ~/.ssh/id_ed25519_github
```

This avoids confusion when you have multiple identities.

# Rotation Policy Example

Many organizations define a policy such as:

|Key Type|Rotation|
|---|---|
|Administrator|Every 12 months|
|Contractor|End of contract|
|Temporary Access|On expiration|
|Compromised Key|Immediately|

The exact schedule depends on organizational risk and operational needs.

Automation reduces manual effort and helps keep access consistent.

# Common Mistakes

## Removing the Old Key Too Soon

Wrong:

```
Delete

↓

Generate

↓

Hope Everything Works
```

Correct:

```
Generate

↓

Install

↓

Test

↓

Delete
```

---

## Never Rotating Keys

Some keys remain in use for many years.

Long-lived keys increase the impact if they are ever compromised.

---

## Leaving Old Keys Behind

Old keys belonging to:

- Former employees
- Old laptops
- Retired servers

should be removed after verifying they are no longer needed.

---

## Using the Same Key Everywhere

Avoid sharing one SSH key across:

- Personal laptop
- Work laptop
- CI/CD systems
- Production automation

Separate keys make revocation and auditing much easier.

---

# Security Best Practices

- Prefer Ed25519 for new keys.
- Protect private keys with a passphrase.
- Use separate keys for different purposes.
- Rotate keys periodically according to policy.
- Remove stale entries from `authorized_keys`.
- Review SSH access during employee onboarding and offboarding.
- Keep an inventory of who owns each key.

# Interview Questions

### 1. What is SSH key rotation?

It is the process of replacing an existing SSH key pair with a new one while maintaining secure access.

---

### 2. What is the safest way to rotate an SSH key?

1. Generate a new key.
2. Add the new public key to the server.
3. Test login with the new key.
4. Remove the old public key.

---

### 3. What should you do if a private key is exposed?

Treat it as compromised:

- Generate a replacement key.
- Deploy the new public key.
- Remove the compromised key from all systems.
- Review logs for suspicious activity.

---

### 4. Why should different devices use different SSH keys?

It improves security, simplifies auditing, and allows you to revoke access for one device without affecting others.

---

### 5. Why are descriptive key comments useful?

They help identify the owner and purpose of a key, making audits and cleanup much easier.
