# What is SSH Hardening?

SSH hardening means:

```
Reduce Risk

↓

Remove Weaknesses

↓

Secure Configuration

↓

Production Ready
```

It is the process of minimizing the attack surface while preserving necessary functionality.

# Step 1 — Verify the SSH Service

Ubuntu/Debian:

```bash
systemctl status ssh
```

RHEL/CentOS:

```bash
systemctl status sshd
```

Expected:

```
Active: active (running)
```

---

# Step 2 — Validate Configuration

Always check syntax before restarting:

```bash
sudo sshd -t
```

No output:

```
Configuration Valid
```

---

# Step 3 — View Effective Configuration

Instead of reading comments:

```bash
sudo sshd -T
```

Filter specific options:

```bash
sudo sshd -T | grep permitrootlogin
```

```bash
sudo sshd -T | grep passwordauthentication
```

```bash
sudo sshd -T | grep pubkeyauthentication
```

Check:

# Step 7 — Verify User Restrictions

Check:

```bash
sudo sshd -T | grep allowusers
```

or

```bash
sudo sshd -T | grep allowgroups
```

Example:

```
allowusers rahul deploy
```

or

```
allowgroups sshusers
```

---

# Step 8 — Check SSH Permissions

Inspect:

```bash
ls -la ~/.ssh
```

Expected:

```
drwx------ .ssh
-rw------- authorized_keys
-rw------- id_ed25519
-rw-r--r-- id_ed25519.pub
```

---

# Step 9 — Verify File Ownership

```bash
ls -la ~/.ssh
```

Expected:

```
rahul rahul authorized_keys
rahul rahul id_ed25519
```

If incorrect:

```bash
sudo chown -R $USER:$USER ~/.ssh
```

---

# Step 10 — Verify Fail2Ban

Check service:

```bash
sudo systemctl status fail2ban
```

Check jails:

```bash
sudo fail2ban-client status
```

Check SSH jail:

```bash
sudo fail2ban-client status sshd
```

Expected:

```
Jail list: sshd
```

---

# Step 11 — Review SSH Logs

Recent logs:

```bash
sudo journalctl -u ssh --since today
```

Search failures:

```bash
sudo journalctl -u ssh | grep Failed
```

Search successful logins:

```bash
sudo journalctl -u ssh | grep Accepted
```

---

# Step 12 — Review Login History

Successful:

```bash
last
```

Failed:

```bash
sudo lastb
```

Current users:

```bash

```

Detailed view:

```bash
w
```

---

# Step 13 — Verify Active SSH Connections

```bash
ss -tnp | grep ssh
```

Review:

- Connected clients
- Remote IPs
- Established sessions

---

# Step 14 — Verify Host Keys

List:

```bash
ls -l /etc/ssh/ssh_host_*
```

Display fingerprint:

```bash
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

---

# Step 15 — Verify Algorithms

Supported keys:

```bash
ssh -Q key
```

Supported KEX:

```bash
ssh -Q kex
```

Supported ciphers:

```bash
ssh -Q cipher
```

Supported MACs:

```bash
ssh -Q mac
```

For most modern deployments, prefer:

- Ed25519 keys
- `curve25519-sha256`
- `chacha20-poly1305@openssh.com`
- `aes256-gcm@openssh.com`

# Example Secure `sshd_config`

```
PermitRootLogin no

PasswordAuthentication no
PubkeyAuthentication yes
PermitEmptyPasswords no

MaxAuthTries 3
LoginGraceTime 30

AllowUsers rahul deploy

AllowTcpForwarding no
X11Forwarding no

StrictModes yes

ClientAliveInterval 300
ClientAliveCountMax 2
```

This is a strong baseline for many production servers, though you should adapt it to your operational requirements.

# Common Security Mistakes

## Root Login Enabled

Bad:

```
PermitRootLogin yes
```

Better:

```
PermitRootLogin no
```

---

## Password Authentication Enabled

Bad:

```
PasswordAuthentication yes
```

Better (after verifying SSH key access):

```
PasswordAuthentication no
```

---

## Weak File Permissions

Bad:

```
777 id_ed25519
```

Correct:

```
600 id_ed25519
```

---

## Too Many Allowed Users

Bad:

```
AllowUsers *
```

Better:

```
AllowUsers rahul deploy
```

Or manage access through:

```
AllowGroups sshusers
```

---

## Ignoring Logs

Without monitoring:

```
Brute Force

↓

Unknown
```

With monitoring:

```
Logs

↓

Detected

↓

Blocked

↓

Investigated
```

# SSH Audit Scenario

Suppose you're asked:

> "Please audit this server before production."

Your checklist could be:

1. Check SSH service status.
2. Validate `sshd_config`.
3. Verify root login is disabled.
4. Verify password authentication policy.
5. Review allowed users/groups.
6. Confirm file permissions and ownership.
7. Verify Fail2Ban.
8. Review recent SSH logs.
9. Check active sessions.
10. Verify key algorithms.
11. Test login with a non-root account using SSH keys.
12. Confirm you can still access the server before closing existing sessions.

---

# Security Best Practices

- Use Ed25519 keys for new deployments.
- Use a passphrase on private keys.
- Rotate keys periodically.
- Restrict SSH users.
- Keep OpenSSH updated.
- Review logs regularly.
- Use a bastion host for private infrastructure.
- Prefer SSH certificates in large environments.
- Test configuration changes before restarting the SSH service.

# Interview Questions

### 1. What is SSH hardening?

SSH hardening is the process of securing an SSH server by reducing unnecessary risk, enforcing strong authentication, limiting access, and following security best practices.

---

### 2. Which command validates `sshd_config`?

```bash
sudo sshd -t
```

---

### 3. Which command shows the effective SSH configuration?

```bash
sudo sshd -T
```

---

### 4. Name five important SSH security checks.

A good answer could include:

- Disable root login
- Disable password authentication (after verifying key-based access)
- Use SSH keys
- Enable Fail2Ban
- Restrict allowed users or groups

Other valid checks include verifying permissions, reviewing logs, and checking active sessions.

---

### 5. What should you do before restarting the SSH service after making configuration changes?

- Run `sudo sshd -t` to validate the configuration.
- Keep your current SSH session open.
- Test a new SSH connection in another terminal.
- Restart the service only after confirming everything works.
