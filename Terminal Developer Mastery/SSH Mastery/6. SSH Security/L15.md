# Scenario

You've just joined a startup as a Backend Engineer.

You receive a new Ubuntu server.

Requirements:

- Only administrators should access SSH.
- No passwords.
- No root login.
- SSH keys only.
- Fail2Ban enabled.
- SSH logging enabled.
- Modern cryptography.
- Proper permissions.
- Production-ready configuration.

---

# Initial State

The server currently has:

```
PermitRootLogin yes

PasswordAuthentication yes

No Fail2Ban

No SSH keys

No restrictions
```

This is **not** production-ready.

---

# Phase 1 — Verify SSH

Check the service:

```bash
systemctl status ssh
```

Expected:

```
Active: active (running)
```

---

# Phase 2 — Create an Administrator

Create:

```bash
sudo adduser rahul
```

Give sudo access:

Ubuntu:

```bash
sudo usermod -aG sudo rahul
```

Verify:

```bash
groups rahul
```

Expected:

```
rahul sudo
```

---

# Phase 3 — Generate an SSH Key

On your client machine:

```bash
ssh-keygen -t ed25519 -C "rahul-workstation"
```

Files created:

```
~/.ssh/id_ed25519
~/.ssh/id_ed25519.pub
```

---

# Phase 4 — Install the Public Key

Copy it:

```bash
ssh-copy-id rahul@server
```

Or manually:

```bash
cat ~/.ssh/id_ed25519.pub
```

Append it to:

```
~rahul/.ssh/authorized_keys
```

---

# Phase 5 — Verify SSH Key Login

Test:

```bash
ssh rahul@server
```

Confirm:

- Login succeeds
- No password is requested (unless your private key has a passphrase)

Keep your original session open while testing.

---

# Phase 6 — Secure `sshd_config`

Edit:

```bash
sudo nvim /etc/ssh/sshd_config
```

Recommended baseline:

```
PermitRootLogin no

PasswordAuthentication no
PubkeyAuthentication yes
PermitEmptyPasswords no

MaxAuthTries 3
LoginGraceTime 30

AllowUsers rahul

AllowTcpForwarding no
X11Forwarding no

StrictModes yes

ClientAliveInterval 300
ClientAliveCountMax 2
```

---

# Phase 7 — Validate Configuration

Never restart blindly.

Run:

```bash
sudo sshd -t
```

No output:

```
Configuration Valid
```

---

# Phase 8 — Restart SSH

Ubuntu:

```bash
sudo systemctl restart ssh
```

Test from another terminal:

```bash
ssh rahul@server
```

If everything works:

Close the original session.

---

# Phase 9 — Verify Permissions

Check:

```bash
ls -la ~/.ssh
```

Expected:

```
drwx------
-rw------- authorized_keys
-rw------- id_ed25519
-rw-r--r-- id_ed25519.pub
```

Fix if needed:

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
chmod 600 ~/.ssh/id_ed25519
chmod 644 ~/.ssh/id_ed25519.pub
```

---

# Phase 10 — Verify Ownership

Check:

```bash
ls -la ~/.ssh
```

Expected:

```
rahul rahul authorized_keys
```

Fix:

```bash
sudo chown -R rahul:rahul ~/.ssh
```

---

# Phase 11 — Install Fail2Ban

Ubuntu:

```bash
sudo apt update
sudo apt install fail2ban
```

Enable:

```bash
sudo systemctl enable fail2ban
sudo systemctl start fail2ban
```

Check:

```bash
sudo fail2ban-client status
```

---

# Phase 12 — Configure the SSH Jail

Create:

```
/etc/fail2ban/jail.local
```

Example:

```
[sshd]
enabled = true
maxretry = 5
findtime = 10m
bantime = 1h
```

Restart:

```bash
sudo systemctl restart fail2ban
```

Verify:

```bash
sudo fail2ban-client status sshd
```

---

# Phase 13 — Verify Logs

Recent SSH logs:

```bash
sudo journalctl -u ssh --since today
```

Monitor live:

```bash
sudo journalctl -u ssh -f
```

Login from another terminal.

Observe:

```
Accepted publickey for rahul
```

---

# Phase 14 — Audit Login History

Successful:

```bash
last
```

Failed:

```bash
sudo lastb
```

Current users:

```bash
who
```

Detailed view:

```bash
w
```

---

# Phase 15 — Review Cryptography

Supported keys:

```bash
ssh -Q key
```

Supported KEX:

```bash
ssh -Q kex
```

Supported ciphers:

```bash
ssh -Q cipher
```

Recommended defaults for modern deployments:

- Ed25519 keys
- `curve25519-sha256`
- `chacha20-poly1305@openssh.com`
- `aes256-gcm@openssh.com`

---

# Final Audit

Verify:

```bash
sudo sshd -T
```

Review:

```
permitrootlogin no

passwordauthentication no

pubkeyauthentication yes
```

# Challenge Tasks

## Challenge 1 — Multiple Administrators

Create another administrator:

```bash
sudo adduser alice
```

Generate a separate SSH key and configure access without affecting `rahul`.

---

## Challenge 2 — Separate Keys

Use:

- Work laptop
- Personal laptop
- CI/CD server

Create a unique SSH key for each.

Configure:

```
~/.ssh/config
```

so the correct key is selected automatically.

---

## Challenge 3 — Bastion Access

Design:

```
Laptop

↓

Bastion

↓

Private Server
```

Configure `ProxyJump` and verify that the private server cannot be reached directly from the Internet.

---

## Challenge 4 — Rotate Keys

Perform a complete key rotation:

1. Generate a new key.
2. Install it.
3. Test it.
4. Remove the old key.

Ensure there is no downtime.

---

## Challenge 5 — Simulate an Attack

In a **lab environment you own**, intentionally make several failed SSH login attempts and observe:

- SSH logs
- Fail2Ban activity
- The banned IP entry

Then unban the test IP.

# Interview Simulation

## Scenario

Your interviewer asks:

> "A Linux server is going live tomorrow. Walk me through how you'd secure SSH."

A strong answer would cover:

1. Create a non-root administrator.
2. Generate and install SSH keys.
3. Verify key-based login.
4. Disable root login.
5. Disable password authentication.
6. Restrict SSH users or groups.
7. Validate the configuration with `sshd -t`.
8. Test access using a second SSH session.
9. Enable Fail2Ban.
10. Review logs and login history.
11. Verify file permissions and ownership.
12. Keep OpenSSH updated and periodically rotate SSH keys.
