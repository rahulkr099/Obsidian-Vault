# Module 6 — SSH Security

# Lesson 2: `authorized_keys` Key Restrictions — Fine-Grained SSH Access Control

In the previous lesson, you learned that every line in `authorized_keys` represents one trusted public key.

But what if you want a key to:

- Log in **only from your office IP**?
- Run **only one backup script**?
- **Never** open an interactive shell?
- **Never** create SSH tunnels?

That's exactly what **`authorized_keys` options** are for.

They allow you to restrict what **each individual key** can do, without affecting other keys.

# Where Do Restrictions Go?

A normal entry looks like:

```
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIF... rahul-laptop
```

A restricted entry looks like:

```
from="203.0.113.10" ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIF... rahul-laptop
```

Notice:

```
Restrictions

↓

Public Key

↓

Comment
```

Restrictions always appear **before** the key type.

---

# Why Restrict Keys?

Suppose a backup server only needs to upload backups.

Should it be allowed to:

- Open an interactive shell?
- Forward ports?
- Use X11?
- Run arbitrary commands?

No.

Instead, give it only the minimum permissions it needs.

This follows the **Principle of Least Privilege**.

---

# Option 1 — `from=`

Restrict a key to specific IP addresses or hostnames.

Example:

```
from="203.0.113.25" ssh-ed25519 AAAA... office-laptop
```

Now the key works **only** from:

```
203.0.113.25
```

Attempting to use the same key from another IP fails.

You can specify multiple addresses:

```
from="203.0.113.25,198.51.100.20" ssh-ed25519 AAAA... office-laptop
```

You can also use CIDR ranges:

```
from="192.168.1.0/24" ssh-ed25519 AAAA... office-network
```

---

# Option 2 — `command=`

Force SSH to execute a single command.

Example:

```
command="/usr/local/bin/backup.sh" ssh-ed25519 AAAA... backup-key
```

Even if the client runs:

```bash
ssh backup@server ls
```

The server ignores `ls` and runs:

```bash
/usr/local/bin/backup.sh
```

This is commonly used for:

- Automated backups
- Git repositories
- Deployment hooks
- Monitoring systems

---

# Option 3 — `no-port-forwarding`

Disable all SSH port forwarding.

Example:

```
no-port-forwarding ssh-ed25519 AAAA... ci-server
```

The key can still log in, but commands like:

```bash
ssh -L 5432:localhost:5432 server
```

or

```bash
ssh -R 8080:localhost:80 server
```

will fail.

Use this when SSH tunneling is unnecessary.

---

# Option 4 — `no-agent-forwarding`

Disable SSH agent forwarding.

Example:

```
no-agent-forwarding ssh-ed25519 AAAA... automation
```

Even if the client requests:

```bash
ssh -A server
```

the forwarded SSH agent is unavailable.

This reduces the risk of agent misuse.

---

# Option 5 — `no-X11-forwarding`

Prevent graphical X11 sessions.

Example:

```
no-X11-forwarding ssh-ed25519 AAAA... server
```

Commands like:

```bash
ssh -X server
```

will not work.

Most production servers don't need X11 forwarding.

---

# Option 6 — `no-pty`

Disable interactive terminal sessions.

Example:

```
no-pty ssh-ed25519 AAAA... deploy-key
```

This prevents the user from getting a shell such as:

```bash
ssh server
```

However, non-interactive commands can still be allowed (for example, with `command=`).

Very useful for automation accounts.

---

# Combining Restrictions

Restrictions can be combined.

Example:

```
from="203.0.113.25",command="/usr/local/bin/backup.sh",no-port-forwarding,no-agent-forwarding,no-X11-forwarding,no-pty ssh-ed25519 AAAA... backup-server
```

Meaning:

- Only from one IP
- Only runs `backup.sh`
- No shell
- No tunnels
- No X11
- No agent forwarding

This is a highly restricted and secure automation key.

---

# Real-World Example — Backup Server

Backup server:

```
192.168.10.50
```

Allowed to:

- Upload backups
- Nothing else

`authorized_keys` entry:

```
from="192.168.10.50",command="/usr/local/bin/backup.sh",no-port-forwarding,no-agent-forwarding,no-X11-forwarding,no-pty ssh-ed25519 AAAA... backup-server
```

Even if someone steals the backup key, they cannot:

- Open a shell
- Tunnel traffic
- Forward an SSH agent
- Start GUI applications
- Execute arbitrary commands

---

# Real-World Example — Git Server

Many Git hosting systems use:

```
command="/usr/bin/git-shell -c \"$SSH_ORIGINAL_COMMAND\"" ssh-ed25519 AAAA... developer
```

This allows Git operations while preventing normal shell access.

# Common Mistakes

## Wrong Placement

❌ Incorrect:

```
ssh-ed25519 AAAA... no-pty
```

✅ Correct:

```
no-pty ssh-ed25519 AAAA...
```

---

## Missing Quotes

❌ Incorrect:

```
command=/usr/local/bin/backup.sh
```

✅ Correct:

```
command="/usr/local/bin/backup.sh"
```

---

## Restricting Yourself Accidentally

If your personal key has:

```
no-pty
```

then:

```bash
ssh server
```

won't give you an interactive shell.

Always keep an unrestricted administrator key available for emergencies.

---

# Testing Restrictions

Verbose mode:

```bash
ssh -v user@server
```

Test a forced command:

```bash
ssh user@server
```

If `command=` is configured, you'll see the forced command run instead of a shell.

Try creating a tunnel:

```bash
ssh -L 5432:localhost:5432 user@server
```

If `no-port-forwarding` is active, the tunnel will be rejected.

---

# Security Best Practices

- Use a separate SSH key for each device or service.
- Apply the **minimum required permissions** to every key.
- Use `command=` for automation tasks.
- Restrict automation keys with `no-pty`.
- Restrict keys to trusted IP addresses using `from=`.
- Review `authorized_keys` regularly and remove unused keys.

# Interview Questions

### 1. What is the purpose of `from=`?

It restricts an SSH key so it can only be used from specified IP addresses, networks, or hostnames.

---

### 2. What does `command=` do?

It forces the server to execute a predefined command, ignoring any command requested by the client.

---

### 3. Why use `no-pty`?

It prevents interactive shell access, making the key suitable for automation or single-purpose tasks.

---

### 4. What does `no-port-forwarding` prevent?

It disables SSH local, remote, and dynamic port forwarding for that specific key.

---

### 5. Why are `authorized_keys` restrictions useful?

They apply the principle of least privilege, limiting what each SSH key can do and reducing the impact if a key is compromised.

---

# Summary

In this lesson, you learned how to strengthen SSH security by applying restrictions directly to individual entries in `authorized_keys`.

You can now:

- Restrict keys to specific IP addresses (`from=`)
- Force a single command (`command=`)
- Disable port forwarding
- Disable agent forwarding
- Disable X11 forwarding
- Disable interactive shells (`no-pty`)
- Combine multiple restrictions to create secure, purpose-specific SSH keys

These techniques are widely used for backup systems, deployment automation, Git servers, CI/CD runners, and other production services where full shell access is unnecessary.
