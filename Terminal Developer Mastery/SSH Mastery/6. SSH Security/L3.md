# Module 6 — SSH Security

# Lesson 3: Root Login Security — Why You Should Never SSH as `root`

One of the first things Linux administrators do on a new server is **disable direct root SSH login**.

Why?

Because **every attacker already knows the root username exists**. If they only have to guess the password, their job becomes much easier.

Professional Linux servers use:

- A normal user account
- SSH keys
- `sudo` for administrative tasks

# What is the Root User?

The **root** account is the Linux superuser.

Root can:

- Read any file
- Delete any file
- Install software
- Create users
- Modify networking
- Shut down the system
- Change security settings

Example:

```bash
sudo rm -rf /
```

With sufficient privileges, commands like this can destroy a system. That's why root access must be tightly controlled.

---

# Why is Root Login Dangerous?

Suppose an attacker scans the Internet.

They already know:

```
Username:

root
```

They only need to guess:

```
Password
```

If you disable root login:

```
No root login

↓

Must guess:

Username

+

Password (or bypass key authentication)
```

This removes a common attack target and improves accountability.

---

# Better Workflow

Instead of:

```
Internet

↓

root

↓

Full System Access
```

Use:

```
Internet

↓

rahul

↓

sudo

↓

Root Privileges (when needed)
```

Now every administrative action is tied to a specific user account.

# The SSH Configuration

The relevant setting is in:

```
/etc/ssh/sshd_config
```

Search for:

```
PermitRootLogin
```

---

# Option 1 — `PermitRootLogin yes`

```
PermitRootLogin yes
```

Behavior:

```bash
ssh root@server
```

Allowed.

This is **not recommended** for production servers.

---

# Option 2 — `PermitRootLogin no`

```
PermitRootLogin no
```

Behavior:

```bash
ssh root@server
```

Result:

```
Permission denied
```

This is the recommended setting for most production environments.

---

# Option 3 — `PermitRootLogin prohibit-password`

```
PermitRootLogin prohibit-password
```

Behavior:

- Password login ❌
- SSH key login ✅

This can be useful in environments that require controlled root access using SSH keys only.

---

# Option 4 — `PermitRootLogin forced-commands-only`

```
PermitRootLogin forced-commands-only
```

Behavior:

Root cannot open an interactive shell.

Root may authenticate **only** when a forced command is configured (for example, in `authorized_keys`).

This is useful for specialized automation tasks.

---

# Which Option Should You Use?

|Setting|Recommended?|Use Case|
|---|---|---|
|`yes`|❌ No|Testing only|
|`prohibit-password`|⚠️ Sometimes|Legacy or special environments|
|`forced-commands-only`|✅ Niche|Automated tasks|
|`no`|✅ Yes|Most production servers|

# Using `sudo`

Instead of:

```bash
ssh root@server
```

Log in as a normal user:

```bash
ssh rahul@server
```

Need administrative privileges?

```bash
sudo apt update
```

or:

```bash
sudo systemctl restart nginx
```

---

# Why `sudo` is Better

Every privileged command is associated with a user.

Example log:

```
rahul

↓

sudo systemctl restart nginx
```

Instead of:

```
root

↓

Unknown Person
```

This greatly improves auditing and accountability.

---

# Create an Administrative User

Example:

```bash
sudo adduser deploy
```

Grant administrative rights (Ubuntu/Debian):

```bash
sudo usermod -aG sudo deploy
```

RHEL/CentOS:

```bash
sudo usermod -aG wheel deploy
```

Verify:

```bash
groups deploy
```

---

# Safe Migration

**Never** disable root login before verifying your new account.

Recommended sequence:

1. Create a new user.
2. Add the user to the `sudo` (or `wheel`) group.
3. Configure SSH keys for the new user.
4. Verify login:

```bash
ssh deploy@server
```

1. Test:

```bash
sudo whoami
```

Expected output:

```
root
```

1. Only then disable root login.

---

# Editing `sshd_config`

Open:

```bash
sudo nvim /etc/ssh/sshd_config
```

or:

```bash
sudo nano /etc/ssh/sshd_config
```

Set:

```
PermitRootLogin no
```

Validate:

```bash
sudo sshd -t
```

Restart:

Ubuntu/Debian:

```bash
sudo systemctl restart ssh
```

RHEL/CentOS:

```bash
sudo systemctl restart sshd
```

---

# Test Before Closing Your Session

Keep your current SSH session open.

Open a **second** terminal:

```bash
ssh deploy@server
```

Verify everything works before closing the original connection.

This helps avoid accidentally locking yourself out.

# Common Mistakes

## Disabling Root Before Testing

Wrong order:

```
Disable Root

↓

Create User

↓

Locked Out
```

Correct order:

```
Create User

↓

Test User

↓

Disable Root
```

---

## Forgetting to Add the User to `sudo`

You can log in:

```bash
ssh deploy@server
```

But:

```bash
sudo apt update
```

fails because the user lacks administrative privileges.

---

## Restarting Without Validation

Always validate first:

```bash
sudo sshd -t
```

Only restart if there are no errors.

---

## Closing Your Only SSH Session

Never do this until you've confirmed the new configuration works in another terminal.

---

# Security Best Practices

- Disable direct root SSH login on production systems.
- Use individual user accounts with `sudo`.
- Protect administrator accounts with SSH keys.
- Keep at least one emergency access method (such as a cloud provider's console or VM console).
- Review who has `sudo` access regularly.

# Interview Questions

### 1. Why should root SSH login be disabled?

Because the root account is well-known, has unrestricted privileges, and provides poor accountability. Using individual user accounts with `sudo` is more secure.

---

### 2. What does `PermitRootLogin no` do?

It prevents direct SSH logins to the root account.

---

### 3. What is the difference between `PermitRootLogin no` and `PermitRootLogin prohibit-password`?

- `no` blocks all direct root SSH logins.
- `prohibit-password` allows root login only with SSH keys, not passwords.

---

### 4. Why is `sudo` preferred?

It grants administrative privileges only when needed and records which user performed privileged actions.

---

### 5. What is the safest way to disable root login?

Create and test a separate administrative user with `sudo` and SSH key access before changing `PermitRootLogin` to `no`.
