# Module 6 — SSH Security

# Lesson 5: SSH File Permissions — Why OpenSSH is So Strict

One of the most common SSH errors is:

```
Permission denied (publickey)
```

Even if your SSH keys are correct, **OpenSSH refuses to use them if the file permissions are too open.**

This is intentional. If other users on the system can read or modify your SSH files, your account could be compromised.

# Why Does SSH Care About Permissions?

Imagine your private key is stored like this:

```
-rwxrwxrwx id_ed25519
```

Everyone on the system can read it.

That means another user could copy your private key and impersonate you.

To prevent this, OpenSSH refuses to use insecure files.

# Permission Basics

View permissions:

```bash
ls -la ~/.ssh
```

Example:

```
drwx------ .ssh
-rw------- authorized_keys
-rw------- id_ed25519
-rw-r--r-- id_ed25519.pub
-rw------- config
-rw-r--r-- known_hosts
```

|Number|Meaning|
|---|---|
|7|Read + Write + Execute|
|6|Read + Write|
|5|Read + Execute|
|4|Read Only|
|0|No Permission|

```
700
```

# 1. `.ssh` Directory

Correct permission:

```bash
chmod 700 ~/.ssh
```

Meaning:

```
Owner:
✓ Read
✓ Write
✓ Execute

Others:
✗ No Access
```

Verify:

```bash
ls -ld ~/.ssh
```

Expected:

```
drwx------
```

---

# 2. `authorized_keys`

Correct permission:

```bash
chmod 600 ~/.ssh/authorized_keys
```

Meaning:

Only the owner can:

- Read
- Write

Nobody else can access it.

Verify:

```bash
ls -l ~/.ssh/authorized_keys
```

Expected:

```
-rw-------
```

---

# 3. Private Key

Example:

```
id_ed25519
```

Correct permission:

```bash
chmod 600 ~/.ssh/id_ed25519
```

or even stricter:

```bash
chmod 400 ~/.ssh/id_ed25519
```

Verify:

```bash
ls -l ~/.ssh/id_ed25519
```

Expected:

```
-rw-------
```

or

```
-r--------
```

---

# Why Private Keys Must Be Protected

Suppose:

```
-rwxrwxrwx id_ed25519
```

Anyone on the machine can copy it.

SSH detects this and refuses to use it.

Typical warning:

```
WARNING: UNPROTECTED PRIVATE KEY FILE!
```

Example:

```
Permissions 0777 for 'id_ed25519' are too open.
```

SSH then ignores the key.

---

# 4. Public Key

Example:

```
id_ed25519.pub
```

Recommended permission:

```bash
chmod 644 ~/.ssh/id_ed25519.pub
```

Expected:

```
-rw-r--r--
```

Public keys are designed to be shared, so they do not need to be secret.

---

# 5. SSH Config File

Example:

```
~/.ssh/config
```

Recommended:

```bash
chmod 600 ~/.ssh/config
```

Verify:

```bash
ls -l ~/.ssh/config
```

Expected:

```
-rw-------
```

---

# 6. `known_hosts`

Recommended:

```bash
chmod 644 ~/.ssh/known_hosts
```

Expected:

```
-rw-r--r--
```

This file stores server host keys.

It does **not** contain your private keys.

---

# Ownership Matters

Correct ownership:

```bash
ls -la ~/.ssh
```

Example:

```
rahul rahul authorized_keys
rahul rahul id_ed25519
```

If files belong to another user:

```
root root id_ed25519
```

SSH may reject them.

Fix ownership:

```bash
chown -R $USER:$USER ~/.ssh
```

# Common Permission Problems

## Problem 1 — Directory Too Open

Bad:

```
drwxrwxrwx .ssh
```

Fix:

```bash
chmod 700 ~/.ssh
```

---

## Problem 2 — Private Key Too Open

Bad:

```
-rwxrwxrwx id_ed25519
```

Fix:

```bash
chmod 600 ~/.ssh/id_ed25519
```

---

## Problem 3 — Wrong Owner

Bad:

```
root root id_ed25519
```

Fix:

```bash
sudo chown -R $USER:$USER ~/.ssh
```

---

## Problem 4 — Missing Execute Permission on `.ssh`

If the directory isn't executable by the owner:

```
drw-------
```

SSH can't enter the directory.

Fix:

```bash
chmod 700 ~/.ssh
```

# Troubleshooting

## SSH Ignores Your Key

Run:

```bash
ssh -v user@server
```

Look for messages like:

```
Offering public key:
```

or

```
WARNING: UNPROTECTED PRIVATE KEY FILE!
```

---

## Verify Ownership

```bash
ls -la ~/.ssh
```

Check that every file belongs to the correct user.

---

## Check Numeric Permissions

```bash
stat -c "%a %n" ~/.ssh/*
```

Example:

```
600 authorized_keys
600 config
600 id_ed25519
644 id_ed25519.pub
644 known_hosts
```

This is a quick way to audit permissions.

---

# Security Best Practices

- Never use `777` for SSH files.
- Never share your private key.
- Use a passphrase on your private key.
- Keep `.ssh` owned by the correct user.
- Review permissions after copying files or restoring backups.

# Interview Questions

### 1. Why does OpenSSH reject overly permissive private keys?

Because other users on the system could read or modify the key, making it insecure. OpenSSH refuses to use keys that are not adequately protected.

---

### 2. What permissions should `~/.ssh` have?

```
700
```

---

### 3. What permissions should a private key have?

Typically:

```
600
```

or

```
400
```

---

### 4. Why can a public key have `644` permissions?

Because it is intended to be shared and does not need to remain secret.

---

### 5. How can you quickly verify SSH file permissions?

Use:

```bash
ls -la ~/.ssh
```

or for numeric permissions:

```bash
stat -c "%a %n" ~/.ssh/*
```
