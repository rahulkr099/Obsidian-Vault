# Module 6 — SSH Security

# Lesson 6: Restricting SSH Users — Controlling Who Can Log In

Even if your SSH server is secure, **not every Linux user should be allowed to log in remotely**.

For example, consider a server with these users:

```
root
rahul
deploy
backup
postgres
mysql
nginx
www-data
```

Should all of them be able to SSH into the server?

**Absolutely not.**

A production server should allow **only the users who actually need remote access**.

# Where is the Configuration?

SSH user restrictions are configured in:

```
/etc/ssh/sshd_config
```

Edit it using:

```bash
sudo nvim /etc/ssh/sshd_config
```

or

```bash
sudo nano /etc/ssh/sshd_config
```

---

# Why Restrict SSH Users?

Imagine a server with:

```
20 Linux users
```

Only:

```
rahul
deploy
```

actually need SSH access.

Without restrictions:

```
20 Possible Login Accounts
```

With restrictions:

```
2 Possible Login Accounts
```

Reducing the number of accounts exposed to SSH **reduces the attack surface**.

---

# `AllowUsers`

Allows **only specific users** to log in via SSH.

Example:

```
AllowUsers rahul deploy
```

Result:

|User|SSH Login|
|---|---|
|rahul|✅ Allowed|
|deploy|✅ Allowed|
|postgres|❌ Denied|
|mysql|❌ Denied|
|nginx|❌ Denied|
|root|❌ Denied (unless explicitly listed and permitted)|

---

# Allowing a User from a Specific IP

You can be even more restrictive.

Example:

```
AllowUsers rahul@192.168.1.*
```

Meaning:

- Rahul can SSH only from:

```
192.168.1.x
```

Attempts from other networks are rejected.

You can also specify a single IP:

```
AllowUsers rahul@203.0.113.10
```

---

# Multiple Users

Example:

```
AllowUsers rahul deploy admin
```

Only these three users can log in.

Everyone else is denied automatically.

---

# `AllowGroups`

Instead of listing users individually, you can allow an entire Linux group.

Example:

```
AllowGroups sshusers
```

Create the group:

```bash
sudo groupadd sshusers
```

Add users:

```bash
sudo usermod -aG sshusers rahul
sudo usermod -aG sshusers deploy
```

Verify:

```bash
groups rahul
```

Example output:

```
rahul sudo sshusers
```

Now any member of `sshusers` can log in.

---

# Why Groups Are Better

Suppose you have:

```
50 Developers
```

Instead of:

```
AllowUsers
developer1
developer2
developer3
...
developer50
```

Use:

```
AllowGroups developers
```

Adding or removing SSH access is as simple as changing group membership.

---

# `DenyUsers`

Explicitly blocks listed users from logging in.

Example:

```
DenyUsers postgres mysql nginx
```

These users cannot SSH, even if they have valid passwords or SSH keys.

---

# `DenyGroups`

Blocks every member of a specified group.

Example:

```
DenyGroups serviceaccounts
```

Useful for:

- Database service accounts
- Web server accounts
- System daemon accounts

---

# How SSH Evaluates These Rules

A simplified evaluation order is:

1. `DenyUsers`
2. `AllowUsers`
3. `DenyGroups`
4. `AllowGroups`

If a user is denied by a matching rule, access is refused.

Always review your configuration carefully to ensure the intended users remain allowed.

---

# Example Production Configuration

```
PermitRootLogin no

PasswordAuthentication no

PubkeyAuthentication yes

AllowUsers rahul deploy

DenyUsers postgres mysql nginx
```

This configuration means:

- Root login disabled
- Passwords disabled
- SSH keys required
- Only `rahul` and `deploy` may log in
- Service accounts are explicitly denied

---

# Enterprise Example

Company server:

```
AllowGroups
developers
devops
admins
```

Every employee belongs to one of these groups.

When someone leaves the company:

```bash
sudo gpasswd -d alice developers
```

Their SSH access is removed immediately.

# Viewing Existing Users

List local users:

```bash
cut -d: -f1 /etc/passwd
```

View human users (UID ≥ 1000 on many distributions):

```bash
awk -F: '$3>=1000 {print $1}' /etc/passwd
```

View groups:

```bash
cat /etc/group
```

---

# Verify Group Membership

Check one user:

```bash
groups rahul
```

Or:

```bash
id rahul
```

Example:

```
uid=1000(rahul)
gid=1000(rahul)
groups=1000(rahul),27(sudo),1002(sshusers)
```

---

# Testing Before Restarting

Always validate your configuration:

```bash
sudo sshd -t
```

No output means:

```
Configuration OK
```

Restart:

Ubuntu/Debian:

```bash
sudo systemctl restart ssh
```

RHEL/CentOS:

```bash
sudo systemctl restart sshd
```

**Keep your current SSH session open** and test a new login from a second terminal before disconnecting.

# Common Mistakes

## Mistake 1 — Forgetting Yourself

Bad:

```
AllowUsers deploy
```

If you're logged in as `rahul`, your next login will fail.

Correct:

```
AllowUsers rahul deploy
```

---

## Mistake 2 — Restarting Without Testing

Always:

1. Validate with `sshd -t`
2. Open a second SSH session
3. Confirm login works
4. Then close the original session

---

## Mistake 3 — Forgetting Group Membership

Configuration:

```
AllowGroups sshusers
```

But the user isn't in the group.

Fix:

```bash
sudo usermod -aG sshusers rahul
```

The user may need to log out and back in (or start a new login session) for new group membership to take effect.

---

## Mistake 4 — Allowing Service Accounts

Don't allow accounts such as:

```
mysql
postgres
nginx
www-data
daemon
```

These accounts exist to run services, not for interactive logins.

---

# Security Best Practices

- Disable root SSH login.
- Allow only administrators and deployment users.
- Use groups (`AllowGroups`) for easier management.
- Block service accounts.
- Use SSH keys instead of passwords.
- Periodically review user and group memberships.
- Remove SSH access promptly when it's no longer needed.

# Interview Questions

### 1. What does `AllowUsers` do?

It limits SSH access to the listed user accounts. All other users are denied.

---

### 2. Why is `AllowGroups` often preferred?

It's easier to manage large teams. You grant or revoke SSH access by changing group membership instead of editing `sshd_config` for every user.

---

### 3. What is `DenyUsers` used for?

It explicitly prevents specific user accounts from logging in via SSH.

---

### 4. Why shouldn't service accounts have SSH access?

Accounts like `postgres`, `mysql`, and `www-data` are intended to run services, not interactive sessions. Allowing SSH access unnecessarily increases the attack surface.

---

### 5. How can you avoid locking yourself out when changing SSH access rules?

- Keep your current SSH session open.
- Validate with `sudo sshd -t`.
- Test a new SSH connection from another terminal before closing the original session.

# Summary

In this lesson, you learned how to control **who** can access your server through SSH.

You now know how to:

- Restrict access with `AllowUsers`
- Manage access using `AllowGroups`
- Block specific accounts with `DenyUsers`
- Deny entire groups with `DenyGroups`
- Build a production-ready SSH access policy

A secure SSH server isn't just about strong authentication—it's also about ensuring that **only the right accounts are allowed to connect**.
