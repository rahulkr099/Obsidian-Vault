# Where is `sshd_config`?

The SSH daemon configuration file is:

```
/etc/ssh/sshd_config
```

Edit it:

```bash
sudo nvim /etc/ssh/sshd_config
```

or

```bash
sudo nano /etc/ssh/sshd_config
```

---

# 1. Disable Root Login

```
PermitRootLogin no
```

Why?

- Prevents direct root SSH access
- Forces administrators to use normal accounts + `sudo`
- Improves auditing

Recommended:

✅ Production

---

# 2. Disable Password Authentication

```
PasswordAuthentication no
```

Why?

Removes the largest attack vector:

```
Brute Force

↓

Passwords

↓

Compromised Server
```

Recommended:

✅ Production

---

# 3. Enable Public Key Authentication

```
PubkeyAuthentication yes
```

Allows:

```
SSH Keys
```

Without this, key authentication won't work.

Recommended:

✅ Always

---

# 4. Disable Empty Passwords

```
PermitEmptyPasswords no
```

This prevents users with blank passwords from logging in.

Recommended:

✅ Always

---

# 5. Restrict Login Attempts

```
MaxAuthTries 3
```

Default is often higher.

Example:

```
Attempt 1

↓

Attempt 2

↓

Attempt 3

↓

Disconnected
```

Recommended:

```
3
```

---

# 6. Reduce Login Timeout

```
LoginGraceTime 30
```

Meaning:

The user has:

```
30 Seconds
```

to authenticate.

If authentication doesn't complete:

```
Connection Closed
```

Recommended:

```
30
```

or

```
30s
```

---

# 7. Limit Concurrent Sessions

```
MaxSessions 2
```

Prevents one SSH connection from opening too many multiplexed sessions.

Recommended:

```
2
```

or

```
5
```

depending on operational needs.

---

# 8. Disable TCP Forwarding (If Unneeded)

```
AllowTcpForwarding no
```

Prevents:

```bash
ssh -L
```

```bash
ssh -R
```

```bash
ssh -D
```

Use:

```
yes
```

only if your workflow requires SSH tunnels.

---

# 9. Disable X11 Forwarding

```
X11Forwarding no
```

Production Linux servers almost never require graphical forwarding.

Recommended:

```
no
```

---

# 10. Limit User Access

Example:

```
AllowUsers rahul deploy
```

or

```
AllowGroups sshusers
```

Only trusted users should have SSH access.

---

# 11. Disable Host-Based Authentication

```
HostbasedAuthentication no
```

Host-based authentication is rarely used today.

Recommended:

```
no
```

---

# 12. Disable Rhosts Authentication

```
IgnoreRhosts yes
```

Legacy `.rhosts` authentication should remain disabled.

Recommended:

```
yes
```

---

# 13. Enable Strict Modes

```
StrictModes yes
```

SSH checks:

- File ownership
- Permissions
- SSH directory security

If something is unsafe:

```
Login Refused
```

Recommended:

```
yes
```

---

# 14. Client Keepalive

```
ClientAliveInterval 300
```

Meaning:

Every:

```
300 Seconds
```

SSH checks whether the client is still connected.

---

# 15. Disconnect Dead Clients

```
ClientAliveCountMax 2
```

After:

```
2 Missed Replies
```

SSH disconnects the session.

This helps clean up abandoned connections.

---

# Example Production Configuration

```
PermitRootLogin no

PasswordAuthentication no
PubkeyAuthentication yes
PermitEmptyPasswords no

MaxAuthTries 3
LoginGraceTime 30

AllowUsers rahul deploy

MaxSessions 2

AllowTcpForwarding no
X11Forwarding no

HostbasedAuthentication no
IgnoreRhosts yes

StrictModes yes

ClientAliveInterval 300
ClientAliveCountMax 2
```

This is an excellent baseline for many Internet-facing Linux servers. Adjust settings like `AllowTcpForwarding` or `MaxSessions` if your operational requirements differ.

---

# Validate Configuration

Never restart SSH blindly.

Check the syntax:

```bash
sudo sshd -t
```

If there is no output:

```
Configuration Valid
```

---

# View Effective Configuration

Instead of reading comments or defaults:

```bash
sudo sshd -T
```

Filter:

```bash
sudo sshd -T | grep password
```

or

```bash
sudo sshd -T | grep permitrootlogin
```

This shows the actual values SSH will use.

---

# Restart SSH

Ubuntu/Debian:

```bash
sudo systemctl restart ssh
```

RHEL/CentOS:

```bash
sudo systemctl restart sshd
```

---

# Test Safely

Never close your current SSH session.

Instead:

Open another terminal:

```bash
ssh user@server
```

Verify:

- Login succeeds
- `sudo` works
- SSH keys work
- Password authentication behaves as expected

Only then close the original session.

# Common Mistakes

## Disabling Passwords Before Testing Keys

Wrong:

```
PasswordAuthentication no

↓

Restart

↓

Locked Out
```

Correct:

```
Install SSH Key

↓

Test SSH Key

↓

Disable Passwords
```

---

## Forgetting `AllowUsers`

If you configure:

```
AllowUsers deploy
```

but you log in as:

```
rahul
```

your login will fail.

---

## Disabling TCP Forwarding Unnecessarily

If your workflow includes:

- Database tunnels
- SSH SOCKS proxies
- Remote debugging

then:

```
AllowTcpForwarding no
```

will break those features.

Choose the setting based on your needs.

---

## Not Validating

Always run:

```bash
sudo sshd -t
```

before restarting the SSH service.

---

# Security Checklist

Before putting a server online, verify:

- ✅ Root login disabled
- ✅ Password authentication disabled (after verifying SSH keys)
- ✅ SSH keys enabled
- ✅ Empty passwords disabled
- ✅ Login attempts limited
- ✅ Login timeout configured
- ✅ Only trusted users/groups allowed
- ✅ X11 forwarding disabled
- ✅ TCP forwarding disabled if not needed
- ✅ Strict modes enabled
- ✅ Keepalive configured
- ✅ Fail2Ban installed and protecting SSH

# Interview Questions

### 1. Why disable root login?

It reduces the attack surface and ensures administrators authenticate with individual accounts before using `sudo`, improving security and auditability.

---

### 2. Why disable password authentication?

Passwords are vulnerable to guessing and brute-force attacks. SSH keys provide much stronger authentication.

---

### 3. What does `StrictModes yes` do?

It tells OpenSSH to verify the ownership and permissions of SSH-related files and directories. If they're insecure, authentication is refused.

---

### 4. What is `MaxAuthTries`?

It limits the number of authentication attempts allowed during a single SSH connection before the server disconnects the client.

---

### 5. Why should you always run `sshd -t` before restarting SSH?

It validates the configuration syntax. Catching errors before restarting helps prevent accidentally breaking remote SSH access.
