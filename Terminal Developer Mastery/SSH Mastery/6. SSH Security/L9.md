# How SSH Creates a Secure Connection

When you run:

```bash
ssh user@server
```

SSH performs several steps:

```
Client

↓

Verify Server Identity

↓

Negotiate Algorithms

↓

Perform Key Exchange

↓

Create Session Key

↓

Encrypt Communication

↓

Authenticate User

↓

Interactive SSH Session
```

Each step uses different cryptographic algorithms.

---

# SSH Has Four Main Cryptographic Components

|Component|Purpose|
|---|---|
|Host Key|Proves the server's identity|
|User Key|Proves your identity|
|Key Exchange (KEX)|Securely creates a shared secret|
|Cipher + MAC|Encrypts and protects the session|

---

# Host Keys

Every SSH server has host keys.

Example:

```
/etc/ssh/

ssh_host_ed25519_key

ssh_host_rsa_key
```

These identify the server.

The first time you connect:

```
The authenticity of host can't be established.
```

SSH asks:

```
Are you sure you want to continue connecting?
```

If you accept:

```
known_hosts
```

stores the server's public host key.

Future connections verify that the server hasn't unexpectedly changed its identity.

---

# User Keys

These are your personal SSH keys.

Example:

```
~/.ssh/

id_ed25519

id_ed25519.pub
```

These authenticate **you** to the server.

---

# Host Key vs User Key

|Host Key|User Key|
|---|---|
|Identifies server|Identifies user|
|Stored on server|Stored on client|
|Prevents man-in-the-middle attacks|Authenticates the user|
|Generated during server setup|Generated by each user|

---

# Ed25519

Modern recommendation:

```bash
ssh-keygen -t ed25519
```

Advantages:

- Small keys
- Fast
- High security
- Resistant to known practical attacks
- Excellent default choice

Current recommendation:

> **Use Ed25519 for new SSH user keys unless you have a compatibility requirement.**

---

# RSA

Generate:

```bash
ssh-keygen -t rsa -b 4096
```

Older recommendation:

```
RSA 2048
```

Current best practice:

```
RSA 3072

or

RSA 4096
```

RSA remains widely supported and is useful for compatibility with older systems.

---

# Ed25519 vs RSA

|Feature|Ed25519|RSA 4096|
|---|---|---|
|Speed|⭐⭐⭐⭐⭐|⭐⭐⭐|
|Key Size|Small|Large|
|Signature Speed|Very Fast|Slower|
|Compatibility|Modern systems|Excellent|
|Recommended|✅ Yes|✅ For compatibility|

---

# Key Exchange (KEX)

Before encryption starts:

Client:

```
"I need to talk securely."
```

Server:

```
"Let's create a secret key."
```

Neither side sends the secret directly.

Instead they perform:

```
Key Exchange
```

Result:

```
Shared Secret
```

Only the client and server know this secret.

---

# Common KEX Algorithms

List supported algorithms:

```bash
ssh -Q kex
```

Typical output:

```
curve25519-sha256

curve25519-sha256@libssh.org

diffie-hellman-group16-sha512

diffie-hellman-group18-sha512
```

Recommended:

- `curve25519-sha256`
- Modern Diffie-Hellman groups with SHA-2

---

# Ciphers

After key exchange, SSH encrypts all traffic.

List supported ciphers:

```bash
ssh -Q cipher
```

Example:

```
aes128-gcm@openssh.com

aes256-gcm@openssh.com

chacha20-poly1305@openssh.com
```

---

# Common Modern Ciphers

### ChaCha20-Poly1305

Advantages:

- Very fast
- Secure
- Excellent on systems without AES hardware acceleration
- Single integrated authenticated encryption algorithm

---

### AES-GCM

Examples:

```
aes128-gcm@openssh.com

aes256-gcm@openssh.com
```

Advantages:

- Hardware accelerated on many CPUs
- Very fast on modern processors
- Widely used

---

# Message Authentication Codes (MACs)

Encryption hides the data.

MACs verify:

```
Was the message modified?
```

List:

```bash
ssh -Q mac
```

Example:

```
hmac-sha2-256

hmac-sha2-512
```

Modern authenticated encryption modes such as ChaCha20-Poly1305 and AES-GCM already provide integrity protection, so separate MAC algorithms may not be used with those ciphers.

---

# Inspect Supported Key Types

Run:

```bash
ssh -Q key
```

Example:

```
ssh-ed25519

ecdsa-sha2-nistp256

ssh-rsa
```

This shows which key algorithms your SSH client supports.

---

# Inspect Server Algorithms

View the negotiated algorithms for a connection:

```bash
ssh -vv user@server
```

Look for lines such as:

```
kex: algorithm: curve25519-sha256

host key algorithm: ssh-ed25519

cipher: chacha20-poly1305@openssh.com
```

This is useful when troubleshooting compatibility issues.

---

# Checking Host Keys

List server host keys:

```bash
ls -l /etc/ssh/ssh_host_*
```

Example:

```
ssh_host_ed25519_key

ssh_host_ed25519_key.pub

ssh_host_rsa_key

ssh_host_rsa_key.pub
```

Display a host key fingerprint:

```bash
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

This helps verify the server's identity.

---

# Choosing Good Algorithms

For most modern Linux servers:

|Component|Recommended|
|---|---|
|User Key|Ed25519|
|Host Key|Ed25519|
|Compatibility Host Key|RSA 3072 or 4096|
|KEX|`curve25519-sha256`|
|Cipher|`chacha20-poly1305@openssh.com` or `aes256-gcm@openssh.com`|

These defaults provide a good balance of security, performance, and compatibility.

---

# Common Mistakes

## Using Weak RSA Keys

Avoid creating new RSA keys with:

```
RSA 1024
```

or

```
RSA 2048
```

if stronger options are practical. Prefer Ed25519 or RSA 3072/4096 for new deployments.

---

## Ignoring Host Key Warnings

Never automatically accept this warning:

```
REMOTE HOST IDENTIFICATION HAS CHANGED!
```

It could indicate:

- Server reinstallation
- Host key rotation
- Connecting to the wrong server
- A potential man-in-the-middle attack

Always investigate before accepting a new host key.

---

## Assuming Bigger Keys Are Always Better

Ed25519 keys are much shorter than RSA keys but remain highly secure due to the underlying cryptographic design.

Shorter does **not** mean weaker.

---

# Security Best Practices

- Use Ed25519 for new SSH keys.
- Keep RSA only when compatibility requires it.
- Verify host key fingerprints before trusting a new server.
- Use modern OpenSSH versions to benefit from secure defaults.
- Remove obsolete algorithms only after confirming client compatibility.

# Interview Questions

### 1. What is the difference between a host key and a user key?

A host key identifies the SSH server, while a user key authenticates a client to the server.

---

### 2. Why is Ed25519 recommended for new SSH keys?

It provides strong security, small key sizes, and excellent performance, making it the preferred default on modern systems.

---

### 3. What is the purpose of key exchange (KEX)?

KEX allows the client and server to securely establish a shared secret used to encrypt the SSH session.

---

### 4. What is `known_hosts` used for?

It stores trusted server host keys so SSH can detect unexpected changes and help prevent man-in-the-middle attacks.

---

### 5. How can you see which algorithms your SSH client supports?

Use:

```bash
ssh -Q key
ssh -Q kex
ssh -Q cipher
ssh -Q mac
```

# Summary

In this lesson, you learned the cryptographic building blocks that make SSH secure:

- Host keys identify servers
- User keys authenticate clients
- Key exchange creates a secure shared secret
- Modern ciphers encrypt traffic
- Integrity protection detects tampering
- Ed25519 is the preferred algorithm for new SSH keys
- `known_hosts` helps verify server identity

You don't need to be a cryptographer to administer SSH, but understanding these components will help you make informed security decisions, troubleshoot compatibility problems, and confidently discuss SSH security in interviews.
