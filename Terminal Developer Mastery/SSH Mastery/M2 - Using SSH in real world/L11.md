# Step 1 — Connect to the Server

If you've configured SSH:

```bash

```

```bash

```

```bash
hostname
```

```bash

```

```bash
pwd
```

# Step 2 — Check Server Health

Before deploying anything:

Memory:

```bash
free -h
```

Disk:

```bash
df -h
```

CPU Load:

```bash
uptime
```

Processes:

```bash
top
```

or

```bash
htop
```

These checks help you catch resource problems before making changes.

---

# Step 3 — Go to the Project

Example:

```bash
cd /var/www/backend
```

or

```bash
cd ~/backend
```

Verify:

```bash
pwd
```

---

# Step 4 — Update Code

Pull the latest changes:

```bash
git pull origin main
```

Check status:

```bash
git status
```

View recent commits:

```bash
git log --oneline -5
```

---

# Step 5 — Install Dependencies

If `package.json` changed:

```bash
npm install
```

or

```bash
npm ci
```

### Which Should You Use?

|Command|Best For|
|---|---|
|`npm install`|Development|
|`npm ci`|Production deployments with a lockfile|

`npm ci` is faster and installs exactly what's in `package-lock.json`.

---

# Step 6 — Restart the Application

Using PM2:

```bash
pm2 restart backend
```

See all applications:

```bash
pm2 list
```

View details:

```bash
pm2 describe backend
```

---

# Step 7 — Verify It's Running

Check status:

```bash
pm2 status
```

Expected:

```
backend   online
```

If it's not online:

Check logs.

---

# Step 8 — Read Logs

Live logs:

```bash
pm2 logs
```

Only backend:

```bash
pm2 logs backend
```

Last 50 lines:

```bash
pm2 logs backend --lines 50
```

Logs are usually your first stop when debugging.

---

# Step 9 — Check the Web Server

If you're using Nginx:

Status:

```bash
sudo systemctl status nginx
```

Restart:

```bash
sudo systemctl restart nginx
```

Reload configuration:

```bash
sudo systemctl reload nginx
```

Reloading is preferred after configuration changes because it avoids dropping active connections.

---

# Step 10 — Check Docker (If Used)

Containers:

```bash
docker ps
```

All containers:

```bash
docker ps -a
```

Logs:

```bash
docker logs container_name
```

Restart:

```bash
docker restart container_name
```

---

# Step 11 — Verify the API

You can test the API directly from the server.

Example:

```bash
curl <http://localhost:5000/health>
```

Expected:

```
OK
```

or

```json
{
  "status": "healthy"
}
```

A health endpoint is a simple way to verify that your application is responding.

# Troubleshooting Scenario

## Users report:

> "The API is down."

You investigate.

### Check PM2

```bash
pm2 status
```

If it's stopped:

```bash
pm2 restart backend
```

---

### Still Broken?

Read logs:

```bash
pm2 logs backend --lines 100
```

Possible error:

```
MongoNetworkError:
Connection refused
```

Now you know to investigate the database connection rather than restarting repeatedly.

---

### Check Memory

```bash
free -h
```

Maybe the server has run out of RAM.

---

### Check Disk

```bash
df -h
```

Maybe the disk is full, preventing writes or logs.

---

### Check Nginx

```bash
sudo systemctl status nginx
```

If Nginx isn't running, users may not be able to reach your application even if Node.js is healthy.

# Using SSH Without Opening a Shell

You don't always need an interactive session.

Restart remotely:

```bash
ssh production "pm2 restart backend"
```

Check uptime:

```bash
ssh production uptime
```

Check Docker:

```bash
ssh production "docker ps"
```

Run a health check:

```bash
ssh production "curl <http://localhost:5000/health>"
```

This style is widely used in automation and CI/CD.

# Common Mistakes

## ❌ Deploying Without Pulling

```bash
pm2 restart backend
```

But you forgot:

```bash
git pull
```

You're still running the old code.

---

## ❌ Forgetting to Restart

You updated the code but didn't restart the application.

The old process keeps serving requests.

---

## ❌ Ignoring Logs

Restarting repeatedly without checking logs often hides the real issue.

Look at the logs first.

---

## ❌ Forgetting to Verify

After deployment, don't assume everything worked.

Check:

```bash
pm2 status
```

and:

```bash
curl <http://localhost:5000/health>
```

# Key Takeaways

- SSH is the foundation of day-to-day backend server management.
- A deployment usually includes pulling code, installing dependencies, restarting services, and verifying the application.
- Logs and health checks are more informative than repeatedly restarting a failing application.
- Many routine tasks can be run directly through `ssh host "command"` for automation.

## Pro Tip ⭐

Since you're building **Node.js/Express backends**, make it a habit to think of every deployment as four phases:

1. **Prepare** — Check server health (`free -h`, `df -h`, `uptime`)
2. **Deploy** — `git pull`, `npm ci`
3. **Activate** — `pm2 restart backend`
4. **Verify** — `pm2 status`, `curl /health`, review logs

Following this sequence consistently reduces deployment mistakes and makes troubleshooting much easier.
