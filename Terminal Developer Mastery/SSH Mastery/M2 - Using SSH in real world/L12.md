# The SSH Troubleshooting Flow

When SSH fails, think in this order:

```
1. Is the server reachable?
        │
        ▼
2. Is SSH listening?
        │
        ▼
3. Is the correct port open?
        │
        ▼
4. Am I using the correct username?
        │
        ▼
5. Am I using the correct SSH key?
        │
        ▼
6. Check verbose logs
```

Don't jump randomly between possible causes.

# Error 1 — Connection Refused

Example:

```
ssh: connect to host 203.0.113.10 port 22:
Connection refused
```

Meaning:

Your computer reached the server, but nothing accepted the SSH connection on that port.

---

## Common Causes

- SSH server (`sshd`) is not running.
- Wrong SSH port.
- SSH service crashed.
- Firewall on the server is rejecting connections.

---

## Check on the Server

If you have console access:

```bash
sudo systemctl status ssh
```

Start it:

```bash
sudo systemctl start ssh
```

Enable it:

```bash
sudo systemctl enable ssh
```

Verify:

```bash
ss -tln | grep :22
```

---

# Error 2 — Connection Timed Out

Example:

```
ssh: connect to host 203.0.113.10 port 22:
Connection timed out
```

Meaning:

Your packets never reached the SSH service.

---

## Possible Causes

- Wrong IP address.
- Firewall blocking port 22.
- Cloud security group not allowing SSH.
- Server powered off.
- Network outage.

---

## First Checks

Can you reach the host?

```bash
ping 203.0.113.10
```

> Note: Some servers intentionally block ICMP (`ping`), so a failed ping does **not** always mean the server is unreachable.

Check the port:

```bash
nc -zv 203.0.113.10 22
```

If the port isn't reachable, investigate network rules or firewall settings.

---

# Error 3 — Permission Denied (Publickey)

Example:

```
Permission denied (publickey)
```

This is probably the most common SSH error.

---

## Meaning

The server received your connection.

It rejected authentication.

---

## Common Causes

- Wrong private key.
- Wrong username.
- Public key not installed on the server.
- Incorrect file permissions.
- SSH agent doesn't have the expected key.

---

## Check Your Key

```bash
ls ~/.ssh
```

Example:

```
id_ed25519
id_ed25519.pub
```

Use it:

```bash
ssh -i ~/.ssh/id_ed25519 ubuntu@203.0.113.10
```

---

## Check Permissions

```bash
chmod 700 ~/.ssh
```

```bash
chmod 600 ~/.ssh/id_ed25519
```

```bash
chmod 644 ~/.ssh/id_ed25519.pub
```

---

## Debug It

```bash
ssh -vvv ubuntu@203.0.113.10
```

Look for lines like:

```
Offering public key:
```

and

```
Authentication succeeded
```

or

```
Permission denied
```

The verbose output often tells you exactly where authentication failed.

---

# Error 4 — Host Key Verification Failed

Example:

```
Host key verification failed.
```

Meaning:

The server's host key doesn't match the one stored in:

```
~/.ssh/known_hosts
```

---

## Why?

Maybe:

- Server reinstalled.
- New VPS created.
- Host keys regenerated.
- Wrong server.
- Possible man-in-the-middle attack.

---

## Fix

If you've verified the server's identity:

```bash
ssh-keygen -R 203.0.113.10
```

Reconnect:

```bash
ssh ubuntu@203.0.113.10
```

SSH will ask whether you trust the new fingerprint.

---

# Error 5 — Could Not Resolve Hostname

Example:

```
Could not resolve hostname production:
Name or service not known
```

Meaning:

SSH couldn't find the server.

---

## Possible Causes

- Typo.
- DNS issue.
- Wrong SSH alias.
- Missing `~/.ssh/config` entry.

---

## Check

View your config:

```bash
cat ~/.ssh/config
```

Verify DNS:

```bash
getent hosts github.com
```

or

```bash
nslookup github.com
```

---

# Error 6 — Broken Pipe

Example:

```
client_loop:
send disconnect:
Broken pipe
```

Usually means:

The network closed an idle connection.

---

## Solution

Use keep-alives:

```
Host *
    ServerAliveInterval 60
    ServerAliveCountMax 3
```

---

# Error 7 — Too Many Authentication Failures

Example:

```
Received disconnect:
Too many authentication failures
```

Meaning:

SSH tried too many keys before the correct one.

---

## Fix

Specify the exact key:

```bash
ssh -i ~/.ssh/company_key server
```

Or restrict key usage:

```bash
ssh -o IdentitiesOnly=yes \
-i ~/.ssh/company_key \
server
```

`IdentitiesOnly=yes` tells SSH to use only the specified identity instead of trying additional keys from your SSH agent.

---

# Error 8 — Wrong Username

Example:

```bash
ssh rahul@203.0.113.10
```

But the server expects:

```bash
ssh ubuntu@203.0.113.10
```

Authentication fails even with the correct key because you're logging in as the wrong user.

---

# The Power of `vvv`

Whenever you're stuck:

```bash
ssh -vvv server
```

Look for:

```
Connecting to...
```

↓

```
Offering public key...
```

↓

```
Authentication succeeded
```

or

```
Permission denied
```

The debug output tells the story of the connection attempt.

---

# Server Logs

If you have access to the server console, check SSH logs.

On Ubuntu:

```bash
sudo journalctl -u ssh
```

Recent entries:

```bash
sudo journalctl -u ssh -n 50
```

These logs often explain why the server rejected a connection.

---

# A Real Debugging Session

Imagine:

```
Permission denied (publickey)
```

Instead of guessing:

Step 1:

```bash
ssh -vvv production
```

↓

Step 2:

See which key SSH offered.

↓

Step 3:

Check:

```bash
ls ~/.ssh
```

↓

Step 4:

Try:

```bash
ssh -i ~/.ssh/id_ed25519 production
```

↓

Step 5:

Success.

This systematic approach is much faster than repeatedly trying random fixes.

# Troubleshooting Cheat Sheet

|Error|Most Likely Cause|First Command|
|---|---|---|
|Connection refused|SSH service not running or wrong port|`systemctl status ssh`|
|Connection timed out|Firewall, security group, wrong IP|`nc -zv HOST 22`|
|Permission denied|Wrong key or username|`ssh -vvv HOST`|
|Host key verification failed|Changed host key|`ssh-keygen -R HOST`|
|Could not resolve hostname|DNS or typo|`getent hosts HOST`|
|Broken pipe|Idle timeout|`ServerAliveInterval 60`|
|Too many authentication failures|Too many keys tried|`-i KEY` + `IdentitiesOnly=yes`|

# Debugging Checklist

Whenever SSH fails:

```
✓ Correct IP?

✓ Correct hostname?

✓ Correct username?

✓ Correct private key?

✓ Correct port?

✓ SSH service running?

✓ Firewall open?

✓ ssh -vvv output checked?

✓ Server logs checked?
```

Print this list or keep it in your notes—it will solve most SSH problems.

# Key Takeaways

- Don't guess; debug systematically.
- `ssh -vvv` is one of the most valuable troubleshooting tools.
- Authentication errors are different from network errors.
- Server logs are just as important as client-side output.
- Most SSH issues can be narrowed down by checking connectivity, authentication, and configuration in order.

Using your local machine:


Observe:

- Which configuration files are read
- Which keys SSH attempts
- Whether authentication succeeds

## Pro Tip ⭐

When someone says, **"SSH isn't working,"** avoid asking vague questions.

Instead, ask these three:

1. **What's the exact error message?**
2. **What command did you run?**
3. **What does `ssh -vvv` show?**

Those answers usually narrow the problem dramatically and are the same questions experienced Linux and DevOps engineers start with.
