# The Problem

Imagine you want to clone a repository.

Option 1:

```bash
git clone <https://github.com/user/backend-api.git>
```

Option 2:

```bash
git clone git@github.com:user/backend-api.git
```

Both download the same repository.

So why are there two methods?

---

# HTTPS Authentication

When using HTTPS, Git communicates over HTTPS.

```
Your Computer
      │
 HTTPS
      │
GitHub
```

Years ago, GitHub allowed username/password authentication.

Today, GitHub requires alternatives such as:

- Personal Access Tokens (PATs)
- Browser-based authentication through tools like Git Credential Manager
- Enterprise authentication methods

For beginners, HTTPS works well and is easy to set up.

---

# SSH Authentication

With SSH:

```bash
git clone git@github.com:user/backend-api.git
```

Authentication happens using your SSH key.

```
Your Computer
      │
 SSH Key
      │
GitHub
```

Your private key never leaves your computer.

GitHub verifies that you own the matching private key.

---

# Real Backend Workflow

Imagine you join a startup.

Every morning you may:

```bash
git pull
```

Create a feature:

```bash
git checkout -b feature/login
```

Commit:

```bash
git commit -m "Add login validation"
```

Push:

```bash
git push
```

If you use HTTPS without a credential helper, you may need to authenticate repeatedly.

With SSH, once your key is configured, Git operations typically happen without additional login prompts.

---

# HTTPS vs SSH

|Feature|HTTPS|SSH|
|---|---|---|
|Easy for beginners|✅|Slightly more setup|
|Uses SSH keys|❌|✅|
|Password required|❌ (PAT/credential helper instead)|❌|
|Good for automation|⚠️|✅|
|Common in professional development|✅|✅ (very common)|

Both methods are valid. SSH is often preferred for long-term development workflows.

---

# How GitHub Knows It's You

Suppose you push code.

```bash
git push origin main
```

Git asks SSH to authenticate.

SSH offers your public key identity.

GitHub checks:

```
Do I have this user's public key?
```

If yes:

```
Authentication successful
```

If no:

```
Permission denied (publickey)
```

This is why adding your public key to GitHub is necessary.

---

# Authentication Flow

```
git push
     │
     ▼
SSH
     │
     ▼
Private Key
     │
     ▼
GitHub
     │
     ▼
Public Key Match?
     │
 ┌───┴────┐
 │        │
Yes       No
 │        │
 ▼        ▼
Push    Permission denied
```

# Why Backend Developers Prefer SSH

### 1. Faster Daily Workflow

No repeated authentication prompts.

Example:

```bash
git push
```

Just works.

---

### 2. Better for Automation

Deployment scripts often use Git.

Example:

```bash
git pull
npm ci
pm2 restart backend
```

SSH works naturally in automated environments where interactive logins are undesirable.

---

### 3. Works Well with Remote Servers

Suppose you're logged into a VPS:

```bash
ssh production
```

Now update your project:

```bash
git pull
```

If the server has the correct SSH key configured, no additional GitHub login is needed.

---

### 4. Widely Used in Open Source

Many open-source contributors configure GitHub SSH once and then work with repositories for months or years without re-authenticating.

---

# When HTTPS Is Still a Good Choice

SSH isn't always the best option.

HTTPS can be preferable when:

- You're using a shared or temporary computer.
- Company policies require HTTPS.
- You're using a managed credential helper that already provides a smooth experience.
- You're making a quick one-time clone and don't want to configure SSH.

Choose the method that fits your environment.

---

# GitHub URLs

HTTPS:

```
<https://github.com/user/backend-api.git>
```

SSH:

```
git@github.com:user/backend-api.git
```

They reference the same repository but use different authentication methods.

# Checking Existing Remotes

Inside a Git repository:

```bash
git remote -v
```

Example output:

```
origin  git@github.com:user/backend-api.git (fetch)
origin  git@github.com:user/backend-api.git (push)
```

Or:

```
origin  <https://github.com/user/backend-api.git> (fetch)
origin  <https://github.com/user/backend-api.git> (push)
```

This tells you whether the repository is currently using HTTPS or SSH.

# Common Mistakes

## ❌ Confusing SSH with Git

Git is the version control system.

SSH is one authentication and transport method that Git can use.

---

## ❌ Expecting SSH to Work Without Adding a Key

Generating an SSH key isn't enough.

You must also upload the **public key** to your GitHub account.

---

## ❌ Sharing Your Private Key

Safe to share:

```
id_ed25519.pub
```

Never share:

```
id_ed25519
```

Your private key should stay on devices you control.

# Key Takeaways

- GitHub supports both HTTPS and SSH authentication.
- SSH uses a public/private key pair instead of passwords.
- Once configured, SSH provides a smooth experience for everyday Git operations.
- Both HTTPS and SSH are valid; the best choice depends on your workflow.
