# SSH Mastery — Module 2, Lesson 3

# Understanding `known_hosts`

One of SSH's most important security features is that it **remembers the servers you've connected to before**.

That memory is stored in:

```
~/.ssh/known_hosts
```

This file protects you from accidentally connecting to the wrong server.

---

# Learning Objectives

By the end of this lesson, you'll understand:

- What `known_hosts` is
- Why SSH remembers servers
- What a host fingerprint is
- How SSH verifies server identity
- How to inspect and manage `known_hosts`

---

# The Problem SSH Solves

Imagine you connect to your production server every day.

```
ssh ubuntu@api.example.com
```

How do you know the server you're talking to today is the **same server** you trusted yesterday?

SSH solves this using **host keys** and the `known_hosts` file.

---

# What is a Host Key?

Every SSH server has its own unique identity.

When the SSH server is installed, it creates a set of **host keys**.

Think of a host key like a server's passport.

```
Server
   │
   ├── Host Key
   └── Unique Identity
```

Every server has different host keys.

---

# First Connection

The first time you connect:

```bash
ssh localhost
```

or

```bash
ssh ubuntu@203.0.113.10
```

SSH cannot know whether this is the correct server.

So it asks you:

```
The authenticity of host
'203.0.113.10'
can't be established.

ED25519 key fingerprint is
SHA256:xxxxxxxx...

Are you sure you want to continue connecting
(yes/no/[fingerprint])?
```

---

# What Happens When You Type "yes"?

SSH stores the server's public host key in:

```
~/.ssh/known_hosts
```

From now on, every connection is checked against this saved identity.

---

# The Verification Process

Every future connection follows this flow:

```
Connect
   │
   ▼
Receive Host Key
   │
   ▼
Compare with known_hosts
   │
 ┌─┴─────────────┐
 │               │
Match         Different
 │               │
 ▼               ▼
Continue      Show Warning
```

If the key matches, SSH continues.

If it doesn't, SSH warns you immediately.

---

# Viewing `known_hosts`

Check if the file exists:

```bash
ls -l ~/.ssh/known_hosts
```

View its contents:

```bash
cat ~/.ssh/known_hosts
```

Example:

```
localhost ssh-ed25519 AAAAC3Nza...
203.0.113.10 ssh-ed25519 AAAAC3Nza...
github.com ssh-ed25519 AAAAC3Nza...
```

Each line represents one trusted server.

---

# Understanding One Entry

Example:

```
github.com ssh-ed25519 AAAAC3NzaC1...
```

Breaking it down:

|Part|Meaning|
|---|---|
|`github.com`|Server name (hostname)|
|`ssh-ed25519`|Host key algorithm|
|`AAAAC3...`|Public host key|

This is **not your SSH key**.

It belongs to the **server**.

---

# Your Key vs Server Key

Many beginners confuse these.

```
Your Laptop
│
├── Private Key
├── Public Key
│
▼
SSH Connection
│
▼
Server
│
├── Host Key
```

Remember:

|Key|Belongs To|
|---|---|
|Private key|You|
|Public key|You|
|Host key|Server|

---

# Why This Matters

Imagine yesterday you trusted:

```
api.example.com
```

Today, an attacker pretends to be that server.

Without verification:

```
You
 │
 ▼
Fake Server
```

You might unknowingly send passwords or commands to the attacker.

With `known_hosts`, SSH notices the identity has changed and warns you.

---

# Host Key Changed

Example warning:

```
@@@@@@@@@@@@@@@@@@@@@@@@@@@@
WARNING:
REMOTE HOST IDENTIFICATION HAS CHANGED!
@@@@@@@@@@@@@@@@@@@@@@@@@@@@
```

SSH refuses to silently trust the new key.

---

# Does This Always Mean an Attack?

No.

Common legitimate reasons include:

- Server reinstalled
- Operating system reinstalled
- SSH host keys regenerated
- New virtual machine replacing the old one

But **never ignore the warning**.

Verify with your server administrator (or yourself, if it's your server).

---

# Removing an Old Entry

Suppose your server was rebuilt.

Remove the old key:

```bash
ssh-keygen -R api.example.com
```

Or using an IP:

```bash
ssh-keygen -R 203.0.113.10
```

Then reconnect.

SSH will ask you to trust the new fingerprint.

---

# Searching for an Entry

Find a specific host:

```bash
ssh-keygen -F github.com
```

Example:

```
# Host github.com found:
```

Useful when your `known_hosts` file grows.

---

# Hashed `known_hosts`

Some systems hide hostnames for privacy.

Instead of:

```
github.com
```

You may see:

```
|1|A7M...
```

These are **hashed hostnames**.

Why?

If someone steals your laptop, they can't easily see which servers you've connected to.

SSH still works normally.

---

# Where Does the Server Get Its Host Key?

On Linux, host keys are typically stored in:

```
/etc/ssh/
```

Example files:

```
ssh_host_ed25519_key
ssh_host_rsa_key
ssh_host_ecdsa_key
```

These are managed by the SSH server (`sshd`) and should not be edited manually.

---

# Real Backend Example

Suppose you deploy your Express API to:

```
api.mycompany.com
```

The first time:

```bash
ssh ubuntu@api.mycompany.com
```

SSH asks you to verify the fingerprint.

After accepting it, every future deployment:

```bash
ssh ubuntu@api.mycompany.com
```

automatically checks that it's connecting to the same trusted server.

# Useful Commands

View the file:

```bash
cat ~/.ssh/known_hosts
```

Check if it exists:

```bash
ls -l ~/.ssh/known_hosts
```

Find a host:

```bash
ssh-keygen -F localhost
```

Remove a host:

```bash
ssh-keygen -R localhost
```

---

# Key Takeaways

- `~/.ssh/known_hosts` stores the identities of trusted SSH servers.
- SSH checks a server's host key every time you connect.
- A changed host key triggers a warning to help protect against impersonation.
- Your SSH key pair identifies **you**; the host key identifies **the server**.
- Use `ssh-keygen -R` to remove outdated host keys when a server has legitimately changed.

## Pro Tip ⭐

As a backend developer, you'll frequently rebuild development servers or create new cloud instances. If you suddenly see:

```
WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!
```

don't immediately delete the entry. First ask yourself:

- Did I recreate or reinstall this server?
- Did its IP address change?
- Did I intentionally regenerate its SSH host keys?

If the answer is **yes**, removing the old entry and trusting the new fingerprint is appropriate. If the answer is **no**, investigate before proceeding.
