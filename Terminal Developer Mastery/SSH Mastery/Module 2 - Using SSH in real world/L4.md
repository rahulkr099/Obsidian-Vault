# Managing Host Keys Safely

In Lesson 3, you learned **what `known_hosts` is**.

Today you'll learn **how to safely manage host keys**—one of the most important security skills when working with production servers.

---

# Learning Objectives

By the end of this lesson, you'll know how to:

- Accept a host key safely
- Verify a host fingerprint
- Remove outdated host keys
- Understand why host keys change
- Avoid common security mistakes

---

# Review: What is a Host Key?

Every SSH server has its own identity.

```
Server
   │
   ├── Host Key
   └── Fingerprint
```

When you connect, the server sends its **public host key**.

Your SSH client checks whether it matches the one stored in:

```
~/.ssh/known_hosts
```

---

# First Connection

Example:

```bash
ssh ubuntu@203.0.113.10
```

SSH responds:

```
The authenticity of host '203.0.113.10'
can't be established.

ED25519 key fingerprint is:

SHA256:AbCdEf123456...

Are you sure you want to continue connecting
(yes/no/[fingerprint])?
```

---

# Should You Type "yes"?

**Only if you're confident you're connecting to the correct server.**

For example:

- ✅ It's your own VPS that you just created.
- ✅ Your cloud provider or administrator gave you the fingerprint.
- ✅ You're connecting to your own `localhost`.

Avoid blindly typing `yes` on unknown or unexpected servers.

---

# What is a Fingerprint?

A fingerprint is a short, readable representation of a host key.

Instead of:

```
AAAAC3NzaC1lZDI1NTE5AAAAIH4...
```

SSH shows:

```
SHA256:AbCdEf123456789...
```

Think of it like a person's fingerprint—short enough to compare, unique enough to identify.

---

# Verifying a Fingerprint

Suppose your cloud provider tells you:

```
Expected fingerprint:

SHA256:AbCdEf123456789...
```

When you connect:

```
ED25519 key fingerprint is:

SHA256:AbCdEf123456789...
```

If they match:

✅ You can trust the server.

If they don't:

❌ Stop and investigate.

---

# What Happens After Acceptance?

When you type:

```
yes
```

SSH saves the server's host key:

```
~/.ssh/known_hosts
```

Next time:

```bash
ssh ubuntu@203.0.113.10
```

SSH silently verifies the key before authenticating you.

---

# Host Key Changed Warning

One day you connect and see:

```
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
WARNING:
REMOTE HOST IDENTIFICATION HAS CHANGED!
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
```

This is one of the most important SSH warnings.

---

# Why Does This Happen?

## Legitimate Reasons

- Reinstalled the operating system
- Recreated the VPS
- Regenerated SSH host keys
- Switched to a replacement server

---

## Suspicious Reasons

- DNS hijacking
- Someone pretending to be your server
- Man-in-the-middle attack

---

# What Should You Do?

Never ignore the warning.

Ask:

1. Did I rebuild this server?
2. Did its IP address change?
3. Did I intentionally replace it?

If **yes**, updating `known_hosts` is expected.

If **no**, investigate before connecting.

---

# Removing an Old Host Key

Remove by hostname:

```bash
ssh-keygen -R api.example.com
```

Remove by IP:

```bash
ssh-keygen -R 203.0.113.10
```

SSH removes only that entry.

---

# Reconnect

Now reconnect:

```bash
ssh ubuntu@203.0.113.10
```

SSH asks again:

```
Are you sure you want to continue connecting?
```

If you've confirmed the new fingerprint is correct:

```
yes
```

The new host key replaces the old one.

---

# Viewing Fingerprints

If you've already trusted a server:

Search for it:

```bash
ssh-keygen -F localhost
```

Example:

```
# Host localhost found:
```

This helps confirm whether SSH already knows a server.

---

# Checking a Server's Fingerprint (Without Connecting)

You can retrieve a server's public host key using:

```bash
ssh-keyscan localhost
```

Example:

```
localhost ssh-ed25519 AAAAC3...
```

> `ssh-keyscan` **does not verify authenticity**. It simply fetches the public host key. You should compare it with a trusted source before deciding to trust it.

---

# Localhost Example

First connection:

```bash
ssh localhost
```

SSH:

```
The authenticity of host
'localhost'
can't be established.
```

Type:

```
yes
```

Now:

```bash
ssh localhost
```

No warning appears because the host key matches the saved entry.

---

# What if You Reinstall Linux?

Reinstalling Linux usually creates **new SSH host keys**.

Result:

```
REMOTE HOST IDENTIFICATION HAS CHANGED!
```

That's expected because it's effectively a new SSH server identity.

---

# Real Backend Example

Suppose your company rebuilds the production server.

Yesterday:

```
api.company.com

↓

Fingerprint A
```

Today:

```
api.company.com

↓

Fingerprint B
```

Before reconnecting:

- Verify with your DevOps team or deployment documentation.
- Confirm that the change was intentional.
- Then update `known_hosts`.

---

# Common Mistakes

## ❌ Blindly Typing "yes"

Never trust an unknown server without checking its identity if verification is available.

---

## ❌ Deleting the Entire File

Avoid:

```bash
rm ~/.ssh/known_hosts
```

This removes trust information for **every** server you've connected to.

Prefer:

```bash
ssh-keygen -R hostname
```

---

## ❌ Ignoring Warnings

SSH warnings exist to protect you.

Read them carefully instead of dismissing them automatically.

---

# Useful Commands

View trusted hosts:

```bash
cat ~/.ssh/known_hosts
```

Find a host:

```bash
ssh-keygen -F localhost
```

Remove a host:

```bash
ssh-keygen -R localhost
```

Fetch a host key:

```bash
ssh-keyscan localhost
```

---

# Practice Exercise

1. Check whether `localhost` is already trusted:

```bash
ssh-keygen -F localhost
```

1. Fetch its host key:

```bash
ssh-keyscan localhost
```

1. Compare the key with the entry in:

```bash
cat ~/.ssh/known_hosts
```

Notice that the stored entry may be hashed depending on your SSH configuration.

---

# Key Takeaways

- A **host key** identifies the **server**.
- A **fingerprint** is a short representation of the host key.
- Always verify a new fingerprint when possible.
- A changed fingerprint is a warning, not automatically an attack.
- Remove outdated entries with `ssh-keygen -R`, not by deleting the whole `known_hosts` file.

## Pro Tip ⭐

As a backend developer, you'll often rebuild development or staging servers. Before deleting an old `known_hosts` entry, ask yourself:

- **Did I intentionally recreate this server?**
- **Am I connecting to the correct hostname or IP?**
- **Can I verify the new fingerprint from a trusted source?**

Making this a habit will help you avoid accidentally trusting the wrong server.
