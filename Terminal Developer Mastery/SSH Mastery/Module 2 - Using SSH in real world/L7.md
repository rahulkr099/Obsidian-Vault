# SSH Session Management

So far you've learned:

- How to connect to servers
- How to run remote commands

Now let's learn how to **manage SSH sessions professionally**.

This is important because backend developers often leave SSH sessions open while deploying applications, monitoring logs, or debugging production servers.

By the end of this lesson, you'll understand:

- Interactive vs non-interactive SSH sessions
- How to safely end a session

- Best practices for production work

# What is an SSH Session?

An SSH session begins when you connect:

```bash
ssh ubuntu@203.0.113.10
```

and ends when you disconnect.

Think of it like a phone call.

```
Dial
  │
  ▼
Connected
  │
  ▼
Conversation
  │
  ▼
Hang Up
```

SSH works the same way.

---

# Interactive Session

Example:

```bash
ssh ubuntu@203.0.113.10
```

Now you receive a shell:

```
ubuntu@server:~$
```

You can run many commands:

```bash
pwd
```

```bash
ls
```

```bash
top
```

```bash
docker ps
```

You remain connected until you disconnect.

---

# Non-Interactive Session

Example:

```bash
ssh ubuntu@203.0.113.10 uptime
```

SSH:

- Connects
- Runs `uptime`
- Prints output
- Disconnects

No shell remains open.

---

# Comparison

|Interactive|Non-Interactive|
|---|---|
|Opens a shell|Runs one command|
|Multiple commands|Single command|
|Manual logout required|Disconnects automatically|
|Great for debugging|Great for automation|

Backend developers use **both** depending on the task.

---

# Ending a Session

The cleanest method:

```bash
exit
```

Output:

```
logout
Connection to server closed.
```

---

# Another Method

Press:

```
Ctrl + D
```

This sends an **End-of-File (EOF)** signal to the shell.

The shell exits, and SSH disconnects.

---

# `exit` vs `Ctrl + D`

|Command|Result|
|---|---|
|`exit`|Explicitly exits the shell|
|`Ctrl + D`|Sends EOF; if the shell is ready for input, it exits|

Both are commonly used.

---

# What Does `Ctrl + C` Do?

This is different.

Suppose you run:

```bash
ping google.com
```

The command continues forever.

Press:

```
Ctrl + C
```

The result:

- `ping` stops.
- Your SSH session **stays connected**.

---

# Summary

|Shortcut|Effect|
|---|---|
|`Ctrl + C`|Stop current command|
|`Ctrl + D`|Exit current shell|
|`exit`|Exit current shell|

This distinction is very important.

---

# What Happens if Wi-Fi Disconnects?

Imagine:

```
Laptop
   │
Wi-Fi Lost
   │
SSH Connection
   │
Server
```

Your SSH session is interrupted.

Typical message:

```
Connection to server closed.
```

or

```
Broken pipe
```

The SSH client exits.

---

# What Happens to Running Commands?

It depends.

Suppose you're running:

```bash
npm install
```

If the SSH session dies unexpectedly, the command often stops as well because it was attached to your terminal.

Some programs continue running, while many interactive commands terminate. Later in this course, you'll learn tools like **tmux**, **screen**, **nohup**, and **systemd** that keep important processes running even if your SSH session ends.

You can open several terminal windows.

Terminal 1:


Terminal 2:

```bash

```

Terminal 3:

# Verify Active User

Inside an SSH session:

```bash
whoami
```

Check where you are:

```bash
pwd
```

Check the server:

```bash
hostname
```

These commands help confirm you're connected to the correct machine.

---

# Check Logged-In Users

On the server:

```bash
who
```

Example:

```
ubuntu pts/0
ubuntu pts/1
```

This shows active login sessions.

---

# Check Your Login History

Run:

```bash
last
```

Example:

```
ubuntu pts/0 ...
```

Useful for auditing access.

---

# Check Current Session Information

Run:

```bash
w
```

Example:

```
USER     TTY
ubuntu   pts/0
```

This displays:

- Logged-in users
- Session start time
- Running commands
- System load

# Real Backend Workflow

Imagine you're deploying your Node.js application.

Interactive session:

```bash

```

Run:

```bash
git pull
```

```bash
npm install
```

```bash
pm2 restart backend
```

```bash
pm2 logs
```

When finished:

```bash

```

This is a typical production maintenance session.

# Best Practices

## ✅ Log Out When Finished

Don't leave unnecessary SSH sessions open.

Use:

```bash
exit
```

---

## ✅ Verify the Server

Before making changes:

```bash
hostname
```

It's surprisingly easy to confuse staging and production servers.

---

## ✅ Verify the User

Run:

```bash
whoami
```

Make sure you're using the expected account.

---

## ✅ Avoid Running Long Tasks Without Planning

If you're starting a long-running operation (large deployment, backup, log monitoring), think about what should happen if your SSH connection drops.

Later modules will introduce tools that make these tasks much safer.

---

# Common Mistakes

## ❌ Closing the Terminal Window

If you simply close the terminal without exiting, your SSH session is abruptly terminated.

Prefer:

```bash
exit
```

---

## ❌ Confusing `Ctrl + C` and `Ctrl + D`

Remember:

- `Ctrl + C` → Stop the running command.
- `Ctrl + D` → Exit the shell.

---

## ❌ Forgetting Which Server You're On

Always verify:

```bash
hostname
```

before running important commands.

---

# Key Takeaways

- Interactive sessions stay open until you disconnect.
- Non-interactive sessions execute one command and exit automatically.
- `exit` and `Ctrl + D` end the shell.
- `Ctrl + C` stops the current command but does **not** disconnect SSH.
- Always verify the server and user before making production changes.

## Pro Tip ⭐

One of the easiest ways to make a costly mistake is to forget **which server you're connected to**. Many experienced backend engineers run:

```bash
hostname
pwd
whoami
```

immediately after logging in. Those three commands take only a second and can prevent deploying code to the wrong machine or modifying the wrong environment.
