# Why Logging Matters

Imagine a monitoring script that runs every 5 minutes.

Without logs:

```text
Script failed.
```

Questions you can't answer:

- When did it fail?
    
- Why did it fail?
    
- Which website failed?
    
- How many times did it fail?
    

---

With logs:

```text
2026-07-27 09:00:02 INFO Website OK
2026-07-27 09:05:01 ERROR Timeout
2026-07-27 09:10:01 INFO Website OK
```

Now you know exactly what happened.

---

# What is a Log?

A **log** is simply a file that records events.

Example:

```text
monitor.log
```

Contents:

```text
2026-07-27 09:00:00 Website UP
2026-07-27 09:05:00 Website DOWN
2026-07-27 09:10:00 Website UP
```

---

# Writing to a Log

Append a message:

```bash
echo "Website checked" >> monitor.log
```

View the log:

```bash
cat monitor.log
```

---

# Add Timestamps

Never log without a timestamp.

```bash
echo "$(date): Website checked" >> monitor.log
```

Example:

```text
Mon Jul 27 18:30:01 IST 2026: Website checked
```

---

# Better Timestamp Format

Use ISO-style timestamps:

```bash
date +"%Y-%m-%d %H:%M:%S"
```

Example:

```text
2026-07-27 18:30:01
```

Log entry:

```bash
echo "$(date +"%Y-%m-%d %H:%M:%S") Website OK"
```

Output:

```text
2026-07-27 18:30:01 Website OK
```

---

# Log Levels

Professional applications categorize messages.

|Level|Purpose|
|---|---|
|DEBUG|Detailed troubleshooting|
|INFO|Normal events|
|WARNING|Something unusual|
|ERROR|Operation failed|
|CRITICAL|Serious failure|

Example:

```text
INFO Server started

WARNING High response time

ERROR Connection failed

CRITICAL Database unavailable
```

---

# Create a Logging Function

Instead of repeating code:

```bash
echo "$(date) Website UP"
```

Create a reusable function:

```bash
log() {

    LEVEL="$1"

    MESSAGE="$2"

    echo "$(date +"%Y-%m-%d %H:%M:%S") [$LEVEL] $MESSAGE"

}
```

Use it:

```bash
log INFO "Website started"

log ERROR "Connection failed"
```

Output:

```text
2026-07-27 18:30:01 [INFO] Website started

2026-07-27 18:30:05 [ERROR] Connection failed
```

---

# Save Logs to a File

```bash
log() {

    LEVEL="$1"

    MESSAGE="$2"

    echo "$(date +"%Y-%m-%d %H:%M:%S") [$LEVEL] $MESSAGE" >> monitor.log

}
```

# Check Exit Status

Every Linux command returns an exit status.

Example:

```bash
curl https://example.com

echo $?
```

Output:

```text
0
```

Meaning:

Success.

---

Example failure:

```bash
curl http://invalid-domain.example

echo $?
```

Output:

```text
6
```

A non-zero exit status indicates an error.

---

# Handle Errors

Instead of assuming success:

```bash
curl "$URL"
```

Check it:

```bash
if curl --fail -s "$URL" >/dev/null
then
    log INFO "Website reachable"
else
    log ERROR "Website unavailable"
fi
```

---

# Exit the Script

Example:

```bash
if ! command -v curl >/dev/null
then

    echo "curl missing"

    exit 1

fi
```

Exit codes:

|Code|Meaning|
|---|---|
|0|Success|
|1|General error|
|2|Misuse of command|
|Other|Program-specific error|

---

# Stop on Errors

A useful Bash option:

```bash
set -e
```

Now the script stops immediately if a command fails.

Example:

```bash
#!/bin/bash

set -e

cp file1 file2

curl https://example.com

echo "Finished"
```

If `curl` fails, `"Finished"` is never printed.

---

# Treat Undefined Variables as Errors

```bash
set -u
```

Example:

```bash
echo "$USERNAME"
```

If `USERNAME` doesn't exist, the script exits instead of continuing with an empty value.

---

# Catch Pipeline Failures

Normally:

```bash
curl ... | grep ...
```

may appear successful even if `curl` fails.

Enable:

```bash
set -o pipefail
```

Now the entire pipeline fails if any command in it fails.

---

# Recommended Safety Settings

Many Bash scripts start with:

```bash
#!/bin/bash

set -euo pipefail
```

Meaning:

- `-e` → Exit on errors.
    
- `-u` → Error on undefined variables.
    
- `pipefail` → Detect pipeline failures.
    

---

# Debugging Scripts

Enable execution tracing:

```bash
bash -x monitor.sh
```

or inside the script:

```bash
set -x
```

Example output:

```text
+ URL=https://example.com

+ curl https://example.com

+ STATUS=200
```

Disable tracing:

```bash
set +x
```

---

# Redirect Errors

Standard error:

```bash
2>
```

Example:

```bash
curl invalid-url 2> errors.log
```

Append:

```bash
2>> errors.log
```

Redirect everything:

```bash
command > output.log 2>&1
```

---

# Log Both Success and Failure

```bash
STATUS=$(curl -s \
-o /dev/null \
-w "%{http_code}" \
https://example.com)

if [ "$STATUS" = "200" ]
then

    log INFO "Website healthy"

else

    log ERROR "HTTP $STATUS"

fi
```

---

# Rotate Logs

Instead of one huge log:

```text
monitor.log
```

Rename periodically:

```bash
mv monitor.log monitor-2026-07-27.log
```

Create a new log:

```bash
touch monitor.log
```

For production systems, Linux commonly uses **logrotate** to automate this process.

---

# Separate Error Log

```
logs/

├── monitor.log

├── error.log

└── access.log
```

This separation makes troubleshooting easier.

---

# Complete Example

```bash
#!/bin/bash

set -euo pipefail

LOGFILE="monitor.log"

log() {

    LEVEL="$1"

    MESSAGE="$2"

    echo "$(date +"%Y-%m-%d %H:%M:%S") [$LEVEL] $MESSAGE" >> "$LOGFILE"

}

URL="https://example.com"

if curl --fail -s "$URL" >/dev/null
then

    log INFO "Website reachable"

else

    log ERROR "Website unavailable"

fi
```

# Common Mistakes

❌ Logging without timestamps.

Bad:

```text
Website DOWN
```

Good:

```text
2026-07-27 18:40:01 [ERROR] Website DOWN
```

---

❌ Ignoring exit codes.

Always verify that important commands succeeded before continuing.

---

❌ Mixing normal output with errors.

Separate logs make debugging much easier.

---

❌ Not using `pipefail`.

Without it:

```bash
curl bad-url | grep title
```

may hide failures from earlier commands.

# Real-World Backend Example

Imagine your backend monitoring service runs every minute.

A healthy log might look like:

```text
2026-07-27 09:00:01 [INFO] Health check started
2026-07-27 09:00:01 [INFO] HTTP 200
2026-07-27 09:00:01 [INFO] Response time: 0.14s
```

If something goes wrong:

```text
2026-07-27 09:05:01 [ERROR] HTTP 503
2026-07-27 09:05:01 [WARNING] Response time exceeded threshold
```

These logs make troubleshooting much faster.

---

# Best Practices

- Use timestamps in every log entry.
    
- Include log levels (`INFO`, `WARNING`, `ERROR`).
    
- Check exit codes after important commands.
    
- Start production Bash scripts with:
    

```bash
#!/bin/bash
set -euo pipefail
```

- Use `bash -x` when debugging.
    
- Rotate logs instead of letting them grow indefinitely.

- `bash -x` is invaluable for debugging.
    
- Good logging and error handling are essential for production automation.

# 💡 Backend Engineer Tip

Professional Bash scripts often begin with a standard template:

```bash
#!/bin/bash

set -euo pipefail

LOGFILE="app.log"

log() {
    local level="$1"
    local message="$2"

    echo "$(date +"%Y-%m-%d %H:%M:%S") [$level] $message" >> "$LOGFILE"
}
```

This gives you:

- A predictable starting point
    
- Safer error handling
    
- Consistent logging
    
- Reusable functions
    

You'll find this pattern in many real-world deployment scripts, CI/CD pipelines, and Linux automation projects.
