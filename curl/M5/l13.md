# Step 7 — Download API Response

```bash
download_api() {

    local url="$1"

    local outfile="$2"

    curl \
        --max-time "$TIMEOUT" \
        -s \
        -o "$outfile" \
        "$url"

}
```

---

# Step 8 — Get Status and Time Together

Instead of making two requests:

```bash
curl -o /dev/null ...

curl -o /dev/null ...
```

Use one:

```bash
curl \
-s \
-o response.json \
-w "%{http_code}|%{time_total}"
```

Example output:

```text
200|0.182
```

Split it:

```bash
STATUS=$(echo "$RESULT" | cut -d'|' -f1)

TIME=$(echo "$RESULT" | cut -d'|' -f2)
```

---

# Step 9 — Compare Responses

Suppose yesterday's response:

```text
previous/users.json
```

Today's response:

```text
current.json
```

Compare:

```bash
diff previous/users.json current.json
```

No output:

```text
No changes
```

Differences:

```text
API changed
```

---

# Step 10 — Save Latest Response

```bash
cp current.json previous/users.json
```

Now the next execution compares against the latest version.

# Detecting Changes

Suppose the previous response:

```json
{
  "version": 1
}
```

Current response:

```json
{
  "version": 2
}
```

`diff` immediately detects the change.

This is useful for:

- Configuration APIs
    
- Feature flags
    
- Deployment status
    
- Health endpoints

Your monitor can verify both:

- HTTP status is `200`

# Common Mistakes

❌ Making multiple requests for the same API.

Instead of:

```bash
curl ...
curl ...
```

collect multiple metrics in one request:

```bash
curl \
-s \
-o response.json \
-w "%{http_code}|%{time_total}"
```

---

❌ Comparing raw JSON.

Whitespace or key order may differ.

Later, you'll learn to normalize JSON with `jq` before comparing.

---

❌ Assuming `200` means everything is fine.

Some APIs return:

```json
{
  "status": "error"
}
```

while still returning HTTP `200`.

Whenever possible, validate both the HTTP status and important JSON fields.

---

❌ Forgetting timeouts.

Always use:

```bash
--max-time 10
```

# Best Practices

- Keep configuration separate.
    
- Use one `curl` request per API.
    
- Log every execution.
    
- Compare responses carefully.
    
- Validate JSON when possible.
    
- Monitor both availability and correctness.

# 💡 Backend Engineer Tip

As you move into backend development, you'll frequently encounter **health endpoints** exposed by frameworks and infrastructure:

- Express.js: custom `/health` route
    
- Spring Boot: `/actuator/health`
    
- ASP.NET Core: `/health`
    
- Kubernetes: `livenessProbe` and `readinessProbe`
    
- Docker: `HEALTHCHECK`
    

A lightweight Bash + `curl` monitor is an excellent way to understand how these systems work before using full monitoring platforms like Prometheus or Grafana. It also makes a practical portfolio project because it demonstrates Linux, Bash, HTTP, and automation skills together.
