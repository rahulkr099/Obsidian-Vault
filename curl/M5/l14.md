# 1. Use Variables Instead of Hardcoding

❌ Bad

```bash
curl https://api.example.com/users
```

✅ Better

```bash
API_URL="https://api.example.com/users"

curl "$API_URL"
```

Benefits:

- Easier to update
    
- More readable
    
- Reusable
    

---

# 2. Always Quote Variables

❌ Bad

```bash
curl $URL
```

If `$URL` contains spaces or special characters, the command may break.

✅ Good

```bash
curl "$URL"
```

Always quote variables unless you specifically need word splitting.

---

# 3. Use `set -euo pipefail`

At the beginning of production Bash scripts:

```bash
#!/bin/bash

set -euo pipefail
```

Meaning:

|Option|Purpose|
|---|---|
|`-e`|Stop on command failure|
|`-u`|Error on undefined variables|
|`pipefail`|Fail if any command in a pipeline fails|

---

# 4. Check Dependencies

Don't assume required tools exist.

```bash
command -v curl >/dev/null 2>&1 || {

    echo "curl is required."

    exit 1

}
```

Also check for tools like:

- `jq`
    
- `awk`
    
- `sed`
    
- `grep`
    

---

# 5. Use One `curl` Request

❌ Inefficient

```bash
curl ...

curl ...
```

✅ Better

```bash
curl \
-s \
-o response.json \
-w "%{http_code}|%{time_total}"
```

Collect multiple metrics with a single request.

---

# 6. Set Timeouts

Never allow scripts to hang forever.

```bash
curl \
--max-time 10 \
https://example.com
```

Useful timeout options:

```bash
--connect-timeout 5
```

Limits the connection phase.

```bash
--max-time 10
```

Limits the total request time.

---

# 7. Retry Temporary Failures

Transient network failures happen.

```bash
curl \
--retry 3 \
--retry-delay 2 \
https://example.com
```

This retries up to three times with a two-second delay.

---

# 8. Fail on HTTP Errors

By default, `curl` may exit successfully even if the server returns `404`.

Use:

```bash
curl --fail https://example.com
```

This makes HTTP 4xx and 5xx responses return a failure exit status.

---

# 9. Keep Configuration Separate

Project layout:

```text
project/

├── monitor.sh
├── config.sh
├── sites.txt
├── logs/
└── reports/
```

Instead of changing the script, update configuration files.

---

# 10. Separate Code into Functions

❌ Bad

One large 500-line script.

✅ Better

```bash
log() { ... }

check_site() { ... }

generate_report() { ... }

main() { ... }

main
```

Each function should have one responsibility.

---

# 11. Use Meaningful Names

❌ Bad

```bash
x=10
```

✅ Better

```bash
TIMEOUT=10
```

Readable names make maintenance much easier.

---

# 12. Use Absolute Paths in Cron

❌ Bad

```bash
python script.py
```

✅ Good

```bash
/usr/bin/python3 /home/rahul/script.py
```

Likewise for shell scripts:

```bash
/bin/bash /home/rahul/monitor.sh
```

Cron uses a minimal environment.

---

# 13. Log Everything Important

Example:

```text
2026-07-27 21:00:01 [INFO] Monitoring started

2026-07-27 21:00:02 [INFO] Google OK

2026-07-27 21:00:03 [ERROR] GitHub Timeout

2026-07-27 21:00:04 [INFO] Monitoring completed
```

Good logs make debugging much easier.

---

# 14. Use Log Levels

Recommended levels:

```text
DEBUG
INFO
WARNING
ERROR
CRITICAL
```

Don't log everything as `INFO`.

---

# 15. Keep Secrets Out of Scripts

❌ Never do this:

```bash
API_KEY="abcd1234"
```

Instead:

```bash
API_KEY="$MY_API_KEY"
```

Set the environment variable before running the script:

```bash
export MY_API_KEY="your_api_key_here"
```

For larger projects, use a `.env` file with appropriate permissions or a dedicated secret manager.

---

# 16. Respect API Rate Limits

Bad:

```bash
while true
do

    curl ...

done
```

Better:

```bash
while true
do

    curl ...

    sleep 60

done
```

Read the API documentation to understand its rate limits.

---

# 17. Validate Input

Check that required files exist:

```bash
if [ ! -f sites.txt ]
then

    echo "sites.txt not found."

    exit 1

fi
```

Validate user input before using it.

---

# 18. Handle Interruptions

Clean up temporary files when the script exits:

```bash
cleanup() {

    rm -f current.json

}

trap cleanup EXIT
```

The `cleanup` function runs automatically when the script exits.

---

# 19. Use ShellCheck

Install:

```bash
sudo apt install shellcheck
```

Analyze your script:

```bash
shellcheck monitor.sh
```

It finds:

- Quoting mistakes
    
- Unused variables
    
- Common Bash pitfalls
    
- Potential bugs
    

---

# 20. Format Your Code

Good:

```bash
if [ "$STATUS" = "200" ]
then

    log INFO "Healthy"

else

    log ERROR "Failed"

fi
```

Readable code is easier to debug and maintain.

# Project Checklist

Before using a script in production:

- ✅ Uses `set -euo pipefail`
    
- ✅ Variables are quoted
    
- ✅ Timeouts are configured
    
- ✅ Retries are configured
    
- ✅ Logging is enabled
    
- ✅ Errors are handled
    
- ✅ Configuration is separated
    
- ✅ Dependencies are checked
    
- ✅ Secrets are not hardcoded

# Performance Tips

Instead of:

```bash
curl ...
curl ...
curl ...
```

Prefer:

- One request with multiple `-w` variables.
    
- Reusing downloaded data.
    
- Avoiding duplicate network requests.
    
- Using `HEAD` requests (`curl -I`) when only headers are needed.
    

---

# Security Tips

Always:

- Use HTTPS.
    
- Verify TLS certificates (don't use `-k` unless absolutely necessary for testing).
    
- Protect API keys.
    
- Use least-privilege credentials.
    
- Keep `curl` updated.
    

Avoid:

```bash
curl -k
```

except in controlled testing environments, because it skips certificate verification.

This helps others (and your future self) understand the project.

# Common Mistakes

❌ Hardcoding secrets.

Use environment variables or secret managers.

---

❌ Ignoring exit codes.

Always check whether critical commands succeeded.

---

❌ Skipping timeouts.

A single hanging request can block an entire automation pipeline.

---

❌ Using `curl -k` in production.

This disables certificate verification and weakens security.

---

❌ Not documenting the project.

A short README can save a lot of time later.

---

# Best Practices Summary

- Write small, focused functions.
    
- Separate configuration from code.
    
- Use safe Bash defaults.
    
- Quote variables.
    
- Log meaningful events.
    
- Handle failures gracefully.
    
- Test before scheduling.
    
- Keep secrets out of source code.
    
- Validate inputs.
    
- Document your work.

# 💡 Backend Engineer Tip

Since you're aiming for **backend engineering**, try to follow these habits in every Bash project:

1. **Lint** your scripts with `shellcheck`.
    
2. **Format** your code consistently.
    
3. **Document** how to run the project in a `README.md`.
    
4. **Version control** everything with Git (except logs, reports, and secrets).
    
5. **Think about failure cases first**—network outages, timeouts, invalid input, and missing dependencies.
    

These habits are just as valuable as knowing the commands themselves, and they'll transfer directly to larger projects in languages like JavaScript, Go, Python, or Java.
