# What is API Polling?

API polling is the process of repeatedly sending requests to an API to check whether something has changed.

Example:

```text
Program
   │
   ├── GET /status
   │
   ├── Wait 30 seconds
   │
   ├── GET /status
   │
   ├── Wait 30 seconds
   │
   └── Repeat
```

# Basic Polling

Request an API:

```bash
curl -s https://api.example.com/status
```

Repeat it:

```bash
while true
do
    curl -s https://api.example.com/status

    sleep 5
done
```

Explanation:

```text
while true
      ↓
Request API
      ↓
Wait 5 seconds
      ↓
Repeat forever
```

Stop with:

```text
Ctrl + C
```

---

# Why Use `sleep`?

Without `sleep`:

```bash
while true
do
    curl -s https://api.example.com/status
done
```

This sends **thousands of requests per second**, which can:

- Overload the API
    
- Trigger rate limits
    
- Get your IP temporarily blocked
    

Always pause between requests unless the API explicitly supports higher request rates.

# Save Responses

```bash
curl -s https://api.example.com/status > current.json
```

Now you have:

```text
current.json
```

---

# Compare Responses

Suppose you already have:

```text
previous.json
```

Download the newest response:

```bash
curl -s https://api.example.com/status > current.json
```

Compare:

```bash
diff previous.json current.json
```

If there is no output:

```text
No changes
```

If differences exist:

```text
API changed
```

---

# Automating Comparison

```bash
if diff previous.json current.json >/dev/null
then
    echo "No changes"
else
    echo "API updated"
fi
```

---

# Update the Stored Copy

After checking:

```bash
mv current.json previous.json
```

Now the next run compares against the latest version.

---

# Complete Polling Script

```bash
#!/bin/bash

URL="https://api.example.com/status"

curl -s "$URL" > current.json

if [ -f previous.json ]; then
    if diff previous.json current.json >/dev/null; then
        echo "No changes."
    else
        echo "API updated!"
    fi
fi

mv current.json previous.json
```

# Check HTTP Status

Sometimes only the HTTP status matters.

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://example.com
```

Output:

```text
200
```

Possible responses:

|Code|Meaning|
|---|---|
|200|Success|
|201|Created|
|204|No Content|
|301|Redirect|
|400|Bad Request|
|401|Unauthorized|
|403|Forbidden|
|404|Not Found|
|500|Internal Server Error|

# Check Response Time

```bash
curl -s \
-o /dev/null \
-w "Time: %{time_total}s\n" \
https://example.com
```

Example:

```text

```

# Monitor Status Code

```bash
STATUS=$(curl -s -o /dev/null -w "%{http_code}" https://example.com)

if [ "$STATUS" = "200" ]; then
    echo "Website is healthy"
else
    echo "Problem detected"
fi
```

# Poll JSON APIs

Suppose the API returns:

```json
    "status": "running",
```

# Poll Multiple APIs

```bash
for url in \
https://example1.com \

https://example3.com

    curl -I "$url"

```

---

# Retry Failed Requests

```bash
curl --retry 3 https://example.com
```

Retry with a delay:

```bash
curl \
--retry 5 \
--retry-delay 2 \
https://example.com
```

This retries up to five times, waiting two seconds between attempts.

---

# Timeout Protection

Don't let scripts hang forever.

```bash
curl --max-time 10 https://example.com
```

The request stops after 10 seconds if no response is received.

---

# Fail on HTTP Errors

Normally, `curl` exits successfully even if a server returns `404`.

Use:

```bash
curl --fail https://example.com
```

Now `curl` exits with a non-zero status for HTTP errors (4xx and 5xx), making it easier to detect failures in scripts.

# Common Mistakes

❌ Polling too frequently.

```bash
sleep 0
```

This can overload APIs and violate rate limits.

✔ Choose an interval that matches the expected update frequency (for example, every 30 seconds, 1 minute, or 5 minutes).

---

❌ Ignoring exit codes.

Instead of only reading the output, also check whether the command succeeded:

```bash
if curl --fail -s https://example.com >/dev/null
then
    echo "Success"
else
    echo "Request failed"
fi
```

---

❌ Comparing formatted JSON.

If the API changes whitespace or key ordering, `diff` may show changes even when the data is effectively the same. Later, you'll learn to use `jq` to compare specific fields instead.

Imagine monitoring your own backend API:

```text
https://api.myapp.com/health
```

Every minute:

1. Send a request.

3. Measure response time.

5. Log failures.
    
6. Alert if something changes.

---

# Best Practices

- Always include a delay between requests.
    
- Respect API rate limits.
    
- Set sensible timeouts.
    
- Use retries only for temporary failures.
    
- Log important events with timestamps.
    
- Compare only the data you care about.

## 💡 Backend Engineer Tip

A simple monitoring pipeline for a production backend often looks like this:

```bash
#!/bin/bash

URL="https://api.example.com/health"

STATUS=$(curl --fail -s -o /dev/null -w "%{http_code}" "$URL")
TIME=$(curl --fail -s -o /dev/null -w "%{time_total}" "$URL")

echo "$(date): Status=$STATUS ResponseTime=${TIME}s"
```

This combines concepts you've already learned:

- `curl` → Send the request.
    
- Variables → Store results.
    
- `date` → Add timestamps.
    
- Shell scripting → Automate monitoring.
    

In the next lesson, you'll expand this into a reusable website monitoring tool that checks availability, performance, and reliability automatically.
