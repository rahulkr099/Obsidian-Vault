# Module 6 — Lesson 11: Debugging HTTPS Problems ⭐⭐⭐⭐⭐

In production, one of the most valuable backend skills is **debugging HTTPS issues**.

When an API call fails, don't immediately assume it's your code.

It could be:

- Expired certificate
    
- TLS version mismatch
    
- Wrong hostname
    
- Invalid CA
    
- Proxy issues
    
- mTLS configuration
    
- DNS problems
    

This lesson teaches you how professionals troubleshoot these problems using `curl` and `openssl`.

---

# Learning Objectives

By the end of this lesson, you'll be able to:

- Debug HTTPS connections with `curl`.
    
- Read verbose TLS output.
    
- Use `curl --trace`.
    
- Inspect TLS handshakes.
    
- Diagnose certificate problems.
    
- Debug mTLS issues.
    
- Troubleshoot common HTTPS failures.
    

---

# The Debugging Mindset

When HTTPS fails, ask these questions:

1. Can I reach the server?
    
2. Is DNS resolving correctly?
    
3. Is the TLS handshake successful?
    
4. Is the certificate valid?
    
5. Does the hostname match?
    
6. Is the server requesting a client certificate?
    
7. Is the HTTP request correct?
    

This step-by-step approach saves time.

---

# `curl -v`

The first debugging tool:

```bash
curl -v https://example.com
```

Verbose mode shows:

- DNS resolution
    
- TCP connection
    
- TLS handshake
    
- Certificate details
    
- HTTP request
    
- HTTP response
    

---

# Example Output

```text
* Host example.com:443 resolved
* Connected to example.com
* TLSv1.3
* Server certificate:
* subject: CN=example.com
* issuer: Let's Encrypt
> GET / HTTP/1.1
< HTTP/1.1 200 OK
```

This tells you the request reached the server successfully.

---

# `curl -vv`

Extra verbosity:

```bash
curl -vv https://example.com
```

Depending on the TLS backend (OpenSSL, Schannel, Secure Transport, etc.), this may reveal additional debugging information.

---

# Trace Mode

For even more detail:

```bash
curl --trace trace.log https://example.com
```

Everything is written to:

```text
trace.log
```

Useful when:

- Investigating difficult bugs
    
- Sharing diagnostics
    
- Comparing requests
    

---

# Human-Readable Trace

```bash
curl --trace-ascii trace.log https://example.com
```

ASCII output is often easier to read than the default binary trace.

---

# Timing Information

Measure the request:

```bash
curl \
-w "\nDNS: %{time_namelookup}\nConnect: %{time_connect}\nTLS: %{time_appconnect}\nTotal: %{time_total}\n" \
-o /dev/null \
-s \
https://example.com
```

Example:

```text
DNS: 0.012
Connect: 0.041
TLS: 0.083
Total: 0.120
```

This helps identify where time is being spent.

---

# TLS Handshake Time

```text
time_appconnect
```

Measures:

```text
TCP Connected

↓

TLS Negotiation

↓

Secure Connection Ready
```

If this value is unusually high, investigate:

- Network latency
    
- Certificate chain size
    
- Server performance
    

---

# Using OpenSSL

One of the most useful commands:

```bash
openssl s_client -connect example.com:443
```

Displays:

- TLS handshake
    
- Certificate chain
    
- Cipher
    
- Verification result
    

---

# Successful Verification

Look for:

```text
Verify return code: 0 (ok)
```

Anything else indicates a problem.

---

# Check Certificate Expiration

```bash
openssl s_client -connect example.com:443 </dev/null \
2>/dev/null \
| openssl x509 -noout -enddate
```

Example:

```text
notAfter=Jan 1 2027
```

---

# View Certificate Subject

```bash
openssl s_client -connect example.com:443 </dev/null \
2>/dev/null \
| openssl x509 -noout -subject
```

---

# View Issuer

```bash
openssl s_client -connect example.com:443 </dev/null \
2>/dev/null \
| openssl x509 -noout -issuer
```

---

# Hostname Problems

Example:

You visit:

```text
https://api.example.com
```

Certificate:

```text
example.org
```

Result:

```text
hostname mismatch
```

The certificate doesn't cover the requested hostname.

---

# Expired Certificate

Example error:

```text
certificate has expired
```

Fix:

Renew the certificate.

---

# Unknown CA

Error:

```text
unable to get local issuer certificate
```

Possible causes:

- Missing intermediate certificate
    
- Private CA not trusted
    
- Incorrect CA bundle
    

---

# Self-Signed Certificate

Example:

```text
self signed certificate
```

Development:

```bash
curl --cacert my-ca.crt https://localhost
```

Avoid:

```bash
curl -k https://localhost
```

except for short-lived testing.

---

# TLS Version Mismatch

Older server:

```text
TLS 1.0
```

Modern client:

```text
TLS 1.3
```

Handshake may fail because the client and server cannot agree on a supported version.

---

# Force a TLS Version

Testing:

```bash
curl --tlsv1.2 https://example.com
```

or

```bash
curl --tlsv1.3 https://example.com
```

Use these primarily for troubleshooting or compatibility testing.

---

# mTLS Problems

Missing client certificate:

```text
handshake failure
```

Correct usage:

```bash
curl \
--cert client.crt \
--key client.key \
https://secure.example.com
```

---

# DNS Problems

Example:

```text
Could not resolve host
```

Verify DNS:

```bash
host example.com
```

or

```bash
dig example.com
```

or

```bash
doggo example.com
```

Since you've been using **doggo**, that's a great modern option on your system.

---

# Connection Refused

Error:

```text
Connection refused
```

Possible reasons:

- Server not running
    
- Wrong port
    
- Firewall
    
- Service crash
    

---

# Timeout

Error:

```text
Operation timed out
```

Possible causes:

- Network issues
    
- Firewall
    
- Server overload
    
- Routing problems
    

---

# HTTP vs HTTPS

Example:

```bash
curl http://example.com
```

Some servers respond:

```http
301 Moved Permanently
```

Redirecting to:

```text
https://example.com
```

Follow redirects automatically:

```bash
curl -L https://example.com
```

---

# Redirect Loops

Error:

```text
Too many redirects
```

Possible causes:

- Incorrect reverse proxy configuration
    
- HTTP/HTTPS redirect loop
    
- Misconfigured application
    

Verbose mode often reveals the repeating redirect chain.

# Common Mistakes

❌ **Using `-k` to hide certificate problems**

Fix the root cause instead of bypassing verification.

---

❌ **Ignoring `curl -v`**

Verbose output is often enough to identify the issue.

---

❌ **Checking only the HTTP status**

Many failures happen before the HTTP request is ever sent.

---

❌ **Ignoring DNS**

If the hostname doesn't resolve, TLS can't even begin.

---

❌ **Sharing verbose logs without review**

Logs can contain:

- Cookies
    
- Authorization headers
    
- API keys
    
- Bearer tokens
    

Redact sensitive information before sharing.

---

# Best Practices

- Start with `curl -v`.
    
- Use `openssl s_client` for certificate inspection.
    
- Measure DNS, TCP, and TLS timings separately.
    
- Avoid `--insecure` in production.
    
- Save traces for difficult issues.
    
- Review logs carefully before sharing them.

# Real-World Backend Example

Imagine your Express.js backend suddenly can't call a payment API.

You investigate:

```bash
curl -v https://payments.example.com
```

You notice:

```text
certificate has expired
```

The problem isn't your Node.js code.

The payment provider's TLS certificate has expired.

Without HTTPS debugging skills, you might spend hours searching for a bug in your application instead of identifying the real cause in minutes.

# Key Takeaways

- `curl -v` is your first tool for HTTPS debugging.
    
- `curl --trace` and `--trace-ascii` provide detailed diagnostics.
    
- `openssl s_client` is invaluable for certificate and TLS inspection.
    
- Diagnose issues systematically: DNS → TCP → TLS → HTTP → Application.
    
- Avoid bypassing certificate validation except for controlled testing.

# 💡 Backend Engineer Tip

A practical debugging sequence that many experienced backend engineers follow is:

```text
DNS
   ↓
TCP Connection
   ↓
TLS Handshake
   ↓
Certificate Validation
   ↓
Authentication
   ↓
HTTP Request
   ↓
Application Logic
```

By isolating the failure layer first, you'll solve production networking and API issues much faster than diving directly into application code.
