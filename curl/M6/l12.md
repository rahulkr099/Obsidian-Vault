# Authentication Function

```bash
login()
```

Responsibilities:

- Send credentials
    
- Receive token
    
- Save token
    
- Log success/failure
    

Example request:

```bash
curl \
-X POST \
-H "Content-Type: application/json" \
-d '{
      "email":"'"$API_USERNAME"'",
      "password":"'"$API_PASSWORD"'"
    }' \
"$API_BASE_URL/login"
```

Expected response:

```json
{
  "accessToken":"abc123",
  "expiresIn":3600
}
```

# Error Handling

Check status code:

```bash
STATUS=$(curl \
-s \
-o response.json \
-w "%{http_code}" \
-H "Authorization: Bearer $TOKEN" \
"$API_BASE_URL/users")
```

Decision:

```text
200

↓

Continue

401

↓

Re-authenticate

403

↓

Permission Denied

500

↓

Retry Later
```

# Common Mistakes

❌ Hardcoding credentials

```bash
PASSWORD="secret"
```

---

❌ Ignoring HTTP status codes

Always inspect:

```bash
%{http_code}
```

---

❌ Ignoring timeouts

Always specify:

```bash
--connect-timeout

--max-time
```

---

❌ Logging tokens

Never write:

```text
Authorization:
Bearer eyJ...
```

to log files.

---

❌ Assuming the token never expires

Always check expiration before using it.

# Best Practices

- Use `set -euo pipefail`
    
- Quote variables
    
- Use `jq` for JSON parsing
    
- Use HTTPS only
    
- Cache tokens securely
    
- Validate responses
    
- Retry transient failures
    
- Log important events
    
- Never expose secrets
    
- Clean up temporary files

# Key Takeaways

- Production API clients need more than just `curl`; they need token management, retries, logging, and secure configuration.
    
- Keep authentication, API logic, configuration, and utilities in separate modules.
    
- Cache tokens securely and verify they are still valid before use.
    
- Treat HTTP errors differently depending on whether they are authentication, authorization, client, or server errors.
    
- Never expose credentials or tokens in logs or source code.
