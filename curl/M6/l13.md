# Basic Download

```bash
curl \
-O \
https://example.com/file.zip
```

`-O`

Save using the remote filename.

---

# Save As

```bash
curl \
-o downloads/app.zip \
https://example.com/file.zip
```

---

# Follow Redirects

Many download URLs redirect.

```bash
curl \
-L \
-O \
https://example.com/download
```

---

# Resume Downloads

Interrupted download?

Continue it:

```bash
curl \
-C - \
-O \
https://example.com/file.zip
```

`-C -`

Resume automatically from where the previous download stopped.

---

# Retry Failed Downloads

```bash
curl \
--retry 5 \
-O \
https://example.com/file.zip
```

Retries transient failures.

---

# Retry Delay

```bash
curl \
--retry 5 \
--retry-delay 2 \
-O \
https://example.com/file.zip
```

Wait 2 seconds between retries.

---

# Retry Only Connection Failures

```bash
curl \
--retry-connrefused \
--retry 5 \
https://example.com/file.zip
```

Useful when a service is starting up.

---

# Timeout

```bash
curl \
--connect-timeout 5 \
--max-time 120 \
-O \
https://example.com/file.zip
```

- Connection timeout: 5 seconds
    
- Total timeout: 120 seconds

# Verify File Size

```bash
stat downloads/file.zip
```

or simply:

```bash
ls -lh downloads/file.zip
```

Unexpectedly tiny downloads can indicate an error page instead of the intended file.

---

# Verify SHA256

Expected checksum:

```text
9b74c9897bac770ffc029102a200c5de...
```

Generate checksum:

```bash
sha256sum downloads/file.zip
```

Compare the generated value with the expected checksum.

---

# Verify Automatically

```bash
sha256sum -c checksums/file.sha256
```

Example checksum file:

```text
9b74c9897bac770ffc029102a200c5de...  downloads/file.zip
```

Output:

```text
downloads/file.zip: OK
```

---

# Detect Corruption

If verification fails:

```text

```

Delete the corrupted file and download it again.

# Error Handling

|Status|Action|
|---|---|
|200|Verify checksum|
|301|Follow redirect|
|401|Re-authenticate|
|403|Permission denied|
|404|Stop|
|429|Retry after delay|
|500|Retry|
|Timeout|Retry|

# Rate Limiting

If the server responds:

```http
429 Too Many Requests
```

Back off before retrying.

A simple approach:

```text
Wait

↓

Retry
```

If the server sends a `Retry-After` header, respect that value.

# Partial Downloads

Suppose:

```text
2 GB ISO
```

Connection breaks at:

```text
1.3 GB
```

Resume:

```bash
curl \
-C - \
-O \
https://example.com/linux.iso
```

No need to start over.

# Parallel Downloads

For independent files:

```bash
curl -O https://example.com/a.zip &

curl -O https://example.com/b.zip &

wait
```

The shell waits until all background downloads finish.

# Common Mistakes

❌ Ignoring checksums

Always verify downloaded files when checksums are available.

---

❌ Downloading over HTTP

Prefer HTTPS to protect integrity and confidentiality.

---

❌ Using `-k`

Don't bypass certificate verification except for controlled testing.

---

❌ Ignoring redirects

Many download endpoints redirect.

Use:

```bash
-L
```

---

❌ Starting over after interruptions

Use:

```bash
-C -
```

---

# Best Practices

- Download over HTTPS.
    
- Verify checksums.
    
- Resume interrupted downloads.
    
- Use retries with sensible delays.
    
- Log all downloads.
    
- Respect rate limits.
    
- Use authentication when required.
    
- Set connection and overall timeouts.
    
- Validate downloaded content before using it.

## 💡 Backend Engineer Tip

This project models how software distribution works in practice. Package managers, deployment systems, and CI/CD pipelines rarely trust a download just because it completed successfully. They typically:

1. Download over HTTPS.
    
2. Verify the file's cryptographic checksum or signature.
    
3. Abort if verification fails.
    
4. Only then proceed with installation or deployment.
    

Adopting the same workflow in your own automation scripts will make them significantly more reliable and secure.
