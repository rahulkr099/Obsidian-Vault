# What is a Certificate?

A TLS certificate is a **digital identity card** for a website.

It tells your computer:

- Who the website claims to be
    
- Its public key
    
- Who verified it
    
- When it expires
    
- What domains it is valid for
    

Example:

```text
Subject: example.com

Issuer: Let's Encrypt

Valid Until: 2027-05-01

Public Key: RSA 2048-bit
```

---

# Certificate Components

A certificate contains many fields.

|Field|Purpose|
|---|---|
|Subject|Website identity|
|Issuer|Certificate Authority|
|Public Key|Used during TLS|
|Valid From|Start date|
|Valid To|Expiration date|
|SAN|Additional domain names|
|Signature|CA's digital signature|

---

# Subject

The **Subject** identifies the website.

Example:

```text
CN=example.com
```

Historically, the **Common Name (CN)** identified the primary domain.

Today, browsers primarily rely on the **Subject Alternative Name (SAN)** extension instead of the CN.

---

# Issuer

The issuer is the Certificate Authority that signed the certificate.

Example:

```text
Issuer:

Let's Encrypt
```

Other common issuers:

- DigiCert
    
- Sectigo
    
- GlobalSign
    
- Google Trust Services
    

---

# Validity Period

Certificates expire.

Example:

```text
Valid From:

2026-01-01

Valid Until:

2027-01-01
```

Expired certificates are rejected by browsers and `curl`.

---

# Public Key

The certificate contains the server's **public key**.

Example:

```text
RSA

2048 bits
```

or

```text
ECDSA

P-256
```

The matching **private key** never leaves the server.

---

# Subject Alternative Name (SAN)

Modern certificates can protect multiple domains.

Example:

```text
example.com

www.example.com

api.example.com
```

If you connect to a domain that isn't listed in the SAN, certificate validation fails.

---

# Digital Signature

The Certificate Authority signs the certificate.

```text
Certificate

↓

Signed by CA

↓

Verified by Browser/curl
```

If someone modifies the certificate, the signature check fails.

---

# View Certificate with `curl`

Verbose mode:

```bash
curl -v https://example.com
```

Look for lines like:

```text
SSL connection using TLSv1.3

Server certificate:
```

You'll also see:

- TLS version
    
- Cipher suite
    
- Certificate subject
    
- Certificate issuer
    

---

# View Only Headers

```bash
curl -I https://example.com
```

This doesn't show the certificate itself, but it's useful for verifying an HTTPS connection.

---

# Inspect with OpenSSL

One of the most useful commands:

```bash
openssl s_client -connect example.com:443
```

This displays:

- Certificate chain
    
- TLS version
    
- Cipher
    
- Handshake information
    
- Verification result
    

---

# Show Certificate Details

Pipe the certificate into `openssl x509`:

```bash
openssl s_client -connect example.com:443 </dev/null \
| openssl x509 -text -noout
```

This produces a detailed certificate report.

---

# Example Output

```text
Subject:
CN=example.com

Issuer:
Let's Encrypt

Not Before:
Jan 1 00:00:00 2026 GMT

Not After:
Apr 1 00:00:00 2026 GMT
```

---

# View Expiration Date Only

```bash
openssl s_client -connect example.com:443 </dev/null \
2>/dev/null \
| openssl x509 -noout -enddate
```

Example:

```text
notAfter=Apr 1 00:00:00 2026 GMT
```

---

# View Issuer Only

```bash
openssl s_client -connect example.com:443 </dev/null \
2>/dev/null \
| openssl x509 -noout -issuer
```

Example:

```text
issuer=C=US,O=Let's Encrypt,CN=R10
```

---

# View Subject Only

```bash
openssl s_client -connect example.com:443 </dev/null \
2>/dev/null \
| openssl x509 -noout -subject
```

Example:

```text
subject=CN=example.com
```

---

# Certificate Chain

Most websites use a chain.

```text
Root CA
      │
Intermediate CA
      │
Website Certificate
```

Your operating system trusts the Root CA.

The Root validates the Intermediate.

The Intermediate signs the website certificate.

---

# Why Use Intermediate CAs?

Instead of signing every website directly with the Root CA:

- The Root CA stays offline and highly protected.
    
- Intermediate CAs perform day-to-day signing.
    
- If an Intermediate is compromised, it can be replaced without replacing the Root CA.
    

---

# TLS Version

Verbose output often includes:

```text
TLSv1.3
```

Common versions:

|Version|Status|
|---|---|
|SSL 2.0|Obsolete|
|SSL 3.0|Obsolete|
|TLS 1.0|Deprecated|
|TLS 1.1|Deprecated|
|TLS 1.2|Widely supported|
|TLS 1.3|Current best practice|

---

# Cipher Suite

Example:

```text
TLS_AES_256_GCM_SHA384
```

This specifies the algorithms used to protect the connection.

You don't need to memorize cipher names, but it's useful to recognize them when debugging.

---

# Verify Certificate

OpenSSL reports whether verification succeeded.

Example:

```text
Verify return code: 0 (ok)
```

A return code of `0` indicates successful verification.

---

# Common Certificate Errors

|Error|Cause|
|---|---|
|Expired certificate|Certificate validity ended|
|Self-signed certificate|Not signed by a trusted CA|
|Unknown CA|Issuer isn't trusted|
|Hostname mismatch|Domain doesn't match certificate|
|Incomplete chain|Missing intermediate certificate|

We'll learn how to fix these in Lesson 3.

# Common Mistakes

❌ **Thinking the certificate contains the private key.**

Only the **public key** is included. The private key stays securely on the server.

---

❌ **Ignoring expiration dates.**

Expired certificates cause HTTPS failures even if everything else is configured correctly.

---

❌ **Confusing Subject and Issuer.**

- **Subject** = the website.
    
- **Issuer** = the Certificate Authority that signed it.
    

---

❌ **Assuming one certificate always means one domain.**

Modern certificates often protect multiple domains through the SAN extension.

---

# Best Practices

- Inspect certificates when troubleshooting HTTPS issues.
    
- Check expiration dates regularly.
    
- Verify the certificate chain is complete.
    
- Prefer TLS 1.2 or TLS 1.3.
    
- Renew certificates before they expire.
    

---

# Key Takeaways

- Certificates identify websites and enable secure TLS connections.
    
- A certificate contains the subject, issuer, public key, validity dates, SANs, and a digital signature.
    
- `curl -v` provides useful HTTPS connection details.
    
- `openssl s_client` is the primary tool for inspecting certificates.
    
- Certificate chains establish trust from the website back to a trusted Root CA.

## 💡 Backend Engineer Tip

When debugging API connectivity in production, one of the first checks is often the server's certificate:

```bash
openssl s_client -connect api.example.com:443
```

This single command can quickly reveal problems such as expired certificates, missing intermediate certificates, hostname mismatches, or unsupported TLS versions—issues that commonly cause HTTPS failures in backend systems.
