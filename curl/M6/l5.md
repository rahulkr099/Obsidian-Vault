# What is a Bearer Token?

A Bearer Token is a credential that proves you're authenticated.

Instead of sending:

```text
Username

Password
```

You send:

```text
Bearer Token
```

Workflow:

```text
Login
   │
Username + Password
   │
────────────►
Server
   │
Creates Token
   │
◄────────────
Bearer Token
   │
Future Requests
```

---

# Authorization Header

Bearer tokens are sent using the `Authorization` header.

Example:

```http
Authorization: Bearer eyJhbGciOi...
```

General format:

```http
Authorization: Bearer <token>
```

---

# Using `curl`

The standard way:

```bash
curl \
-H "Authorization: Bearer YOUR_TOKEN" \
https://api.example.com/users
```

---

# Example API Request

```bash
TOKEN="eyJhbGciOi..."

curl \
-H "Authorization: Bearer $TOKEN" \
https://api.example.com/profile
```

---

# Why Use Tokens?

Instead of storing your password in every application:

```text
Password

↓

Every Request
```

You authenticate once.

Then:

```text
Password

↓

Access Token

↓

Many Requests
```

Benefits:

- Password isn't repeatedly transmitted.
    
- Tokens can expire.
    
- Tokens can be revoked.
    
- Different permissions can be assigned.
    

---

# What is a JWT?

JWT stands for:

```text
JSON Web Token
```

A JWT is a compact, signed token.

Example:

```text
xxxxx.yyyyy.zzzzz
```

Notice the three sections separated by dots.

---

# JWT Structure

```text
HEADER

.

PAYLOAD

.

SIGNATURE
```

Example:

```text
eyJhbGci...

.

eyJ1c2VySWQi...

.

SflKxwRJS...
```

---

# Part 1 — Header

The header describes the token.

Example:

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

Meaning:

- Algorithm: HS256
    
- Type: JWT
    

---

# Part 2 — Payload

The payload contains claims.

Example:

```json
{
  "userId": 42,
  "name": "Rahul",
  "role": "admin",
  "exp": 1785200000
}
```

Common claims:

|Claim|Meaning|
|---|---|
|`sub`|Subject (user ID)|
|`iss`|Issuer|
|`aud`|Audience|
|`iat`|Issued at|
|`exp`|Expiration time|
|`nbf`|Not before|
|`jti`|Token ID|

Applications can also include custom claims like `role` or `department`.

---

# Part 3 — Signature

The signature protects the token from tampering.

Workflow:

```text
Header

+

Payload

+

Secret Key

↓

Signature
```

If someone changes the payload, the signature check fails.

---

# Important Security Rule

The payload is **Base64URL-encoded**, not encrypted.

Anyone who has the token can decode the header and payload.

For example, a payload like:

```json
{
  "role": "admin"
}
```

is readable after decoding.

**Never store sensitive information** (passwords, API secrets, credit card numbers, etc.) inside a JWT payload.

---

# Access Token

Access tokens are:

- Short-lived
    
- Used for API requests
    
- Sent with every request
    

Example:

```text
Valid

15 minutes
```

or

```text
1 hour
```

Exact lifetimes vary by application.

---

# Refresh Token

Refresh tokens are:

- Longer-lived
    
- Stored securely
    
- Used to obtain a new access token
    

Workflow:

```text
Access Token Expired
        │
Refresh Token
        │
────────────►
Server
        │
New Access Token
```

---

# Typical Authentication Flow

```text
Login
 │
 ▼
Server
 │
 ▼
Access Token

+

Refresh Token
 │
 ▼
API Requests
 │
 ▼
Access Token Expires
 │
 ▼
Use Refresh Token
 │
 ▼
Receive New Access Token
```

# Example Login

Request:

```http
POST /login
```

Body:

```json
{
  "email": "rahul@example.com",
  "password": "secret123"
}
```

Response:

```json
{
  "accessToken": "...",
```

# Using the Token

```bash
ACCESS_TOKEN="eyJhbGciOi..."

curl \
-H "Authorization: Bearer $ACCESS_TOKEN" \

```

---

# Expired Token

If the access token expires:

```http
HTTP/1.1 401 Unauthorized
```

The client typically uses the refresh token to obtain a new access token, then retries the request.

---

# Invalid Token

Example:

```http
HTTP/1.1 401 Unauthorized
```

Reasons include:

- Invalid signature
    
- Expired token
    
- Malformed token
    
- Token revoked
    

---

# 401 vs 403

|Status|Meaning|
|---|---|
|401|Missing, invalid, or expired authentication|
|403|Authentication succeeded, but access is not allowed|

---

# Environment Variables

Avoid hardcoding tokens.

❌ Bad

```bash
TOKEN="eyJhbGciOi..."
```

✅ Better

```bash
export API_TOKEN="eyJhbGciOi..."
```

Use:

```bash
curl \
-H "Authorization: Bearer $API_TOKEN" \
https://api.example.com/users
```

---

# Debugging

Verbose mode:

```bash
curl \
-v \
-H "Authorization: Bearer $API_TOKEN" \
https://api.example.com/users
```

Check:

- Request
    
- Response
    
- Status code
    
- Response headers
    

Be careful not to expose real tokens when sharing logs or screenshots.

# Common Mistakes

❌ **Treating JWTs as encrypted.**

JWT payloads are usually only encoded.

---

❌ **Putting secrets in JWT payloads.**

Anyone with the token can decode the payload.

---

❌ **Hardcoding tokens in source code.**

Use environment variables or a secure secret manager.

---

❌ **Using expired access tokens indefinitely.**

Handle `401` responses by refreshing the token or prompting the user to log in again.

---

# Best Practices

- Always send Bearer tokens over HTTPS.
    
- Keep access tokens short-lived.
    
- Store refresh tokens securely.
    
- Never log real tokens.
    
- Validate JWT signatures on the server.
    
- Use environment variables for local development.
    

---

# Real-World Backend Example

A React frontend logs a user in.

The backend returns:

```json
{
  "accessToken": "...",
  "refreshToken": "..."
}
```

The frontend sends:

```http
Authorization: Bearer eyJhbGciOi...
```

Your Node.js backend:

1. Verifies the JWT signature.
    
2. Checks the expiration time.
    
3. Reads claims such as `userId` and `role`.
    
4. Returns:
    

```http
HTTP/1.1 200 OK
```

or

```http
HTTP/1.1 401 Unauthorized
```

if the token is invalid or expired.

---

# Key Takeaways

- Bearer tokens authenticate API requests without sending passwords each time.
    
- JWTs consist of a **Header**, **Payload**, and **Signature**.
    
- JWT payloads are encoded, not encrypted.
    
- Access tokens are short-lived; refresh tokens are used to obtain new ones.
    
- Store tokens securely and send them only over HTTPS.

## 💡 Backend Engineer Tip

This lesson directly connects to your Node.js backend work. A common authentication flow is:

1. User logs in.
    
2. The server generates an **access token** (often a JWT) and, optionally, a **refresh token**.
    
3. The client includes the access token in the `Authorization: Bearer` header for API requests.
    
4. Backend middleware verifies the token before allowing access to protected routes.
    

This is the authentication pattern you'll encounter in many modern Express.js, NestJS, Spring Boot, and ASP.NET Core applications.
