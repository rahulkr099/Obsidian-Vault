# Why OAuth Exists

Imagine a travel website that wants to access your Google Calendar.

Without OAuth:

```text
Travel Website

↓

Ask for your Google password

↓

Very Dangerous
```

Problems:

- Website knows your password
    
- Full account access
    
- Can't limit permissions
    
- Hard to revoke safely
    

---

With OAuth:

```text
Travel Website

↓

Redirect to Google

↓

Google asks YOU

↓

Permission Granted

↓

Access Token
```

The travel website **never sees your Google password**.

---

# Authentication vs Authorization

This is one of the most important concepts.

|Authentication|Authorization|
|---|---|
|Who are you?|What can you access?|
|Login|Permissions|

Example:

```text
Login to Google

↓

Authentication

↓

Allow Calendar Access

↓

Authorization
```

OAuth primarily handles **authorization**.

Many services also use it as part of authentication ("Login with Google"), but the OAuth protocol itself is about delegated authorization.

---

# OAuth Roles

OAuth defines several participants.

```text
User

↓

Client App

↓

Authorization Server

↓

Resource Server
```

Let's understand each one.

---

## 1. Resource Owner

Usually:

```text
You
```

The owner of the data.

Example:

- Your GitHub repositories
    
- Your Google Drive
    
- Your Spotify playlists
    

---

## 2. Client

The application requesting access.

Examples:

- VS Code
    
- Your React app
    
- Mobile app
    
- CLI tool
    

---

## 3. Authorization Server

Responsible for:

- Login
    
- Asking for consent
    
- Issuing tokens
    

Examples:

- accounts.google.com
    
- github.com/login/oauth
    
- login.microsoftonline.com
    

---

## 4. Resource Server

Hosts the protected APIs.

Examples:

```text
Google Drive API

GitHub API

Microsoft Graph API
```

# Authorization Code Flow

This is the **most common OAuth flow** for web applications.

Step 1

User clicks:

```text
Login with Google
```

---

Step 2

Browser redirects:

```text
Your App

↓

Google Login
```

---

Step 3

User logs in.

---

Step 4

Google asks:

```text
Allow this app to:

✓ Read profile

✓ Read email
```

---

Step 5

Google redirects back with:

```text
Authorization Code
```

Example:

```text
code=ABC123XYZ
```

---

Step 6

Your backend exchanges that code for tokens.

```text
Authorization Code

↓

Google

↓

Access Token

+

Refresh Token
```

---

# Access Token

Used to call APIs.

Example:

```http
Authorization: Bearer ACCESS_TOKEN
```

---

# Refresh Token

Longer-lived.

Used to obtain a new access token without requiring the user to log in again.

---

# Client ID

Every OAuth application has a **Client ID**.

Example:

```text
123456.apps.googleusercontent.com
```

The Client ID is generally **public**.

It identifies your application.

---

# Client Secret

Example:

```text
GOCSPX-xxxxxxxxxxxxxxxx
```

The Client Secret is **confidential**.

Never expose it in:

- JavaScript
    
- React
    
- Mobile apps
    
- Public repositories
    

It belongs only on a trusted backend.

---

# Redirect URI

After login, the Authorization Server redirects the user back to your application.

Example:

```text
https://myapp.com/auth/callback
```

The redirect URI must usually match one of the URIs registered with the OAuth provider.

---

# Scopes

OAuth lets users grant limited permissions.

Examples:

```text
email
```

```text
profile
```

```text
calendar.readonly
```

```text
repo
```

Instead of full account access, the application receives only the permissions it requested and the user approved.

---

# Example Authorization Request

A simplified example:

```text
GET /authorize

client_id=12345

redirect_uri=https://myapp.com/callback

response_type=code

scope=email profile
```

---

# Exchanging the Code

Your backend sends:

```text
Authorization Code

↓

Authorization Server
```

Response:

```json
{
  "access_token": "...",
  "refresh_token": "...",
  "expires_in": 3600
}
```

# Using `curl`

Once you have an access token:

```bash
curl \
-H "Authorization: Bearer ACCESS_TOKEN" \
https://api.github.com/user
```

OAuth APIs ultimately use Bearer tokens just like you learned in Lesson 5.

---

# PKCE (Proof Key for Code Exchange)

PKCE (pronounced "pixy") improves security for:

- Mobile apps
    
- Single-page applications (SPAs)
    
- Public clients that cannot safely store a Client Secret
    

Instead of relying on a Client Secret, PKCE uses:

- Code Verifier (random secret)
    
- Code Challenge (derived from the verifier)
    

Simplified flow:

```text
Client

↓

Code Verifier

↓

Code Challenge

↓

Authorization Request

↓

Authorization Code

↓

Send Code Verifier

↓

Access Token
```

If an attacker steals the authorization code, they still cannot exchange it for a token without the original Code Verifier.

# Common Errors

## Invalid Redirect URI

```text
redirect_uri_mismatch
```

The redirect URI sent by the application doesn't match the registered URI.

---

## Invalid Client Secret

```text
invalid_client
```

The Client Secret is incorrect or missing.

---

## Expired Access Token

```http
HTTP/1.1 401 Unauthorized
```

Use the Refresh Token to obtain a new Access Token.

---

## Missing Scope

```http
HTTP/1.1 403 Forbidden
```

The token doesn't have permission to access the requested resource.

# OAuth vs API Keys

|OAuth|API Key|
|---|---|
|User authorization|Application identification|
|User consent|No user consent|
|Fine-grained permissions|Usually broader permissions|
|Access Token|Static key|
|Refresh Token|Usually none|

---

# OAuth vs JWT

|OAuth|JWT|
|---|---|
|Authorization framework|Token format|
|Defines how access is granted|Defines one way to represent a token|
|Can issue JWTs or opaque tokens|Often used as an OAuth Access Token|

OAuth and JWT are **not competitors**. An OAuth server may issue JWT access tokens, but it can also issue opaque (non-JWT) tokens.

# Common Mistakes

❌ **Confusing OAuth with JWT**

OAuth is a protocol.

JWT is a token format.

---

❌ **Exposing the Client Secret**

Never include it in frontend code or public repositories.

---

❌ **Requesting excessive scopes**

Ask only for the permissions your application actually needs.

---

❌ **Storing access tokens insecurely**

Protect tokens and send them only over HTTPS.

---

❌ **Ignoring Refresh Tokens**

Design your application to handle token expiration gracefully.

---

# Best Practices

- Always use HTTPS.
    
- Use the Authorization Code Flow for server-side web apps.
    
- Use PKCE for mobile apps and SPAs.
    
- Keep Client Secrets on the backend.
    
- Request the minimum required scopes.
    
- Validate tokens on the server.
    
- Rotate client credentials if compromised.

Suppose your Express.js application supports **"Sign in with GitHub."**

The flow looks like this:

```text
User
 │
 ▼
Clicks "Login with GitHub"
 │
 ▼
GitHub Login Page
 │
User Grants Permission
 │
 ▼
Authorization Code
 │
 ▼
Express Backend
 │
Exchange Code
 │
 ▼
Access Token
 │
 ▼
GitHub API
 │
 ▼
User Profile
```

Your backend never receives the user's GitHub password. It only receives tokens after GitHub authenticates the user and they approve access.

# Key Takeaways

- OAuth 2.0 is an **authorization framework**, not a login protocol.
    
- It allows applications to access user data without knowing the user's password.
    
- The Authorization Code Flow is the standard flow for server-side web applications.
    
- PKCE protects public clients from authorization code interception.
    
- Client IDs are public; Client Secrets must remain confidential.
    
- OAuth commonly uses Bearer tokens to access protected APIs.

## 💡 Backend Engineer Tip

Since you've worked with **Node.js/Express** and Google authentication before, it's worth connecting the concepts:

- **OAuth 2.0** gets permission from Google (or another provider).
    
- Google returns an **authorization code**.
    
- Your Express backend exchanges that code for **access** and **refresh tokens**.
    
- Your backend fetches the user's profile.
    
- Finally, **your own application** creates its own session or JWT for future requests.
    

This separation—using OAuth to verify identity and then issuing your application's own authentication token—is the architecture used by many production systems.
