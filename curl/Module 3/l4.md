# 1. HTTP vs HTTPS

## HTTP

```text
Browser
    │
    ▼
Internet
    │
    ▼
Server
```

Everything is sent **in plain text**.

Anyone on the network could potentially read:

- Passwords
    
- Tokens
    
- Cookies
    
- Personal data
    

---

## HTTPS

```text
Browser
    │
Encrypted Connection
    │
    ▼
Server
```

Now everything is encrypted.

Even if someone captures the traffic, they cannot easily read its contents.

---

# 2. What is TLS?

Historically:

```text
SSL
```

Modern systems actually use:

```text
TLS
```

Although people often say "SSL certificate," they almost always mean a **TLS certificate**.

---

# 3. What Happens When You Visit an HTTPS Site?

Example:

```text
https://example.com
```

Simplified flow:

```text
Client

↓

Hello

↓

Server

↓

Certificate

↓

Verify Certificate

↓

Generate Encryption Keys

↓

Encrypted Connection

↓

HTTP Requests
```

Only after the handshake completes do HTTP requests begin.

---

# 4. What Does a Certificate Contain?

A certificate includes information like:

```text
Domain:
example.com

Issuer:
Let's Encrypt

Valid From:
2026-01-01

Valid Until:
2026-04-01

Public Key
```

The browser checks that:

- The certificate matches the domain.
    
- It hasn't expired.
    
- It's signed by a trusted Certificate Authority (CA).
    

---

# 5. Inspect HTTPS with curl

Basic request:

```bash
curl -v https://httpbin.org/get
```

Notice lines similar to:

```text
* SSL connection using TLSv1.3

* Server certificate:

* subject:

* issuer:
```

This confirms a secure TLS connection was established.

# 6. View Response Headers

```bash
curl -Iv https://httpbin.org/get
```

Useful information includes:

```text
SSL connection using TLSv1.3

subject:

issuer:

HTTP/2 200
```

# 7. Common Certificate Authorities

Some well-known CAs include:

- Let's Encrypt
    
- DigiCert
    
- GlobalSign
    
- Sectigo
    
- Google Trust Services
    

Browsers and operating systems trust certificates issued by these authorities.

---

# 8. Self-Signed Certificates

During development you might encounter:

```text
https://localhost:3000
```

with a self-signed certificate.

Result:

```text
SSL certificate problem:
self signed certificate
```

The certificate isn't trusted because it wasn't signed by a recognized CA.

---

# 9. Ignore Certificate Verification (`-k`)

Development only:

```bash
curl -k https://localhost:3000
```

or

```bash
curl --insecure https://localhost:3000
```

This tells curl:

> "Skip certificate verification."

---

⚠️ **Never use `-k` in production.**

Doing so removes an important security check.

---

# 10. Why `-k` Is Dangerous

Suppose an attacker intercepts your connection.

Without verification:

```text
Client

↓

Attacker

↓

Real Server
```

Your client cannot verify it's talking to the legitimate server.

This weakens HTTPS security and can enable man-in-the-middle attacks.

---

# 11. Certificate Expired

Example error:

```text
SSL certificate problem:
certificate has expired
```

Fix:

- Renew the certificate.
    
- Restart the web server if needed.
    

Never ignore expired certificates in production.

---

# 12. Wrong Hostname

Example:

```text
https://api.example.com
```

Certificate:

```text
www.example.com
```

Result:

```text
SSL:
certificate subject name does not match target hostname
```

The certificate must match the hostname you are connecting to.

---

# 13. Unknown Certificate Authority

Example:

```text
SSL certificate problem:

unable to get local issuer certificate
```

Possible causes:

- Self-signed certificate
    
- Missing intermediate certificate
    
- Old CA bundle
    

---

# 14. Client Certificates (Mutual TLS)

Some enterprise APIs require both sides to authenticate.

Normal HTTPS:

```text
Client

↓

Server Certificate
```

Mutual TLS (mTLS):

```text
Client Certificate

↓

Server Certificate
```

Both verify each other.

---

# 15. Using a Client Certificate

```bash
curl \
--cert client.pem \
--key client.key \
https://example.com
```

Meaning:

```text
client.pem
```

contains the client certificate.

```text
client.key
```

contains the private key.

This is common in banking, healthcare, and internal enterprise APIs.

---

# 16. Custom CA Certificate

Suppose your company has its own CA.

Use:

```bash
curl \
--cacert company-ca.pem \
https://internal.example.com
```

Instead of trusting all certificates (`-k`), you're telling curl exactly which CA to trust.

---

# 17. Check TLS Version

Verbose mode shows:

```bash
curl -v https://httpbin.org/get
```

Example:

```text
SSL connection using TLSv1.3
```

Modern servers generally support:

- TLS 1.2
    
- TLS 1.3
    

Older protocols such as SSLv3 and TLS 1.0 are considered insecure and are typically disabled.

---

# 18. Force a TLS Version

Sometimes useful for debugging.

Force TLS 1.2:

```bash
curl \
--tlsv1.2 \
https://httpbin.org/get
```

Force TLS 1.3:

```bash
curl \
--tlsv1.3 \
https://httpbin.org/get
```

Only use versions supported by both client and server.

---

# 19. HTTPS Redirects

Many websites redirect:

```text
http://example.com
```

↓

```text
https://example.com
```

Follow automatically:

```bash
curl -L http://example.com
```

---

# 20. Debugging TLS Problems

Always start with:

```bash
curl -v https://example.com
```

Check:

✅ Certificate validity

✅ Certificate issuer

✅ Hostname match

✅ TLS version

✅ Redirects

Verbose output often identifies the problem immediately.

---

# 21. Common TLS Errors

|Error|Meaning|
|---|---|
|Certificate expired|Certificate needs renewal|
|Self-signed certificate|Not trusted by your system|
|Hostname mismatch|Wrong certificate for the domain|
|Unknown CA|Missing or untrusted certificate authority|
|Handshake failed|TLS negotiation problem|
|Connection reset|Network or server issue|

# 💡 Pro Tips

### 1. Prefer `--cacert` over `-k`

If you're working with an internal CA:

```bash
curl \
--cacert company-ca.pem \
https://internal.example.com
```

is much safer than:

```bash
curl -k https://internal.example.com
```

---

### 2. Always inspect TLS issues with verbose mode

```bash
curl -v https://example.com
```

This usually provides enough detail to determine whether the issue is with the certificate, hostname, or protocol negotiation.

---

### 3. Use HTTPS everywhere

For production APIs:

- Protect authentication tokens.
    
- Protect session cookies.
    
- Protect personal data.
    
- Encrypt all traffic between clients and servers.
