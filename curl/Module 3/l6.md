# 1. Why Timeouts Matter

Imagine your API never responds.

```text
Client
   │
GET /users
   │
   ▼
Server (stuck)
```

Without a timeout:

```text
curl

↓

Wait...

↓

Wait...

↓

Wait forever...
```

A timeout tells `curl`:

> "Stop waiting after a certain amount of time."

---

# 2. Types of Timeouts

There are two major types you'll use:

|Timeout|What It Controls|
|---|---|
|Connection Timeout|Time allowed to establish the connection|
|Maximum Time|Total time for the entire request|

These solve different problems.

---

# 3. Connection Timeout

Suppose a server doesn't even accept the connection.

Use:

```bash
curl \
--connect-timeout 5 \
https://example.com
```

Meaning:

> If a TCP/TLS connection isn't established within **5 seconds**, stop trying.

Example error:

```text
curl: (28) Failed to connect
```

---

# 4. Maximum Request Time

Sometimes the connection succeeds but the server is extremely slow.

```text
Connect ✓

↓

Waiting...

↓

Waiting...

↓

Waiting...
```

Limit the total request time:

```bash
curl \
--max-time 10 \
https://example.com
```

Meaning:

> Abort the request if it takes longer than **10 seconds** overall.

---

# 5. Difference Between the Two

Imagine this timeline:

```text
0 sec --------2 sec-----------15 sec

Connect      Server Processing

```

With:

```bash
--connect-timeout 5
```

Connection succeeds.

No problem.

---

With:

```bash
--max-time 10
```

The request is cancelled at 10 seconds because the overall request exceeded the limit.

---

# 6. Combining Both

Very common in production:

```bash
curl \
--connect-timeout 3 \
--max-time 15 \
https://api.example.com/users
```

Meaning:

- Connect within 3 seconds
    
- Finish everything within 15 seconds
    

---

# 7. Retrying Failed Requests

Networks fail.

Servers restart.

Packets get lost.

Instead of failing immediately:

```bash
curl \
--retry 3 \
https://example.com
```

Flow:

```text
Attempt 1 ❌

↓

Attempt 2 ❌

↓

Attempt 3 ✅
```

---

# 8. Retry Delay

Default retry timing may not suit every situation.

Specify a delay:

```bash
curl \
--retry 5 \
--retry-delay 2 \
https://example.com
```

Meaning:

Retry every **2 seconds**.

---

# 9. Retry Only Connection Refused

Sometimes you only want retries when the server is temporarily unavailable.

```bash
curl \
--retry 5 \
--retry-connrefused \
http://localhost:3000
```

Useful when waiting for a development server or container to start.

---

# 10. Retry All Errors

Sometimes APIs return:

```text
500
502
503
504
```

Retry them:

```bash
curl \
--retry 5 \
--retry-all-errors \
https://example.com
```

This is especially useful in automation scripts.

---

# 11. Measuring Request Time

One of curl's most powerful features.

```bash
curl \
-w "\nTotal Time: %{time_total}s\n" \
-o /dev/null \
-s \
https://httpbin.org/get
```

Example:

```text
Total Time: 0.253s
```

---

# 12. Useful Timing Variables

```bash
curl -w "
DNS Lookup: %{time_namelookup}
Connect: %{time_connect}
TLS: %{time_appconnect}
First Byte: %{time_starttransfer}
Total: %{time_total}
"
```

Meaning:

|Variable|Measures|
|---|---|
|`time_namelookup`|DNS resolution|
|`time_connect`|TCP connection|
|`time_appconnect`|TLS handshake|
|`time_starttransfer`|Time until first response byte|
|`time_total`|Entire request|

---

# 13. Save Response While Measuring

```bash
curl \
-o response.json \
-w "\nTotal: %{time_total}s\n" \
https://httpbin.org/get
```

Now you have:

- Response saved
    
- Performance measured
    

---

# 14. Keep-Alive Connections

Without Keep-Alive:

```text
Request 1

Connect

Disconnect

↓

Request 2

Connect

Disconnect
```

Many unnecessary connections.

---

With Keep-Alive:

```text
Connect Once

↓

Request 1

↓

Request 2

↓

Request 3

↓

Disconnect
```

Much faster.

HTTP/1.1 uses persistent connections by default unless disabled.

---

# 15. HTTP/2 Improvements

HTTP/1.1:

```text
Connection

↓

Request

↓

Response

↓

Request

↓

Response
```

Sequential communication.

---

HTTP/2:

```text
Connection

↓

Request 1

Request 2

Request 3

↓

Responses
```

Multiple streams can share one connection.

Benefits:

- Lower latency
    
- Better bandwidth utilization
    
- Fewer TCP connections
    

---

# 16. Detect HTTP Version

```bash
curl -I https://httpbin.org/get
```

Example:

```text
HTTP/2 200
```

or

```text
HTTP/1.1 200 OK
```

---

# 17. Force HTTP Version

Force HTTP/1.1

```bash
curl \
--http1.1 \
https://httpbin.org/get
```

---

Force HTTP/2

```bash
curl \
--http2 \
https://httpbin.org/get
```

Useful for testing compatibility.

---

# 18. Fail on HTTP Errors

Normally:

```text
404

↓

curl exits successfully
```

To treat HTTP errors as failures:

```bash
curl \
--fail \
https://httpbin.org/status/404
```

Result:

```text
curl: (22)
The requested URL returned error: 404
```

This is very useful in Bash scripts.

---

# 19. Silent + Fail

A common production combination:

```bash
curl \
-s \
--fail \
https://example.com
```

No progress meter.

Fails correctly.

Ideal for automation.

---

# 20. Production Example

```bash
curl \
-s \
--fail \
--retry 5 \
--retry-delay 2 \
--connect-timeout 3 \
--max-time 20 \
-H "Authorization: Bearer $TOKEN" \
https://api.example.com/users
```

This command is robust enough for many production scripts.

---

# 21. Health Checks

Many deployments periodically verify application health.

```bash
curl \
--fail \
https://example.com/health
```

Success:

```text
200 OK
```

Failure:

```text
500
```

Automation can use the exit code to decide whether the service is healthy.

---

# 22. Debugging Slow APIs

Suppose users report:

> "The API is slow."

Run:

```bash
curl \
-o /dev/null \
-s \
-w "
DNS: %{time_namelookup}
Connect: %{time_connect}
TLS: %{time_appconnect}
TTFB: %{time_starttransfer}
Total: %{time_total}
" \
https://example.com
```

Interpretation:

|Observation|Possible Cause|
|---|---|
|High DNS time|DNS resolver issue|
|High connect time|Network latency|
|High TLS time|Slow TLS handshake|
|High TTFB|Slow backend/database|
|High total time|Large response or multiple delays|

# 23. Common Timeout Errors

### Connection timeout

```text
curl: (28)
Connection timed out
```

---

### Maximum time exceeded

```text
curl: (28)
Operation timed out
```

---

### Server unavailable

```text
503 Service Unavailable
```

Often temporary—retries may help.

# 24. Best Practices

✅ Always set timeouts in automation.

```bash

```

---

✅ Retry transient failures.

```bash
--retry 3
```

---

✅ Use `--fail` in scripts.

---

✅ Measure performance with `-w`.

---

✅ Check HTTP status codes before parsing responses.

# 💡 Pro Tips

### 1. A solid default for automation

```bash
curl \
-s \
--fail \
--connect-timeout 5 \
--max-time 30 \
--retry 3
```

This combination works well for many scripts and CI/CD pipelines.

---

### 2. Separate network and server issues

If:

- `time_connect` is high → investigate networking.
    
- `time_starttransfer` is high → investigate backend logic or databases.
    

This distinction saves a lot of debugging time.

---

### 3. Use exit codes in Bash

```bash
if curl --fail -s https://example.com/health > /dev/null; then
    echo "Healthy"
else
    echo "Unhealthy"
fi
```

Using the exit status is more reliable than parsing response text.
