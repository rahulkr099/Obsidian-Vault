# 1. Why Compression Exists

Imagine your server returns:

```text
10 MB JSON
```

Without compression:

```text
Server

↓

10 MB

↓

Client
```

This:

- Takes longer
    
- Uses more bandwidth
    
- Costs more money
    
- Feels slower
    

---

With compression:

```text
10 MB JSON

↓

Compressed

↓

1.8 MB

↓

Client
```

Much faster.

---

# 2. How Compression Works

Client sends:

```http
Accept-Encoding: gzip
```

Server replies:

```http
Content-Encoding: gzip
```

Response body:

```text
Compressed Binary Data
```

The client decompresses it automatically.

---

# 3. Request vs Response

Request:

```http
GET /users

Accept-Encoding: gzip
```

Response:

```http
HTTP/1.1 200 OK

Content-Encoding: gzip
```

Remember:

|Header|Direction|
|---|---|
|Accept-Encoding|Client → Server|
|Content-Encoding|Server → Client|

---

# 4. Common Compression Algorithms

|Algorithm|Usage|
|---|---|
|gzip|⭐⭐⭐⭐⭐ Most common|
|Brotli (br)|⭐⭐⭐⭐⭐ Modern web|
|Deflate|⭐⭐⭐ Legacy support|
|zstd|⭐⭐⭐⭐ Increasing adoption|

---

# 5. Gzip

The most widely supported compression.

Request:

```http
Accept-Encoding: gzip
```

Response:

```http
Content-Encoding: gzip
```

Works with nearly every HTTP client.

---

# 6. Brotli (br)

Modern browsers often prefer Brotli.

Example:

```http
Accept-Encoding: br
```

Response:

```http
Content-Encoding: br
```

Advantages:

- Better compression than gzip
    
- Often smaller responses
    
- Excellent for HTML, CSS, and JavaScript
    

---

# 7. Deflate

Older compression method.

```http
Content-Encoding: deflate
```

Still supported, but gzip and Brotli are more common today.

---

# 8. Ask for Compression

Manual request:

```bash
curl \
-H "Accept-Encoding: gzip" \
https://httpbin.org/gzip
```

Response:

```http
Content-Encoding: gzip
```

However, the body remains compressed unless curl is instructed to decompress it.

---

# 9. Automatic Compression

The recommended approach:

```bash
curl \
--compressed \
https://httpbin.org/gzip
```

`--compressed` tells curl to:

1. Advertise supported compression methods.
    
2. Automatically decompress the response before displaying it.
    

This is what you'll usually use.

---

# 10. Inspect Headers

```bash
curl \
-I \
--compressed \
https://httpbin.org/gzip
```

Look for:

```http
Content-Encoding: gzip
```

or

```http
Content-Encoding: br
```

---

# 11. Verify What curl Sends

```bash
curl \
-v \
--compressed \
https://httpbin.org/gzip
```

You'll see something similar to:

```text
> Accept-Encoding: deflate, gzip, br, zstd
```

depending on how your version of curl was built.

---

# 12. Text vs Binary Responses

## Text

Examples:

```text
HTML

JSON

CSS

JavaScript
```

These compress very well.

---

## Binary

Examples:

```text
PNG

JPEG

MP4

ZIP
```

These are usually already compressed.

Compressing them again provides little or no benefit.

---

# 13. Compression Savings

Example:

Without compression:

```text
JSON

10 MB
```

With gzip:

```text
1.9 MB
```

Bandwidth saved:

```text
81%
```

Large APIs can save significant bandwidth and improve response times.

---

# 14. Download Files

Regular download:

```bash
curl \
-O \
https://example.com/file.json
```

Compressed download:

```bash
curl \
-O \
--compressed \
https://example.com/file.json
```

The file you save is the decompressed content, ready to use.

---

# 15. Saving Compressed Data As-Is

Sometimes you want the compressed bytes exactly as sent by the server (for debugging or archival). In that case, **do not** use `--compressed`.

Example:

```bash
curl \
-H "Accept-Encoding: gzip" \
-o response.gz \
https://example.com/data
```

Now you have the compressed payload.

---

# 16. Measuring Transfer Size

Use:

```bash
curl \
-o /dev/null \
-s \
-w "
Downloaded: %{size_download} bytes
" \
--compressed \
https://httpbin.org/gzip
```

Example output:

```text
Downloaded: 357 bytes
```

Useful variables:

|Variable|Meaning|
|---|---|
|`%{size_download}`|Response body size received|
|`%{speed_download}`|Average download speed|
|`%{time_total}`|Total request time|

---

# 17. Compression in Express

Enable compression middleware:

```bash
npm install compression
```

Example:

```javascript
import compression from "compression";

app.use(compression());
```

Now Express automatically compresses eligible responses when clients support it.

---

# 18. When Servers Don't Compress

Possible reasons:

- Response is too small
    
- Compression disabled
    
- Binary content
    
- Client didn't send `Accept-Encoding`
    

Check:

```bash
curl \
-v \
--compressed \
URL
```

---

# 19. Common Compression Issues

## Missing Accept-Encoding

```http
GET /users
```

Server sends:

```text
Large uncompressed response
```

---

## Correct Request

```http
GET /users

Accept-Encoding: gzip
```

Server sends:

```text
Small compressed response
```

---

## Double Compression

Avoid compressing data that's already compressed, such as:

- ZIP files
    
- JPEG images
    
- MP4 videos
    

This wastes CPU without reducing size.

↓

---

# 22. Compression vs HTTPS

Compression and encryption are different:

```text
Server

↓

Compress

↓

Encrypt (TLS)

↓

Internet

↓

Decrypt

↓

Decompress

↓

Application
```

Compression reduces size.

TLS protects confidentiality.

# 💡 Pro Tips

### 1. Prefer `--compressed`

Instead of manually setting:

```http
Accept-Encoding: gzip
```

use:

```bash
curl --compressed URL
```

It automatically negotiates supported compression and decompresses the response.

---

### 2. Compress text, not already-compressed files

Great candidates:

- JSON
    
- HTML
    
- CSS
    
- JavaScript
    
- XML
    

Poor candidates:

- ZIP
    
- PNG
    
- JPEG
    
- MP4
    
- PDF (often already compressed internally)
    

---

### 3. Verify compression with verbose mode

```bash
curl \
-v \
--compressed \
URL
```

Check:

- Request contains `Accept-Encoding`
    
- Response contains `Content-Encoding`
    

This quickly confirms whether compression is actually being used.
